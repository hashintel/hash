Petrinaut is a visual editor and simulation runtime for Stochastic Dynamic
Coloured Petri Nets (SDCPN). This documentation has two kinds of page, and
each is maintained in its own way.

**Generated pages** are everything under [Architecture](architecture). Every
build extracts them from annotations in the source and from the references
the type checker resolves between files. A reference needs no import: reading
a property off a value whose type another file declares counts. Layer sizes
and dependency counts come from the code, and
`yarn workspace @apps/petrinaut-docs lint:arch-docs` fails when an annotation
and the code disagree.

**Authored pages** are this one and the guides. They carry the reasons a
dependency graph cannot supply: why a boundary sits where it does, which
alternatives were ruled out, which mistakes are easy to make. Nothing checks
their prose against the code, so they leave to the generated pages what those
already state.

## The diagrams

On a generated page, a box is a layer. A solid arrow is counted from the
references between files, and a dashed arrow is an edge a `@talksTo` tag
declares. There are three kinds of diagram:

- The [Architecture](architecture) page opens with the **top-level layers**:
  the whole system, with everything below the first level folded into its
  parent.
- Every layer page opens with its **neighbourhood**: what that layer depends
  on, and what depends on it.
- A layer that has sub-layers also gets a **drill-down** of its direct
  children.

Where a layer has more neighbours than fit legibly, the remainder is drawn as
one "further layers" node, and the tables on the page list all of them.

## Guides

A guide describes one layer as the code is. The tables of
[Building blocks](doc:building-blocks) link every guide beside its block. The

- [How a step is computed](doc:core.simulation.engine/stepping): the fixed

### Editor

How `@hashintel/petrinaut` is put together: what the React layer provides and
what the UI layer mounts.

![The host mounts the Petrinaut component, which creates a core instance, mounts the React providers and renders the editor view; the preview creates an instance of its own and mounts the same canvas and panel parts without the editor view](@diagrams/editor-layers.svg)

- [The React layer](doc:react/react-layer): the providers and hooks that mirror
  Core state into React, the order the providers nest in, and which hook to
  call for what.
- [Editor state](doc:react.state/editor-state): who owns each piece of the
  state of an editing session, who writes it, and which hook reads it.
- [Panel geometry outside React state](doc:react.state/panel-sizes): how a
  panel drag or slide changes the page without rendering the editor.
- [The life of a run](doc:react.simulation/simulation-session): how the React
  layer configures a run, starts it, plays it back and hands its frames to the
  canvas and the timeline.
- [The UI layer](doc:ui/ui-layer): what the Petrinaut component mounts, and
  where a new part of the editor goes.
- [Sub-views](doc:ui.sub-view/sub-views): the descriptor a panel lists for each
  section or tab, and the containers that render one.
- [The canvas](doc:ui.views.canvas/canvas): how the active net becomes an
  interactive graph, and what renders for each gesture.
- [The arc layer](doc:ui.views.canvas.react-flow/arc-layer): how every arc is
  drawn in one `svg`, and what each keeps of an edge of React Flow.
- [The fade of a node](doc:ui.views.canvas.react-flow/node-fade): how a node
  outside a highlight is drawn without an opacity, and where it differs.
- [The editor shell](doc:ui.views.editor/editor-shell): the regions of the
  editor, what mounts in each mode and what places each region.
- [Monaco](doc:ui.monaco/monaco): one load of Monaco, one model per document
  URI, and how typing reaches the document.

Layer rules in `archinaut.config.ts` hold the directions between these parts.
`yarn workspace @apps/petrinaut-docs lint:arch-docs` fails on a dependency that
breaks one. The [Architecture](architecture) page lists every rule with its
reason under "Enforced rules"; one is that [react](layer:react) never depends
on [ui](layer:ui).

## Design notes

A design note is a proposal, a plan or a list of gaps. It says what is to be
built or changed, so parts of it describe code that does not exist, or code as
it was. [Writing a layer guide](doc:maintaining/writing-a-guide) exempts these
pages from the guide template.

- [Event-driven simulation](doc:core.simulation/event-driven-design): the
  proposal for the [event trace](layer:core.simulation.event-trace), which is
  built, with the reasons behind its steppers. Its opening describes Quick
  Simulation as it was before the trace: one frame per fixed step.
- [Next steps](doc:core.composition/next-steps): what composition does not do
  yet, in the order it is expected to come, and what each step needs first.
- [Handle contract gaps](doc:core.handle/contract-gaps): where the
  `PetrinautDocHandle` contract leaves behaviour open, what happens today, and
  the change each gap calls for.

## The packages at a glance

`@hashintel/petrinaut-core` is the headless half: the document model, the HIR
compiler for user-authored code, the simulation runtimes, and the language
server. It has no React, no DOM and no Monaco, so it runs unchanged in Node
and inside workers.

`@hashintel/petrinaut` is the editor built on top. It splits into a React layer
that owns state and a UI layer that renders it.

`petrinaut-optimizer-core` is the Python package with the Optuna study logic
behind the editor's optimizer. The core's browser runtime loads it under
Pyodide in a worker; the
[browser runtime](doc:core.optimization.browser/browser-runtime) page covers
how a study runs. It declares one layer, `optimizer-core`.

`@apps/petrinaut-website` is the demo site and the host that embeds the editor.
Its layers cover the routes, the example catalog, the plugins, and the Vercel
functions in `api/`. These pages describe how it drives Petrinaut:
[Router integration](doc:website.routes/router-integration) for the navigation
contract, [oEmbed](doc:website.api/embedding) for the embed endpoint,
[The demo site's plugins](doc:website.plugins/plugins) for the plugins it gives
the editor, and
[Experiments in AI chat](doc:website.plugins.petrinaut-ai-chat/experiment-chat)
for the experiment card of its assistant.
