A layer guide is a hand-written `.mdx` page beside a layer's code that explains
why the layer has its shape. The generated layer page states the role, the
folder, the size and the dependencies, and TSDoc states the signatures. A guide
repeats neither.

![Annotations and references produce the layer page, so a guide carries reasons, and the build checks its links, its MDX and its diagram](@diagrams/guide-sources.svg)

## Template

```mdx
---
title: <Layer name>
description: <the @role sentence>
sidebar_order: <n>
---

<The @role sentence, then what the layer owns and what it leaves to others.>

![<A caption that states the takeaway>](./<name>.d2)

## Entry point

<The file and the exported symbol. The parts it composes, in order.>

## Interface

<Three to seven names a caller starts from, or the files other blocks import and what each gives.>

## Protocol

<Optional. The contract the layer owns: the messages of a channel, or the value of a context.>

## Data flow

<Numbered steps of one user action, using the arrow labels of the diagram.>

## Rules

<A checkable sentence, its reason, and the test, lint rule or layer rule that holds it.>

## Pitfalls

<Symptom, cause, the rule that avoids it.>
```

The first sentence defines the layer. A page that needs two definitions is two
pages. A guide above about 500 words says why it is longer.

A `README.md` that declares a layer is that layer's page, so it takes the same
sections, and it needs no diagram.

## Interface and protocol

The Interface section says where a caller starts. In a layer with one entry
it names what the entry exports. In a layer without one it is a table of the
files other blocks import, with what a caller takes from each. It leaves out
the files that only the layer itself imports.

A layer has a Protocol section when it owns a contract that two sides must
keep: a worker channel, the value of a context, the shape of a store, or a
lifecycle. The section states the contract and names the file that defines
it. [Building blocks](doc:building-blocks) links each protocol from its
block's row.

A worker channel has a page of its own beside the file that defines its
messages, named `protocol.mdx`, with these sections:

| Section            | What it states                                                           |
| ------------------ | ------------------------------------------------------------------------ |
| Messages           | Each message in each direction, with its payload and its effect.         |
| One run end to end | The messages of one exchange in order, from the first to the last.       |
| Flow control       | What bounds how far one side runs ahead of the other.                    |
| Lifecycle          | The states of each side, and the message that moves it from one to next. |

[Worker protocol and backpressure](doc:core.simulation.worker/protocol) is
the model for such a page.

## Design notes and measurements

Two kinds of page are no layer guides, and the template does not apply to
them.

- A **design note** proposes or plans: a design that is not built, an order
  of work, a list of gaps. It may describe code that does not exist and code
  as it was.
- A **measurement** page reports costs, the revision and the machine they
  were taken on, and the way to reproduce them.

Both may be long, and both may carry history. The [index](doc:index) lists
them under "Design notes" and "Measurements", apart from the guides.

## What a guide leaves out

| Left out                                 | Reason                                                                                                                                    |
| ---------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| Lists of files, exports and dependencies | The code lists the first two, the layer page the dependencies. The Interface section is the exception: it names what other blocks import. |
| Signatures and parameter lists           | TSDoc on the export has them, and the editor shows them on hover.                                                                         |
| Counts, versions, dates, people, tickets | They change while the page stays the same.                                                                                                |
| History                                  | A guide describes the code as it is.                                                                                                      |

A flaw that needs a refactor is the one place for a ticket: it gets a
`:::danger` aside that names the flaw and its ticket.

## The diagram

A guide has one D2 diagram, in a `.d2` file beside it.
[Declaring layers](doc:maintaining/declaring-layers) shows how a page
references it.

- It has at most about fifteen nodes. A larger subject is split by user action.
- Each arrow has one direction and a verb as its label.
- The caption states what the reader should take from it.
- A legend names the line styles when the diagram uses two.
- A label that contains `:` or `[` is quoted.

## What the build checks

| Rule                                                                 | Reason                                                         | Check                                                |
| -------------------------------------------------------------------- | -------------------------------------------------------------- | ---------------------------------------------------- |
| Every `layer:` and `doc:` link names a layer or a page that exists.  | A renamed layer or page would leave a link that leads nowhere. | `yarn workspace @apps/petrinaut-docs lint:arch-docs` |
| A dependency that a rule in `archinaut.config.ts` forbids is absent. | A guide can then state the direction as a fact.                | `yarn workspace @apps/petrinaut-docs lint:arch-docs` |
| The MDX compiles, each formula parses and each D2 file renders.      | The check reads a page without compiling it.                   | `yarn workspace @apps/petrinaut-docs build`          |

No build checks that a symbol in backticks exists. Search for each one in the
code before the page is committed.
