---
title: Two execution paths
description: Why a single run and an experiment each have a runtime and a memory model of their own.
sidebar_order: 1
---

A net runs in one of two ways: as a single run the user plays back, or as an
experiment of many runs that returns aggregates. Each way has a runtime and a
memory model of its own.

**Quick Simulation** is a single run, recorded as events. The
[simulator registry](layer:core.simulators) starts it through
`createEventSimulation`. The worker records the states its stepper finds worth
keeping, and the main thread reads the state at any time by interpolating
between them. The [event trace](layer:core.simulation.event-trace) layer holds
this path.

**Experiments** run many Monte Carlo simulations with bounded memory, two
reusable buffers per run, and send only metric aggregates to the main thread.
Frame buffers never leave the worker.

## Why an experiment does not reuse the single run

An experiment is hundreds or thousands of runs. Keeping the recorded states of
each, even until the run ends, makes peak memory scale with run length times
concurrency.

## What this means when changing code

The two paths share the step. The files named here are under
`libs/@hashintel/petrinaut-core/src/simulation`. A fixed step of a run is
`advanceRun` in `monte-carlo/advance-run.ts`, built on `frame-operations.ts`
and `transition-effect.ts` beside it. The Monte Carlo simulator calls it for each
run of an experiment, and the fixed-step and untimed
[steppers](layer:core.simulation.steppers) call it for Quick Simulation. The
adaptive stepper has an advance of its own in `steppers/adaptive-stepper.ts`,
on the same run buffers, and serves both paths as well.

`computeNextFrame` in [the engine](layer:core.simulation.engine) is a second
implementation of the step, in `engine/compute-next-frame.ts`. It serves the
`compiled-model` entry, which runs a net in the calling thread, and neither
path of the editor. A change to the order of a step is made in both files.

The runtimes around the step are separate, so a change to how a run starts or
ends is made once in [the event trace](layer:core.simulation.event-trace) and
once in [the Monte Carlo runtime](layer:core.simulation.monte-carlo).

## Actual mode is a third source of frames

Actual mode renders an execution that came from a live external system, with
no simulation behind it. The canvas and the timeline read frames through the
[execution-frame interface](layer:react.execution-frame), so they show such an
execution with the code that shows a run. For a run, a frame behind that
interface is a recorded event.
