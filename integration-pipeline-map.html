What the compare stage does

It is not a second diff of the data. The stage 4 diff already decides what changed, and that decision rides along as the "changed" hint. The compare stage (finalize_projection_plan) merges the plan with projection N-1, object by object, to produce a complete projection N:

  1. No hint: take N-1's bytes instead of the new ones, and send nothing. The new bytes differ only by loadedAt.
  2. Hint: take the new bytes. Send them only if their sha256 differs from N-1's. Across runs it always differs, because of loadedAt.
  3. Only in N-1: archive it if the plan covered every source, otherwise carry it over. This catches objects of a sink that was removed from the definition.
  4. Already archived: carry it, with its archive request, forever.

So for the writes themselves, yes: you can plan them straight from the diff. Upsert the inserted and updated rows, and archive the deleted IDs. The compare stage only exists to maintain a stored projection.

Could we drop the stored projection?

Your proposal: keep the capture and a hash table per run (the snapshot already is one per state version), derive the changes from them, and store no projection. For the monorepo, I think this works. The main reason labs needed the projection does not carry over.

Why labs needed exact bytes. Labs writes loadedAt into every property's provenance (row_to_entity_op). Resending an unchanged row with a new loadedAt would therefore change property metadata and create a new Graph edition. Keeping N-1's bytes avoided that.

Why the monorepo doesn't. The monorepo planner (BE-1123) writes no property provenance; only the edition carries loadedAt. The Graph returns a patch as unchanged when properties, property metadata, types, draft, archived state and confidence all match, and it does not compare edition provenance (postgres-store, knowledge/entity/patch.rs). Resending an unchanged entity costs a request but writes nothing.

What we give up.

  • A record of the desired Graph state that does not depend on code. If N-1 is planned again by newer code, the bodies take today's shape with N-1's values. For a restore that is arguably what you want.
  • Restore and reconcile cost a pipeline run instead of a file read. Both are rare.
  • With roll-forward, a failed run leaves the Graph holding a mix of N-1 and N values until the next run. It already does that during any delivery that is in flight.
  • Everything that shapes a request has to change the hash or a version: the mapped columns (already hashed), the sink config (already a config hash), the planner and encoding version, and connector-level provenance settings. Labs bumps the hash version to force a full resend; the same mechanism covers these.

What stays the same. Retries: captures are bound per run, planning is deterministic, the effect file is written once and delivery resumes at its cursor. The state version still names the snapshot, so a state is adopted or abandoned as a unit.

What it would change in the tickets. BE-1116 (the projection, about 1,200 lines) would mostly go. BE-1117 would write one effect file instead of indexes, pages and packs. BE-1154 (restore) would need a decision between roll-forward and replanning N-1. Before deciding, confirm the Graph no-op holds for links and archives, and that nobody needs per-property provenance later; adding it would bring the labs reason back.

Where a run resumes

The orchestration crate (hashintel/hash#10410, BE-1132) runs an integration as a run function that requests named steps. A finished step's output is recorded. When the run executes again, recorded steps return their output without running, and the run continues at the first unrecorded step. Only capture and plan are named in a ticket (BE-1152); the other step names follow labs and BE-1153.

Where publishing happens

The end of planning uploads the workspace as snapshot N (RunPlanner::build_candidate in orchestrator/planning.rs). It returns an in-memory candidate: the plan, the snapshot ref and the digests. The worker passes that candidate straight to plan_apply in graph/apply.rs. That function loads projection N-1, compares, and writes projection N, state version N, the effect index and the work manifest, in that order. Only then does it record WorkPlanned. Each file is written before the record that names it.

In the monorepo, BE-1152 keeps the plan out of the plan step's output, and BE-1153 publishes it in the apply. Neither ticket yet says how the plan gets from one to the other.

Where it looks heavier than it needs to

  1. The stored projection may not be needed in the monorepo

    See "Could we drop the stored projection?" above. Without it, planning, the S3 writes and restore all scale with changes instead of the whole dataset.

  2. Paging bounds file sizes; it doesn't reduce reads

    Only delivery's archive lookup reads pages selectively. If the projection stays, one pack plus one sorted Parquet table of objects would do the same job.

  3. The plan's hand-off from plan to publish is not decided

    Labs passes it in memory. The monorepo tickets put planning and publishing in separate steps.

  4. Size ceilings

    The 4 MiB index allows roughly 1.5 to 1.8 million objects. A payload may be 4 MiB, but /entities/bulk uses axum's default 2 MB body limit, and bulk chunks are sized by count.

  5. The tickets port two delivery designs

    BE-1111, BE-1115, the diff_and_sync half of BE-1108 and the pending-link staging in BE-1112 port labs' older direct sync, which nothing calls at 40a8d14.
