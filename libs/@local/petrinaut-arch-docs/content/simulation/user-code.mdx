Dynamics, lambdas, kernels, metrics and scenario code all compile through the
HIR: user TypeScript is lowered to a source-spanned IR and checked against the
net. The hot-path surfaces are emitted as buffer-native JavaScript with
offsets and strides baked in; scenario code, which runs once per run or
optimization trial, is evaluated by an HIR interpreter instead: no emitted
JavaScript and no `new Function`.

The editor's type checking is the same pipeline seen from the other end: the LSP
generates the `Color_*`, `Parameters`, `Dynamics` and kernel declarations Monaco
checks against, so editor diagnostics and runtime artifacts come from the same
HIR checks and emitters.

## What compiles where

| Surface           | Authored as                                  | Executed in                                                           |
| ----------------- | -------------------------------------------- | --------------------------------------------------------------------- |
| Transition lambda | module, `Lambda(fn)`                         | Worker, per enablement check                                          |
| Transition kernel | module, `TransitionKernel(fn)`               | Worker, per firing                                                    |
| Dynamics          | module, `Dynamics(fn)`                       | Worker, per step per place                                            |
| Metric            | plain function body                          | Main thread (timeline) and MC worker (experiments)                    |
| Scenario          | per-place expressions, or one code-mode body | HIR interpreter: main thread before a run, CLI per optimization trial |
| Place visualizer  | module, `Visualization(fn)` returning JSX    | Main thread, at render                                                |

The visualizer is the one inherently React-based surface — it authors JSX — which
is why it compiles in the UI package rather than in the headless core.

Metrics must return a finite number; NaN and infinity throw rather than
propagating into a chart.

## Scenarios produce a marking, not a run

Scenario compilation produces an initial marking (plus parameter overrides)
before the simulation is created, in two halves. Lowering to HIR needs the
TypeScript compiler, so it runs where the compiler lives: the LSP worker in
the browser (`requestScenarioHir`), or inline in Node
(`lowerScenarioToHir`). `compileScenario` takes the lowered result,
type-checks it against the net's parameters and places, and evaluates it with
the interpreter (`hir/interpret.ts`). One lowering serves many evaluations:
optimization trials and parameter tweaks re-run only the type check and the
interpreter, never the TypeScript frontend.

Two modes, with one asymmetry worth remembering: **per-place mode is keyed by
place ID, code mode is keyed by place name.** In code mode, unknown names are
silently dropped at evaluation, and the type checker reports them
(`hir:unknown-scenario-place`).

In per-place mode an uncoloured place takes an expression evaluated with
parameters in scope, rounded and clamped at zero; a coloured place takes row
arrays in colour-element order, each coerced with typed defaults for missing
columns. Extra columns and invalid typed values are reported as compilation
errors.

## What the sandbox is for

The place visualizer is the one surface still executed as raw JavaScript
(`compile-visualizer.ts` in the UI package; it authors JSX, which the HIR
does not represent). Its Babel-compiled module body runs in strict mode with
a list of globals shadowed (`window`, `document`, `globalThis`, `fetch`,
`importScripts`, `Function`, timers and similar), so those name lookups
resolve to `undefined`. Because shadowing only stops identifier lookup, the
sandbox additionally blocks the constructor-chain escape
(`({}).constructor.constructor` reaching `Function`) around the module
evaluation and each render, by swapping the `.constructor` descriptors on the
built-in prototypes and restoring them afterwards.

**Treat this as robustness hardening, not isolation.** Visualizer code
executes with `new Function` in the same realm as the host. It protects
against typos and accidental API use, not against an attacker. Every other
surface, scenario code included, compiles through the HIR, where
out-of-subset code is a blocking diagnostic rather than a sandbox concern.

Identity strings (ids, parameter variable names, element names) are the other
untrusted input: [Untrusted names](doc:simulation/untrusted-names) covers how
they are rejected at the import and simulation boundaries and why records
keyed by them have no prototype.

## Distributions are sampled once

Kernels can construct distribution values rather than numbers. They defer
sampling through the ABI sink, and the engine samples each value once per token
with the seeded RNG. That is what lets chained `.map(fn)` transforms share a
single draw and keeps runs reproducible.

When stochasticity is disabled the runtime is not injected at all, and plain
values are required.

## Compatibility

HIR artifacts carry a version and a fingerprint of their sanitized compilation
input. Any schema, code, or extension change requires recompilation before the
engine will run them — a stale artifact is refused rather than silently
mismatched against a changed net.
