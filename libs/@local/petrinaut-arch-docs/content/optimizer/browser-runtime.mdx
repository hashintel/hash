Terms on this page: a **study** is one capability run, identified by its
`runId`; a **step** in the UI is a **trial** in Optuna and in the contract; a
**replicate** is one seeded simulation run of a trial; a **segment** is the
trials between a run start or extension and a terminal event. A study
evaluated in the tab is **connected**; one run by the optimizer service is
**remote**.

An optimization needs an Optuna study that suggests parameter values and a
simulator that scores them. The browser has both: Optuna runs under Pyodide,
and the editor's experiments backend simulates. This layer is the adapter
between them. `createBrowserOptimization()` returns a
`PetrinautConnectedOptimization`, a source the
[optimizations provider](layer:react.optimizations) `connect`s with a channel
to obtain a `PetrinautConnectedOptimizationCapability`: the
`PetrinautOptimization` a remote service offers, plus `extendOptimizationRun`
and `releaseOptimizationRun` for the study the worker keeps between segments.
The drawers and the event schema ([the contract](layer:core.optimization)) are
the same for both variants.

The provider reaches the source through `useOptimizationSource()`, which
returns a connected source only while the experimental **In-browser
optimization** user setting is on. Off, the hook returns `null`: the
Optimizations tab hides, and the provider disposes the connection, which
cancels every run made through it. A remote capability passes through the hook
unchanged.

## The data flow

1. **Drawer → provider.** The create drawer builds an optimization manifest
   (model snapshot, scenario, objective metric, parameter domains, study
   settings including `seedsPerTrial`) and the provider calls
   `createOptimizationRun(manifest, { parallelism })` on the connected
   capability. `parallelism` comes from the create form's **Parallel steps**
   field: 1 by default, at most `PETRINAUT_OPTIMIZATION_MAX_PARALLELISM`, and
   fixed for the study's life. The requested compute backend travels beside
   the manifest, on the record.
2. **Capability → worker.** The capability parses the manifest
   (`parseOptimizationManifest`), describes the study with the
   `describeOptimization` the CLI uses, derives the trial seeds once
   (`deriveOptimizationTrialSeeds(seed, seedsPerTrial)`; every trial runs
   the same seeds, as common random numbers), allocates a run id, appends
   `started { requestedTrials }` to the run's event log and queues
   `start { runId, description, parallelism }` for a shared module worker.
   Runs execute one at a time: a run created while another runs waits in the
   capability's queue.
3. **Worker → Optuna.** On first use the worker loads Pyodide from
   `pyodide.indexURL` (jsDelivr, at the version pinned in
   `runtime-lock.json`), installs the pinned packages with micropip, writes
   the [optimizer-core](layer:optimizer-core) sources into Pyodide's
   filesystem and imports `pyodide_entry`.
   `create_browser_study(description, parallelism)` builds the study once per
   run (the constant-liar TPE sampler when `parallelism` is above 1) and keeps
   it in a handle;
   `run_browser_study(handle, trials, evaluate, on_trial, is_cancelled)` runs
   one segment on that handle, asking the sampler for values and awaiting the
   `evaluate` callback for each trial, with up to the handle's `parallelism`
   trials in flight; `release_browser_study(handle)` drops the study.
4. **Worker → channel.** Each `evaluate` crosses to the main thread as
   `evaluate { runId, requestId, trial, suggestedValues }`; the worker numbers
   the trial from its count of evaluate calls for the study. The capability
   resolves the trial's scenario parameter values
   (`resolveTrialScenarioParameterValues`) and calls `channel.evaluateTrial`
   with the run's seeds and the segment's abort signal.
5. **Channel → experiments.** The [channel](layer:react.optimizations.channel)
   turns the trial into one detached objective run: `runDetachedObjective` on
   the [experiments provider](layer:react.experiments), with `cacheKey` set to
   the run id, so the study compiles its snapshot once, and `queueKey` set to
   `${runId}:trial:${n}`, so the trials in flight overlap. The request carries
   the trial's values, `runCount = seeds.length`, the seeds pinned per run
   (`runSeeds`) and the study's requested backend. The first run of a study on
   a backend walks the registrations (`selectExperimentBackend`, GPU first,
   the CPU pool last, at a third of the pool's shards so the user's own
   experiments keep workers) and keeps the winner for the study's later runs.
   Pinned seeds go to the CPU pool only; the GPU backend derives run seeds
   from the base seed. The channel calls the study's `trialStarted` when the
   run begins and `trialSettled` when it settles, so the
   [connected study](doc:optimizer/connected-study) can follow it. The trial's
   objective is the mean of the per-run finals the CPU reports (`runResults`)
   or, where the backend reports no run axis, the objective metric's last
   sampled frame reduced to a mean. Optuna is told that mean; the replicates
   stop at the channel. A batch that does not complete settles with a reason
   (the metric's compile diagnostics, each backend's refusal, the terminal
   error, or the count of errored runs), and the channel prunes the trial with
   that reason; a cancelled batch is pruned as `cancelled`, and a non-finite
   objective names the metric. Every failure reaches Optuna as a pruned trial
   carrying the reason.
6. **Events → drawer.** Each told trial produces a `trial { runId, event }`
   message carrying the running best, which the capability appends to the run
   log as a `trial` event; the segment's summary produces `complete`. The
   provider consumes the log through `attachOptimizationRun`, which replays it
   from a cursor and then tails it, so a re-attach delivers each event once.
   The record's `connected` field carries the local side: where the drawer
   points and the objective's live stream there
   ([connected study](doc:optimizer/connected-study)).

## Stop, Continue and Remove

A run's log is a sequence of segments, each begun by `started` (carrying the
cumulative `requestedTrials`) and ended by a terminal event. The capability
tracks each run as `queued` (waiting for the worker), `running` (its segment
posted), `finished-resumable` (the segment ended, the study kept in the
worker) or `finished` (no study to return to).

**Stop** calls `cancelOptimizationRun`: the capability aborts the segment's
signal, so the channel cancels the trial's runs, and posts `cancel { runId }`.
The worker resolves the segment's pending evaluations as pruned, so the Python
loop's awaits settle; the loop reads `is_cancelled()` at its next poll, tells
every trial asked and not yet told as failed **without reporting it**, so a
stopped step appears in no event, table or count, and returns its summary
with `cancelled` set. The worker posts `cancelled { runId }`, and the
capability appends the cancelled error event (`optimization_cancelled`) and
marks the run `finished-resumable`. The study stays in the worker. Every
terminal event carries `resumable`: `true` when the study stays in the worker,
`false` when the run failed or its first segment never reached the worker,
as when a study is stopped while the runtime still loads or another study
holds the worker. The host offers Continue from that flag alone.

**Continue** calls `extendOptimizationRun(runId, trials)`. The capability
computes the new total from the trials the log holds (`requestedTotal`),
checks it against `PETRINAUT_OPTIMIZATION_MAX_TRIALS`, appends `started` with
that total and queues `extend { runId, trials }`; the segment inherits the
run's parallelism, and the trials continue Optuna's numbering. The provider
then re-runs its attach loop from the record's `lastSeq`.

**Remove** calls `releaseOptimizationRun(runId)`, which cancels a running
segment and posts `release { runId }`; the worker drops the study after the
segments queued before it, and posts nothing back. `dispose()` cancels every
run, drops every study and terminates the worker.

## What each side owns

- **Python ([optimizer-core](layer:optimizer-core))** owns the study: sampler,
  suggestion, ask/tell, trial state and the best-so-far. It sees flat
  descriptors and scalar objectives, and it checks its own trial cap
  (`handle.requested` against `MAX_STUDY_TRIALS`).
- **The worker** owns Pyodide (loading, package installation, marshalling
  proxies to plain objects) and pairs each `evaluate` request with its reply
  by request id. It owns trial numbering: Optuna numbers trials densely in ask
  order and every ask leads to one evaluate call, so the count of evaluate
  calls made for a study is the next trial's number, across segments and
  across trials a stop left untold.
- **The capability** owns run identity, the queue, the event log (dense
  sequence numbers, replay from a cursor, terminal `complete`/`error`) and
  `requestedTrials`, which it computes and appends in `started`. It maps the
  channel promise onto the run: a rejection fails the run with
  `trial_evaluation_failed`; an evaluation of a cancelled segment gets no
  reply from the capability, since the worker answered it as pruned. A worker
  that fails to load, or crashes after `ready`, fails the active run with the
  retryable `optimizer_unavailable`, and the next queued run starts a fresh
  worker; an error raised by the Python study fails the run with
  `study_failed`.
- **The channel** owns the mapping between a trial and a detached run: the
  request, the outcome, and the `trialStarted`/`trialSettled` callbacks.
- **The experiments provider** owns simulation: compilation cached per
  `cacheKey`, the backend choice per study, seeding, frames and progress
  streamed on a 100 ms throttle, and the per-`queueKey` queue.
- **The connected study** owns the drawer's local state: navigation,
  following, the refinement ladder at the navigated point and the activity
  list ([connected study](doc:optimizer/connected-study)); the
  [Optimizations tab](doc:ui/optimizations-tab) renders it.

## Parity with the service

Both drivers derive per-trial seeds with `deriveOptimizationTrialSeeds`, and
the sampler runs the same Optuna version with the same seed and the same
number of start-up trials: `create_study` in
[optimizer-core](layer:optimizer-core) sets the TPE sampler's
`n_startup_trials` to `tpe_startup_trials(trials)`, a third of the requested
trials, at least 2 and at most Optuna's default of 10. On the CPU pool the
request pins every run's seed (`runs: [{ seed }]`), so a trial's replicates
run on the seeds the CLI runs and the trial reports the service's objective
value. After its start-up trials the TPE sampler conditions each proposal on
the objectives it was told, so with **Parallel steps** at 1 the study proposes
the same parameter values step for step while the objective values match;
above 1 the constant-liar sampler also counts the trials in flight, and the
proposals differ from a sequential study's. Every connected study runs on the
CPU: the objective is an expression metric, which the GPU backend cannot
compute, so `useGpuAvailability` reports it unavailable and the **Backend**
switch stays disabled. `test_runtime_lock.py` in optimizer-core fails when the
Optuna pin in `runtime-lock.json` differs from the version the package's own
lockfile installs; the service resolves the same version range
(`optuna>=4.9,<5`) in its own lockfile. The study lives in the tab: closing
the page ends it, and because a connected run is kept in memory only, the next
load shows no record for it.
