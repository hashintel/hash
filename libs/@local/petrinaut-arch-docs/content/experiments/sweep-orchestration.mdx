A sweep experiment has one orchestrator, the sweep session, and one React
provider that owns it. The session holds no React; it turns selection changes
into batches and folds their frames into a per-selection cache. The provider
turns the session's publishes into experiment records and decides which
compute backend each batch runs on.

![One selection change, one optimizer trial, and the batch list](@diagrams/sweep-orchestration.svg)

## The selection path

A slider commit or a surface drag calls `setSweepSelection` through the
actions context. The session normalizes the selection, aborts the ladder that
was computing, and starts the refine ladder for the new selection: batches of
8, 25, 100, 500 and 1,000 runs, each covering the run range the previous
rungs left. Rungs are pipelined: as soon as a rung streams its first frames
the next rung starts, so at most two rungs are live, and folds into the cache
stay in rung order. Run ranges are disjoint and per-run draws and seeds are
prefix-stable, which is what makes overlapping rungs sound.

Each rung asks the provider to instantiate a batch. The provider builds an
`ExperimentRequest` (per-run parameter draws travel as a typed-array plan
over the net parameters the sweep's axes can reach — a point selection as a
constant plan, so every batch lays out the same per-run buffer and the GPU
backend keeps one compiled setup across selections) and lets the backend
selection choose between the CPU worker pool and the WebGPU backend the first
time; later rungs reuse the chosen backend.

Frames come back through the experiment handle's stores. The session merges
the selection's cached frames with the live rungs' frames and publishes on a
leading-edge 100 ms throttle: the first frames publish immediately, and while
a batch streams the record updates about ten times a second. The provider
writes each publish into the record, which the drawer and its charts read
from the experiments context.

## The optimizer path

A study starts during creation when **Start optimizer immediately** is
checked (`useCreateOptimizedExperiment`: create → start → select), or later
through **Parameters → Optimize** (`useSweepOptimizer.start`). Both paths
call `useStartSweepStudy` with the experiment's model snapshot, metric and
execution settings. The study runs its trials through the sweep. The first trial relies on one contract of
`createExperiment`: the sweep branch of the experiment's initialization
awaits nothing before `startSweepSession`, so the session is registered by
the time the promise resolves and the study's first `navigateSweep` finds it;
the provider's test pins that no await is ever inserted before it. If immediate startup rejects, creation removes the experiment before selecting
it. If a later start rejects, the existing experiment and study remain.
Its trials go through `navigateSweep(experimentId, point, { runCap })`: the
session adopts the point as its selection with a run cap, restarts its ladder
there, and resolves the call once the point has folded that many runs (or is
cached that deep already) with the point's per-metric values. It resolves
null when another navigation superseded it or the sweep was disposed, and
rejects with the batch's reason when a batch of the point fails or the sweep
is gone; the evaluator lets that rejection fail the study. The cap keeps the ladder from pipelining a rung the next trial would abort; a
plain `setSweepSelection` lifts it, so a point the user returns to refines to
the run budget. The optimizations provider owns the evaluator that calls
this ([react.optimizations.sweep-evaluator](layer:react.optimizations.sweep-evaluator));
the experiments layer never learns who asked. A fresh sweep computes nothing
until something selects (`startComputing: false`).

## The batch path

Every publish of the session lists the rungs computing right now in its
`batches` — oldest first, each with its id, its run count and its completed
runs read from the rung's handle — and the provider stores that list as
`record.sweepBatches`, which the activity list and the top-bar popover read.
A session that stopped computing publishes an empty list. Both show the same progress rule: for a sweep, the selected combination's
sampled runs over the run budget; otherwise simulated time over the
experiment's max time.

## Constraints through the sweep

An experiment's constraints are lowered to HIR in the Create Experiment
drawer (`create-experiment-drawer/constraints/`: the drafts and their
transitions in `constraint-drafts.ts`, one LSP session per row in
`use-constraint-lsp-session.ts`, the lowering and the GPU gate specs in
`lower-constraint-drafts.ts`, the section in `constraints-section.tsx`) and
stored on the record with the pass threshold as `constraintPolicy` and the
scenario's parsed values as `scenarioParameterValues`. They are enforced in
two places, both outside the study's own code:

- A **parameter constraint** is judged by the sweep evaluator at the snapped
  grid point, before `navigateSweep` is called
  (`shared/parameter-constraints.ts` interprets the HIR with the net
  defaults as `parameters` and the snapped values as `scenario`). An
  infeasible draw is pruned as `Infeasible: <name>`, carries
  `{ parameters, state: [], infeasible }`, and moves nothing: the sweep's
  selection stays where it was.
- A **state constraint** rides every request the experiments provider
  builds for the sweep, from creation on, as one precompiled indicator
  metric (`react/experiments/constraint-indicators.ts`): the body wrapped
  as `cond ? 1 : 0`, `aggregateTime: "min"` over each run's frames and
  `sampleRuns: "notErrored"`, under the id `constraint:<id>`. Those ids
  never reach `record.metricSpecs`, so no tile, picker or surface option
  shows them. A visited cell's mean of the indicator is `passed / total`
  over the runs that did not error, and `sweepCellPassCount` turns it back
  into the count the evaluator reports as `constraints.state`. Because
  `toGpuMetricSpecs` refuses a time aggregation, a sweep with state
  constraints runs on the CPU; the drawer's GPU gate carries a placeholder
  `min` spec per drafted state row so the switch says so before creation.

Downstream, `constraint-rates.ts` turns `trial.constraints` into the rates
the Constraints card, the steps table and the objective strip's greyed
infeasible steps read. A trial pruned as cancelled or "the sweep moved on"
carries no `constraints` and counts in no rate.

## The study in the experiment drawer

`experimentResultsModel` (`experiments/experiment-results.tsx`) builds the
shared `ResultsModel` the [results view](layer:ui.views.editor.results)
renders. `useSweepOptimizer` finds the current study by
`OptimizationRecord.origin.experimentId`. Once a study exists, the results
show optimization progress, an objective strip, constraint and sensitivity
cards, and a steps table. Configuration and the search summary live in
Details. These displays stay available after the study completes, stops or
fails.

The Parameters header offers **Optimize** for an eligible sweep with metrics
and a connected source. Its popover selects the metric, direction and step
budget, using the same validation as creation. An active study replaces that
action with **Stop** and locks the sliders and Surface. Assistant-owned
requests and cancelled experiments also lock the controls. A successful new
start removes the settled study after the provider registers its replacement;
a rejected start keeps the previous study. The experiment keeps its sampled
points across searches.

The Parameters footer lists the record's constraints through
`experiment-results/constraints-fold.tsx`. Constraints are recorded at
creation and apply to later optimizer starts too. The results-model and
panel tests cover controls and layout before, during and after a study; hook
tests cover start eligibility and replacement after successful registration.

## Where the pieces live

- The session's private pieces (selection keys and range draws) sit next to
  `sweep-session.ts` in
  [react.experiments.sweep](layer:react.experiments.sweep); the throttle and
  the batch registry are `react/experiments/shared` helpers.
- The provider's batch instantiator, experiment creation and record patching
  sit under `provider/`.
- Backends and the run plan contract are in
  [core.experiments](layer:core.experiments); the pooled worker factory in
  [core.simulation.monte-carlo.runtime](layer:core.simulation.monte-carlo.runtime).
- The surface's field and the shared surface shell are described in
  [The sweep surface](doc:experiments/sweep-surface).
