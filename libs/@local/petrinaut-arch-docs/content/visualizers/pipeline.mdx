A place visualizer is the one piece of user code Petrinaut compiles on the
main thread with Babel and executes as raw JavaScript, with no type checking,
no completion and no diagnostics. This page proposes moving it onto the path
every other surface already uses: type-checked and compiled in the language
worker, evaluated as a pure function off the main thread, written into the DOM
by a small patch applier, and defined on nets as well as on places. Each
section states the current behaviour, the options measured, and the
recommendation. The measurements come from the scripts under
`spikes/visualizers/` in this package, run on Chromium 153 and WebKit through
Playwright on an Apple Silicon Mac.

## Today

|             | Place visualizer                                                                | Every other surface                                                  |
| ----------- | ------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| Authored as | module `export default Visualization(fn)`, `fn` returns JSX                     | bare function body, or the legacy `export default <Ctor>(fn)` module |
| Checked by  | nothing: the editor colours syntax, the language worker has no file for it      | TypeScript 6 language service in the language worker, then HIR lints |
| Compiled by | `@babel/standalone` (3.1 MB) on the main thread, `ui/lib/compile-visualizer.ts` | `lowerTypeScriptToHir` in the language worker                        |
| Executed as | `new Function` in the host realm, inside `runSandboxed`                         | buffer programs in the simulation worker, or the HIR interpreter     |
| Defined on  | `Place.visualizerCode`                                                          |                                                                      |

Three surfaces render it, each calling the compiled function on every frame on
the UI thread: the Visualizer section of the Properties panel, the hover and
pin box on the canvas (`place-state-tooltip.tsx`), and the notebook cell.
`PlaceStateVisualization` opts out of the React Compiler (`"use no memo"`)
because its component is made at run time, and `compileVisualizer` keeps the
24 most recent compiled sources. The sandbox around evaluation is hardening
rather than isolation; [Compiling user code](doc:simulation/user-code) sets
out what it does and does not stop.

The increments at the end of this page land this one step at a time; the first

## Type checking and completion

The language worker holds one `ts.LanguageService` over a virtual file system
(`create-language-service-host.ts`): `lib.es5`, three `lib.es2015` files, and
the files `generateVirtualFiles` derives from the net. Visualizers need a
different program: JSX, React's element and attribute types, and the DOM
attribute names those types reference.

**Recommendation: a second service in the same worker.** The compiler options
differ (`jsx`, `jsxImportSource`), the lib set differs, and keeping the two
programs apart means an edit to a visualizer never re-checks the net's
transitions, nor the other way round. The same worker keeps the 9.1 MB
TypeScript bundle downloaded once, and the transport and diagnostics push
unchanged. `SDCPNLanguageServer` gets a sibling class over the same host
factory; the worker routes a file path by prefix.

The service's inputs, as measured by `spikes/visualizers/scripts/s1-jsx-service.mjs`:

- `@types/react`'s `index.d.ts` (178 KB), `global.d.ts` (7.5 KB) and
  `jsx-runtime.d.ts` (1.2 KB), served under a virtual package named by
  `jsxImportSource`. `global.d.ts` declares empty `HTMLElement`,
  `SVGSVGElement`, `Event` and the rest, so `lib.dom` (2.35 MB) is not
  needed. Without it, `window`, `document`, `fetch` and `setTimeout` are
  unknown names, which is the first purity rule for free.
- `csstype` (895 KB), which `index.d.ts` imports for `CSSProperties`. A stub
  declaring `Properties` as a string record drops it at the cost of CSS
  property completion in `style` objects.
- Per visualizer, a generated `visualizer-defs.ts` declaring
  `VisualizerProps` from the place's `Color_<id>` type and `Parameters`, and
  `Visualization`. Both types exist already.
- Compiler options: `jsx: react-jsx`, `moduleResolution: bundler`,
  `strict`, `types: []`.

| Step, 2.2 KB visualizer                | Without `lib.dom` | With `lib.dom` |
| -------------------------------------- | ----------------: | -------------: |
| First diagnostics (parses every lib)   |            186 ms |         291 ms |
| Diagnostics after an edit              |        28 – 43 ms |     40 – 43 ms |
| Completions at an attribute, 487 items |             16 ms |          15 ms |

The checks hold up: a misspelt `strokeWidht` is TS2322 against the
`SVGProps` type, `t.z` on a token is TS2339 against `Color_<id>`, and the
shipped satellites example reports its own three attribute mismatches against
the mock types the spike generates.

Wiring in the editor is the existing pattern. `ItemType` gains
`place-visualizer`; `document-uris.ts` maps
`inmemory://sdcpn/places/<id>/visualizer.tsx` (the URI the section already
gives Monaco) to `/places/<id>/visualizer/code.tsx`; `checkSDCPN` runs the
visualizer file of every place that has one when the colours extension is on;
the Diagnostics tab groups the result under the place through
`parseDocumentUri`. One decision to make explicit: `errorDiagnosticsCount`
gates simulation today, and a broken picture must not stop a run, so
visualizer errors are counted apart from the net's.

## Keeping a visualizer a pure function

A visualizer is pure when its output depends on `tokens` and `parameters`
only: no hooks, no state, no effects, no host access, no mutation of anything
outside the function. Three layers enforce that, each cheaper than the next
and each catching what the previous one lets through.

1. **The type environment.** No `lib.dom` makes host globals unknown names.
   Naming the JSX package after `jsxImportSource` rather than `react` makes
   `import { useState } from "react"` an unresolved module (TS2307). Dropping
   the `export as namespace React` line when the types are copied in makes
   `React.useState` an unknown name too; with the line kept it is TS2686
   ("UMD global in a module"), which also fails.
2. **An AST lint in the worker**, the `check-hir.ts` pattern over the parse
   tree the service already holds, reported through the same diagnostic codes
   table:

   | Rule                                                                    | Severity |
   | ----------------------------------------------------------------------- | -------- |
   | Any `import`, or an export other than the one `export default`          | error    |
   | A call whose callee matches `/^use[A-Z]/` (hooks)                       | error    |
   | `class`, `this`, `new`, `async`, `await`, `yield`, generators           | error    |
   | `let`, `var`, or assignment to a binding declared outside the component | error    |
   | JSX attributes `on*`, `ref`, `dangerouslySetInnerHTML`                  | error    |
   | `.map` returning JSX without `key`                                      | warning  |
   | `Math.random`, `Date.now`: output no longer a function of the frame     | warning  |

3. **Lowering to the view HIR** (increment 6). The HIR has no node for a hook
   call, an import or an assignment, so whatever the lint missed is an
   `hir:unsupported-syntax` diagnostic with a span, as for scenario code
   today. Once it lands, layer 2 keeps only the rules that deserve a better
   message than "unsupported".

ESLint can run in a browser (its `Linter` class does no file system work) and
`eslint-plugin-react-hooks` carries the React Compiler's rules, but
type-aware rules need `@typescript-eslint/parser` and a second TypeScript
program per lint, and the bundles are megabytes. The seven rules above are a
few dozen lines over `ts.forEachChild`. Not worth a second linter.

## Compiling

Timings for the 2.2 KB satellites visualizer
(`spikes/visualizers/scripts/s2-transpile-bench.mjs`):

| Transform                          |  Cold |   Warm | Bytes it adds to the editor               |
| ---------------------------------- | ----: | -----: | ----------------------------------------- |
| `ts.transpileModule`, TypeScript 6 | 26 ms | 1.8 ms | none, TypeScript is already in the worker |
| `@babel/standalone` (today)        | 23 ms | 3.4 ms | 3.1 MB, on the main thread                |
| `sucrase`                          |  6 ms | 0.5 ms | 1.5 MB                                    |

**First step: transpile in the language worker** with `ts.transpileModule`
(`jsx: react`, a Petrinaut-owned factory name) and remove `@babel/standalone`
from `@hashintel/petrinaut`'s dependencies. The compiled text joins the other
artifacts the worker already returns from `sdcpn/compileHirArtifacts`, so the
UI never holds a compiler and the host never ships Babel.

**Second step: lower to a view HIR.** The HIR is an expression tree with
`let`, `cond`, `arrayMap`, `arrayReduce`, `recordLit`, `mathCall`,
`paramRef` and `fieldAccess` nodes. An inventory of the 30 `visualizerCode`
strings in the shipped examples (13 with real code,
`spikes/visualizers/scripts/s3-syntax-inventory.mjs`) finds only these
constructs outside it:

| Construct                                  | Example visualizers using it | HIR addition                                       |
| ------------------------------------------ | ---------------------------: | -------------------------------------------------- |
| JSX elements, attributes, children, `key`  |                     13 of 13 | `jsxElement`, children as `arrayLit`               |
| Template literals and string concatenation |                     12 of 13 | `templateLit`                                      |
| `.slice`                                   |                     11 of 13 | `arraySlice`                                       |
| `.toFixed`                                 |                      3 of 13 | `numberFormat`                                     |
| `.filter`                                  |                      1 of 13 | `arrayFilter`                                      |
| `&&` and ternaries selecting JSX or `null` |                     10 of 13 | widen `cond` and `binary` typing to element values |

None uses a loop, an `if` statement, a class, an import, `new`, or a helper
function beyond the component arrow and its `.map` and `.filter` callbacks.
The lowering gives purity by construction, a JSON artifact the UI can hold
without source text, an interpreter that runs anywhere, and later a second
backend (canvas) from the same tree.

## Running off the main thread

| Option                                                                          | What it isolates                                                                                          | Measured                                                                                                                                                                                                                                                                                   | Verdict                                     |
| ------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------- |
| Main thread, `new Function` (today)                                             | Nothing                                                                                                   | Every frame re-runs user code on the UI thread                                                                                                                                                                                                                                             | Replace                                     |
| Web Worker, tree posted to the main thread                                      | The UI thread. Not a security boundary: same origin, `fetch`, IndexedDB, `BroadcastChannel` all available | Object tree of 1k / 5k / 20k nodes: 0.6 / 3.0 / 12.2 ms per frame to arrive, and the receiver pays the same again to deserialize; typed-array columns or patches, transferred: under 0.1 ms                                                                                                | Use, with columns and patches               |
| Sandboxed iframe, `sandbox="allow-scripts"`, `srcdoc`, CSP `default-src 'none'` | Origin: storage, cookies, parent DOM and network all blocked (probed). | Shadow DOM                                                                      | Styles and DOM identity                                                                                   |                                                                                                                                                                                                                                                                                            | Use for the host element either way         |
| ShadowRealm                                                                     | The realm                                                                                                 | TC39 stage 2.7, not shipped                                                                                                                                                                                                                                                                | Not available                               |
| SES / Hardened JavaScript                                                       | The realm, by freezing every intrinsic on the page                                                        |                                                                                                                                                                                                                                                                                            | Unacceptable in a library embedded in hosts |

Chromium has isolated opaque-origin sandboxed iframes by default since M132,
per Microsoft's WebView2 notice of the same Chromium change. Firefox was not
measured; Playwright's Firefox build did not launch on this machine.

**Recommendation: evaluate in a worker, patch on the main thread.**

- The visualizer worker evaluates `fn(tokens, parameters)` for every open
  visualizer when a frame arrives. The simulation worker can host it, since
  it already holds the frame; a dedicated worker fed by the frame source
  covers Actual mode and playback of stored frames. Before the view HIR, the
  transpiled module runs there under `new Function` with a `createElement`
  shim that returns plain `{ tag, props, key, children }` records; the worker
  keeps `SHADOWED_GLOBALS` and `runSandboxed` as today. After it, the
  interpreter builds the same records and `new Function` leaves the package.
- The worker diffs the tree against the previous frame's, keyed by `key` and
  index, and emits create, remove, attribute, text and move patches as
  typed-array columns plus a string table interned once per visualizer.
- A 100-line applier on the main thread writes the patches into a Shadow DOM
  host with `contain: strict`: `createElementNS`, `setAttribute`,
  `textContent`. No React work per frame. The "vanilla applier" row in the
  next section is this loop: 0.6 / 2.3 / 10.2 ms at 1k / 5k / 20k tokens
  when every token moves, 0.1 / 0.6 / 2.6 ms when a tenth of them do.
- Patches carry no functions, so a visualizer has no event handlers. See
  open questions.
- While arbitrary JavaScript is still accepted (before increment 6) the
  worker is a robustness boundary like today's sandbox, with the DOM out of
  reach. If a hard boundary is needed before then, the sandboxed iframe is
  the only one the platform offers for arbitrary code, at one document per
  box (React and ReactDOM 190 KB minified inside it, or Preact at 11 KB)
  and with the UI thread protected on Chromium only.

## Lists and many tokens

`spikes/visualizers/bench/` renders N tokens as SVG circles and feeds each
variant a fresh array of fresh token objects per frame, as a frame reader
does, moving every token or a tenth of them. Script is the synchronous
render-and-commit time; frame is the interval between animation frames and so
includes style, layout and paint. Medians over 40 frames, Chromium 153.

| Variant                         | 1k all | 1k 10% | 5k all | 5k 10% | 20k all | 20k 10% | 20k frame |
| ------------------------------- | -----: | -----: | -----: | -----: | ------: | ------: | --------: |
| Vanilla patch applier           |    0.6 |    0.1 |    2.3 |    0.6 |    10.2 |     2.6 |     33 ms |
| React 19, one keyed component   |    0.7 |    0.3 |    3.4 |    1.1 |    11.5 |     4.0 |     33 ms |
| Same, React Compiler            |    0.7 |    0.3 |    2.7 |    1.1 |    10.7 |     4.1 |     33 ms |
| React 19, a component per token |    0.9 |    0.5 |    3.2 |    1.8 |    13.5 |     6.3 |     33 ms |
| Same, `memo`                    |    0.9 |    0.4 |    3.4 |    1.2 |    14.1 |     4.3 |     33 ms |
| Same, React Compiler            |    1.0 |    0.4 |    3.3 |    1.4 |    13.7 |     5.1 |     33 ms |
| Preact 11                       |    1.0 |    0.4 |    4.2 |    1.5 |    17.9 |     5.6 |     50 ms |
| Solid `<Index>`                 |    0.8 |    0.7 |    7.2 |    4.2 |    46.2 |    24.0 |     67 ms |
| Solid store with `reconcile`    |    1.8 |    1.0 |   14.4 |    4.6 |    80.8 |    20.4 |    100 ms |
| Svelte 5 keyed `each`           |    1.1 |    1.1 |   13.1 |    9.6 |    92.6 |    69.5 |    117 ms |

Four readings:

- **Paint is the ceiling.** At 20k SVG elements every variant's frame takes
  at least two vsyncs, with script at 10 ms. The DOM holds 60 fps up to
  roughly 5k elements per picture; above that a canvas is the only option
  (the renderer spike for the main canvas held its frame cap at 10k nodes
  with instanced meshes).
- **Fine-grained libraries lose when the data is rebuilt every frame.** Each
  item signal fires because the object identity changed, and per-item
  effects cost more than one tight diff loop. The applier and React's keyed
  reconciliation cost about the same.
- **The React Compiler does not help this shape.** Its cache keys on
  `tokens`, which is a new array every frame, so the single-component form
  gains nothing; a component per token gains 1 – 2 ms at 20k, less than
  `memo`. It does run in the browser (`@babel/standalone` plus a 3.7 MB
  plugin, 11 – 16 ms per compile; the `Visualization(() => …)` arrow needs
  `compilationMode: "all"` or a named component). The oxc port
  (`oxc-transform-react`) ships native bindings only. Not recommended.
- **Change detection before rendering is the lever.** Frames are packed
  buffers, so the worker can compare each token's bytes with the previous
  frame and skip the unchanged ones; the 10% columns show what that buys.
  The view HIR makes it systematic: a `map` whose body reads only token
  fields is memoizable per token by value rather than by identity, and a
  subtree that reads no token at all is hoisted once.

## Visualizers for nets and subnets

`Place.visualizerCode` is the only visualizer today. The proposal adds
`SDCPN.visualizerCode` for the root net and `Subnet.visualizerCode` for a
subnet's definition. A component instance carries no code of its own: it
renders its subnet's visualizer with its own tokens.

- **Props.** `{ places, parameters, time }`, where `places` is keyed by place
  name and typed per place (`Color_<id>[]`), the shape kernels already get as
  `input`, and `parameters` holds the net's values, or the instance's resolved
  values for a subnet rendered through an instance. The generated
  `NetVisualizerProps` comes from the same virtual-file generator as
  `Parameters`.
- **Per instance.** The engine flattens instances with scoped ids
  (`instance::place`, `flatten-component-instances.ts`), so the frame reader
  already addresses each instance's places. The visualizer worker maps the
  subnet's place ids to the scoped ids of the instance it is drawing; nested
  instances extend the path.
- **Where it shows.** The Properties panel with nothing selected becomes the
  active net's properties, root or subnet (`ActiveNetContext.activeSubnetId`),
  with the same Visualizer section places have. A component instance on the
  canvas gets the hover and pin box places have, drawing the subnet's picture
  for that instance. The root net's picture gets a subview in the Simulate
  view.
- **Language worker.** `/visualizers/net/code.tsx` and
  `/subnets/<id>/visualizer/code.tsx`, URIs to match, diagnostics grouped
  under a "Net" entity.
- **Touchpoints.** `types/sdcpn.ts` and `sdcpn-input.ts`, the zod schema in
  `schemas/entity-schemas.ts`, `extensions.ts` (stripped when the colours
  extension is off, as for places), the AI mutation schemas in
  `action-schemas.ts`, the file-format version, the notebook's parameter
  edges in `notebook-model.ts`, and `docs/petri-net-extensions.md`.

## Increments

Each one ships on its own and leaves the previous behaviour for what it does
not cover.

1. **Language worker coverage.** Second service, virtual files, URI mapping,
   Diagnostics tab entries. Gate: the satellites example type-checks with no
   errors against its real types; a `fetch` call is an error; completions
   and hover work in the Visualizer section.
2. **Compile in the worker.** `ts.transpileModule` in the language worker,
   `@babel/standalone` removed. Gate: every example visualizer renders the
   same markup as before (snapshot), and the dependency is gone from the
   package.
3. **Purity lint.** The rules table above. Gate: each rule has a fixture
   with the expected code and span.
4. **Worker evaluation and patch applier.** Evaluation in a worker, column
   patches, Shadow DOM host; the three render surfaces mount the host. Gate:
   the benchmark's applier numbers reproduced inside the editor, and the
   canvas hover box opens without the main thread compiling anything.
5. **Net and subnet visualizers.** Data model, panel, instance box, worker
   files. Gate: one example with a root visualizer and a subnet visualizer
   drawn once per instance.
6. **View HIR.** Lowering, typing and interpreter; `new Function` removed
   from `@hashintel/petrinaut`. Gate: the 13 example visualizers lower;
   every out-of-subset construct is a positioned diagnostic.
7. **Canvas backend.** The same HIR drawn to an OffscreenCanvas in the
   worker for pictures above the DOM ceiling. Gate: 20k tokens at 60 fps.

## Open questions and scope

- Interactivity. Patches carry no functions, so `onClick` and friends are
  rejected by the lint. An action protocol (a visualizer declares actions the
  host dispatches) is the shape if it is wanted; not part of these
  increments.
- A visualizer with errors does not block simulation. The diagnostics count
  that gates a run excludes visualizer files.
- Firefox's process model for sandboxed iframes was not measured.
- Preview and embeds get the worker path for free; the iframe fallback would
  need its own entry point.
- AI-generated visualizers get the same loop as scenarios once the view HIR
  exists: generate, lower, return diagnostics.
