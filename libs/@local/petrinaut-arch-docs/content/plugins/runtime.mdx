The code is in `petrinaut/src/ui/plugins/`.

![How the editor runs plugins](@diagrams/plugin-runtime.svg)

## Hosts

`<Petrinaut>` mounts `PetrinautPluginsProvider` inside `<PetrinautProvider>`.
It renders one host per running plugin, beside the editor view. A host calls
its plugin's hook with `api`, and is keyed by the plugin editor and the
plugin's `hostKey`.

`PluginEditorProvider` builds one plugin editor per core instance. The
editor holds the access families, `errors` and `notifications`, built once
from that instance, so the family objects on `api` never change while a host
is mounted.

## Publishing contributions

After each commit, a host publishes its contributions, in a layout effect, to
a store the view's outlets read. The same contributions object publishes
nothing, and a host that unmounts withdraws them. A plugin switched on, off or
failing therefore never remounts the view. `usePluginService` reads the same store, so
a plugin's service is readable a layout pass after the plugin mounts, before
paint.

## Commands

A host also renders one `useCommand` registration per command its manifest
declares, into the ambient command registry, with the id
`pluginCommandId(manifest.id, key)`. The registration is replaced only when
the manifest's spec changes; `run` always calls the hook's latest handler,
and a `when` of `false` disposes the registration until it holds again.
Unmounting the host, as switching the plugin off does, disposes them all.

## First paint

`ViewAfterHosts` mounts the view in its first layout effect, which runs after
the hosts', so the view's first paint shows every contribution.

## Editor state the actions read

`PluginEditorSync` copies the editor state that actions read, such as the
read-only reason, the viewed subnet and the host's `setTitle`, into the plugin
editor's stores in the first layout effect of each commit. A host's layout
effect therefore already sees the read-only reason of the same commit. The
diagnostics snapshot is copied too; the language client makes a new one only
when a push changes it. The navigation state is copied the same way, but set
only when a field differs, so a controlled host's new state object on every
render wakes no subscriber.

## Remounts and re-runs

| Event                                                                  | What happens                                                                 |
| ---------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| The document changes                                                   | `<Petrinaut>` creates a new core instance, and the whole editor remounts.    |
| The host toggles `readonly`                                            | A new core instance and plugin editor: the hosts remount, the view does not. |
| A plugin is re-created by a new definition call, as hot reloading does | That plugin remounts. The same plugin object keeps its host.                 |
| A setting changes                                                      | The plugin's hook runs again, with a new `api`.                              |
| Another plugin switches on, off or fails                               | No other hook runs. Readers of the statuses re-render.                       |
| The host passes a new `plugins` array                                  | A plugin object it held before keeps its host, and its hook does not run.    |
| An edit, a mode switch, or a simulation                                | No hook runs. Plugins see the change through stores and actions.             |

## Statuses

Each plugin passed to the editor is `on`, `off` or `failed`. User settings →
Plugins lists them in the host's order, each with its switch, and marks a
failed one **Not running**. Opening a row shows the plugin's description and
what its manifest declares.

Switching a plugin off unmounts its host; its contributions and settings rows
go. A plugin whose manifest sets `required: true` has no switch, for controls
the host depends on. A hook that throws still marks it failed, and with no
switch it stays failed until it is re-created or another document opens.

## Boundaries and failures

One `PluginBoundary`, Suspense plus an error boundary, wraps each host and
each contribution. A contribution that suspends renders nothing until it is
ready. A thrown error renders nothing, is
[reported](doc:plugins/reference#failure-reports) to the host's error tracker,
and stops only that host or contribution. Boundaries catch only errors thrown
while rendering: an error in `onClick`, a command's `run`, async code or
`settings.set` reaches none, so plugin code reports it with
`api.errors.capture`. A contribution that threw stays empty while its plugin
shows as on, until its host remounts: a `readonly` toggle, the user switching
the plugin off and on, or a re-created plugin.

A hook that throws marks its plugin `failed` until the user switches it off
and on, its module is replaced (a new `hostKey`), or another document opens. A
`readonly` toggle keeps it failed.

## Settings storage

A host loads its plugin's values once, from `localStorage` under
`petrinaut:plugin:<id>`. A stored value the spec rejects reads as the default,
unknown keys are dropped, and unreadable storage gives every default.
`settings.set` validates the value, stores it, then persists it; when storage
is full or unavailable, the value applies until reload. Two `set` calls in one
tick both apply. Each change gives a new settings snapshot, which becomes the
plugin's `api.settings`. The rows of a plugin that is off or failed are hidden.

## React Compiler

Plugin code runs without the React Compiler. Compiled, a hook returns the same
contributions while its inputs hold, so nothing publishes. Uncompiled, it
returns new contributions on every render of its host, which publishes them
again and re-renders every outlet.

- `PluginHost` opts out with `"use no memo"`: the hook it calls differs per
  host, which the compiler cannot compile. A host is keyed by its plugin's
  `hostKey`, so it calls one hook for life.
- `usePluginApi` opts in with `"use memo"`, because it calls no hook and
  `infer` mode would skip it. Compiled, it returns a new `api` only when the
  settings snapshot changes.

## Performance measurements

`<Petrinaut>` includes the Performance plugin alongside the host's plugins.
Its [monitor](layer:ui.plugins.performance) reads the public performance API.
The plugin declares persisted visibility and expansion switches, one palette
command with a keyboard binding, and a root contribution. The FPS counter starts hidden and
expands into collapsible detail sections. The reader mounts while the counter
is visible; collapsing details preserves its subscription and frame history.
Hiding it preserves the host and settings without keeping an idle subscription.
Snapshot updates stay inside the monitor and do not republish plugin contributions.
The monitor uses the public React user-settings context for motion preferences.
Disclosures retain content through their closing transition, then unmount it.
Pointer capture separates dragging from clicks; resize observations keep the
widget within the editor bounds.

`PluginEditorRuntime` owns the performance collector. Plugins request its
read-only capability through `access.performance`; the same API is available
to first-party and third-party plugins. Subscription owns collection, so a
monitor can stop collecting by unmounting its reader. Store publications are
batched at 250 ms intervals and frame history holds 24 samples. Host records
are removed on unmount; snapshots include at most 128 active hosts.

With no subscribers, the collector has no animation callback or visibility
listener. Host creation and first publication each read the clock once.
Subsequent publication and profiler callbacks return without reading the
clock while collection is off. The profiler wrappers keep a stable position
in the tree when monitoring switches on or off, preserving component state.

| Measurement             | Interpretation and limits                                                                                                                                                                                                                                                                                                       |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Browser FPS             | Animation callbacks divided by actual elapsed time. It follows the display's refresh rate and includes main-thread stalls. It cannot establish how many frames were painted, GPU cost, or which editor caused a gap. Hidden documents stop collection and resume with a fresh window.                                           |
| First publication       | Wall time from creation of the committed host wrapper to the hook's first contribution publication. It includes scheduling, sibling work and Suspense waiting. It excludes module download before host creation, completion of asynchronous effects, and first paint. It is a lifecycle interval, not isolated plugin CPU time. |
| Publications per second | Contribution publications divided by the observation window. The host's layout effect publishes when contributions or settings change. This differs from hook invocations, descendant updates and React commits.                                                                                                                |
| Profiled commits        | Distinct React commit timestamps across a plugin's hook and contribution boundaries during observation. One commit can update several boundaries.                                                                                                                                                                               |
| Render milliseconds     | The sum of React `actualDuration` across those separate boundaries. It covers render work associated with committed updates. Commit-phase duration, layout, paint and abandoned render work are outside this value.                                                                                                             |
| Observer milliseconds   | Synchronous frame collection, snapshot construction, listener delivery and profiler aggregation in the preceding sample. It excludes later React rendering, browser layout/paint, and React's own profiling bookkeeping. Use an external comparison to measure the full observer effect.                                        |

Standard production React does not call `Profiler.onRender`. Render duration
therefore remains `null`, and profiling stays `waiting-for-callback`; zero
would falsely claim a measurement. Development and production profiling
builds can supply callbacks. Development Strict Mode can repeat work and
effects, so its counts are unsuitable for production comparisons. React's
[Profiler reference](https://react.dev/reference/react/Profiler) documents
the build requirement and the meaning of `actualDuration`.

React Compiler can reuse component output and calculations. Neither a
publication nor a commit proves unnecessary work. The collector leaves
component invocation counts unavailable and applies no waste score. The
monitor's own updates are included under its plugin id. Compare the same
interaction with monitoring off and on, and use browser performance traces
when attribution needs commit, layout, paint or worker timing.
