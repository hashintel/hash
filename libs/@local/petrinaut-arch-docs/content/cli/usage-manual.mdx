The Petrinaut CLI runs **one model per process**. `petrinaut serve` loads
Petrinaut Core once, then compiles one model: TypeScript/HIR compilation, a
check that every metric the model advertises compiled, and one engine
instantiation. Readiness then goes to stderr. From that point the process
answers one JSON-lines request at a time, until stdin closes over stdio or it
receives SIGINT or SIGTERM over a socket.

It is an internal tool for scripts, Python loops, and backend jobs — it
exposes no HTTP or TCP, only stdio (default) or a Unix socket.

```bash
turbo --filter @hashintel/petrinaut-cli build
node libs/@hashintel/petrinaut-cli/dist/cli.js serve --model ./my-model.yaml
```

The examples below shorten `node libs/@hashintel/petrinaut-cli/dist/cli.js` to
`petrinaut`, the package's bin name.

## Where models and manifests come from

Both are produced by the Petrinaut editor:

- A **model** file is the editor's save format.
- An **optimization manifest** is generated by the editor when the user
  configures an optimization experiment: a snapshot of the model with the
  chosen scenario, objective, and parameter bindings.

## Choosing a model source and transport

`serve` takes exactly one model source and at most one transport flag:

| Flag                    | Source                                        | Transports    |
| ----------------------- | --------------------------------------------- | ------------- |
| `--model <path>`        | Model file (YAML or JSON)                     | stdio, socket |
| `--model-stdin`         | Model JSON as the first stdin line            | stdio only    |
| `--optimization <path>` | Optimization manifest file (YAML or JSON)     | stdio only    |
| `--optimization-stdin`  | Optimization manifest as the first stdin line | stdio only    |

- `--stdio` (the default) reads requests from stdin and writes responses to
  stdout; diagnostics and the ready line go to stderr.
- `--socket <path>` serves the same protocol on a Unix socket instead.
  `--stdio` and `--socket` are mutually exclusive, and the socket transport
  requires `--model <path>`.
- The stdin bootstrap line (model or manifest) is capped at 8 MiB. The stdin
  sources exist for read-only containers and callers that already hold the
  current snapshot, avoiding a temporary file.
- Both model sources accept the editor's versioned save format and the older
  unversioned one.
- The file sources (`--model`, `--optimization`) accept YAML or JSON, detected
  from the content rather than the file name. The stdin sources read a single
  JSON line.

```bash
# stdio, model from a file
petrinaut serve --model ./my-model.yaml

# stdio, manifest as the first line
petrinaut serve --optimization-stdin --stdio

# Unix socket
petrinaut serve \
  --model ./my-model.yaml \
  --socket /tmp/petrinaut.sock
```

## The JSON-lines protocol

One JSON object per line in, exactly one JSON object per line out, in request
order. Requests carry `{ id, method, params? }`; the `id` is echoed on the
response.

![One request through the CLI](@diagrams/cli-request-flow.svg)

Errors come back as one line too:

```json
{ "id": 2, "error": { "message": "Unknown parameter \"x\"" } }
```

Request lines are capped at 10 MiB. Five methods exist:

| Method                  | Purpose                                               | Needs      |
| ----------------------- | ----------------------------------------------------- | ---------- |
| `healthz`               | Liveness — returns `{ "ok": true }`                   | any source |
| `metadata`              | Parameters, places, and metrics of the compiled model | any source |
| `run`                   | One simulation with explicit parameters or a scenario | any source |
| `optimization.describe` | The study's direction, settings, and search space     | manifest   |
| `optimization.evaluate` | One trial: suggested values in, objective out         | manifest   |

`metadata` lists the parameter aliases, place names, and metric ids that the
other requests use.

```json
{
  "id": 1,
  "result": {
    "parameters": [
      {
        "id": "param__infection_rate",
        "name": "Infection Rate",
        "variableName": "infection_rate",
        "type": "real",
        "defaultValue": "3",
        "valueRange": null
      }
    ],
    "places": [
      { "id": "place__infected", "name": "Infected", "index": 0, "color": null }
    ],
    "metrics": [
      {
        "id": "metric__infected_fraction",
        "name": "Infected Fraction",
        "optimizationObjective": null
      }
    ]
  }
}
```

## Run requests

```json
{
  "id": 2,
  "method": "run",
  "params": {
    "parameters": { "infection_rate": 1.5, "recovery_rate": 0.8 },
    "initialState": { "Susceptible": 990, "Infected": 10, "Recovered": 0 },
    "metrics": ["Infected Fraction"],
    "maxSteps": 100,
    "dt": 0.1,
    "seed": 4242
  }
}
```

- `parameters` — keys may be a parameter's variable name, id, or display
  name; exact ids win, then variable names, then display names, and duplicate
  aliases resolve to the model's last entry. Reals must be finite, integers
  integral, booleans JSON booleans or the strings `"true"`/`"false"`.
- `initialState` — keys may be a place id or display name (ids win; last
  entry wins on duplicate names). Uncolored token counts are integers `0`
  through `4,294,967,295`; colored places take one object per token.
- `scenario` — alternatively `{ "id": "...", "parameterValues": { ... } }`
  selects a model scenario: the CLI validates the flat values' declared types
  and materializes net parameters and the initial marking through Petrinaut
  Core's scenario compiler. `scenario` cannot be combined with `parameters`
  or `initialState`.
- `metrics` — metric names or stable ids, evaluated **on the final frame
  only** and returned as scalars under the caller's selector. Display names
  must be unique because the compiled model keys its result values by name.
- `maxSteps` / `maxTime` — at least one is required. The last step is
  shortened so a `maxTime` completion returns exactly that `finalTime`. `dt`
  defaults to `1`.
- `seed` — optional integer `0` through `2,147,483,647`. Omitted seeds are
  generated, so pass one for reproducibility.

Every `run` starts from fresh simulation state, so repeating an identical
request with the same seed returns the same result.

Transition predicates are part of the model structure. To change predicate
logic, change the model; to change the values a predicate reads, pass new
`parameters`.

The response is summary-first — no frame histories or metric distributions:

```json
{
  "id": 2,
  "result": {
    "seed": 4242,
    "status": "complete",
    "completionReason": "maxSteps",
    "frameCount": 101,
    "finalTime": 10,
    "finalPlaceTokenCounts": {
      "place__susceptible": 900,
      "place__infected": 40,
      "place__recovered": 60
    },
    "metrics": { "Infected Fraction": 0.04 }
  }
}
```

`finalPlaceTokenCounts` covers the root places advertised by `metadata`;
places created internally by subnet expansion are not part of the contract.

## Optimization studies

An optimization manifest is a versioned, self-contained document (YAML or
JSON): a complete model snapshot with **one scenario** and **one metric**, plus
`scenario.parameterBindings` naming every scenario parameter once as either
`fixed` or `optimize`. Bounds, integer steps, and numeric scales live in the
manifest — they are transient to that study, not part of the model. The CLI
owns the Petrinaut side: it validates the manifest, injects fixed values,
compiles the scenario, runs the model, and returns one scalar objective per
trial. An optimizer such as Optuna only consumes the flat description and
submits one suggestion per trial.

![The optimization loop](@diagrams/cli-optimization-loop.svg)

Manifest validation enforces work budgets: at most 1,000 trials, at most
100,000 steps per seeded run (`ceil(maxTime / dt)`), and at most 5,000,000
total steps across `steps × seedsPerTrial × trials`. A manifest over budget is
rejected with the field to fix (`study.trials`, or `execution.seedsPerTrial`
when the seed count alone pushed it over).

### Describe the search space

```json
{ "id": 1, "method": "optimization.describe" }
```

The response carries the direction, the study settings, and the parameters
that are not fixed:

```json
{
  "id": 1,
  "result": {
    "direction": "maximize",
    "study": {
      "trials": 100,
      "sampler": "tpe",
      "seed": 42,
      "seedsPerTrial": 1
    },
    "parameters": [
      {
        "identifier": "production_rate",
        "type": "float",
        "default": 100,
        "minimum": 80,
        "maximum": 140,
        "scale": "linear"
      },
      { "identifier": "enabled", "type": "boolean", "default": true }
    ]
  }
}
```

| CLI type  | Domain                                                    | Optuna suggestion                    |
| --------- | --------------------------------------------------------- | ------------------------------------ |
| `float`   | `minimum`, `maximum`, `scale` (`linear` or `log`)         | `suggest_float`                      |
| `int`     | `minimum`, `maximum`, `step`, `scale` (`linear` or `log`) | `suggest_int`                        |
| `boolean` | no numeric bounds                                         | `suggest_categorical([False, True])` |

A logarithmic integer domain requires `step: 1`. `default` is the scenario's
default value; the optimizer picks each trial's value.

### Constraints

A manifest may carry `constraints`: a list of boolean conditions, each
`{ "space", "id", "name"?, "code", "hir" }`. `space` is `"parameters"` for a
condition over the scenario and net parameters (checkable before a run) or
`"state"` for a condition over the simulation state (observed while a run
goes); `code` is the authored TypeScript and `hir` its lowered form, validated
against the HIR grammar. The describe response returns the list verbatim, so a
client evaluates them itself: the Python binding reads each one as a callable
with a boolean, a signed margin, and a pydantic validator. The CLI does not
enforce constraints yet.

### Evaluate a trial

Send every — and only — described parameter:

```json
{
  "id": 2,
  "method": "optimization.evaluate",
  "params": {
    "parameterValues": { "production_rate": 112.5, "enabled": true }
  }
}
```

```json
{ "id": 2, "result": { "objective": 1234.5 } }
```

The CLI handles requests serially: use one CLI process with a single Optuna
worker, or one independent CLI process per parallel worker.

### Seeded runs per trial

Set `execution.seedsPerTrial` (1–100, default 1) in the manifest to evaluate
every trial as a small Monte Carlo batch. The trial's seeds derive
deterministically from `execution.seed`: run 0 keeps `execution.seed` itself,
and each later run `i` (counting from 0) uses the Monte Carlo derivation
`|seed + (i + 1) × 2654435761| mod 2^31`. Every trial reuses the identical
sequence, so the optimizer compares parameter configurations under **common
random numbers**.

With more than one seed, `objective` becomes the mean of the per-seed
objectives and `replicates` reports each seed's value; with one seed the
response stays `{ "objective": ... }` alone:

```json
{
  "id": 2,
  "result": {
    "objective": 1234.5,
    "replicates": [
      { "seed": 42, "objective": 1230.0 },
      { "seed": 1013904268, "objective": 1239.0 }
    ]
  }
}
```

The seeded runs execute as one [Monte Carlo experiment](doc:simulation/worker-sharding):
one run per seed, split across `worker_threads` shards. `--threads <n>` sets
the shard count; the default is one per logical core minus one, and it is never
more than `seedsPerTrial`. `--threads 1` spawns no workers at all and simulates
on the calling thread. Sharding never changes the replicate values — each run's
seed is pinned explicitly — only how fast the trial finishes. When the worker
bundle is unavailable (running the CLI from source), runs fall back to the
calling thread and the CLI says so on stderr.

## Driving the CLI from Python

The [python-bindings](layer:python-bindings) package wraps this protocol: a
session owns one CLI process, each request is a method, and an error frame
raises. Its [usage manual](doc:python-bindings/usage-manual) covers the session
lifecycle, the timeouts, and the exception types.

```python
from petrinaut import OptimizationSession

with OptimizationSession(manifest_path="optimization.json") as session:
    description = session.describe()
    print([parameter.identifier for parameter in description.parameters])
    # Send every — and only — described parameter.
    value = session.objective({"production_rate": 112.5, "enabled": True})
```

An Optuna study calls `describe()` once and maps each described
parameter to the `suggest_*` call from the table above. Its objective function
passes the suggested values to `objective()`. The manifest and the CLI own the
Petrinaut types, the scenario compilation, and the fixed values.
