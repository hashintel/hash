The ad-hoc form lets a user define Initial State and Parameters inline —
without saving a [scenario](layer:core.simulation.authoring) — and compiles
what they enter through a scenario **generated at run time and never
persisted**. Three consumers mount the same component, differing only in
what selecting a value means (`selection` prop): quick simulation and plain
experiment creation pass `"none"` (no toggles), and the optimization drawer
passes `"optimize"` (a value is selected for the optimizer). A third mode,
`"controls"`, relabels the same selection as a control over the state for a
future classical scenario editor — no consumer mounts it yet; a story
exercises it. The toggle column, the pill on every open editor, and the
strings all follow the mode; the underlying state field is the same
`optimize` settings object in every mode.

The design is the scenario **code editor's model, constrained**: everything
the form can express synthesizes to code-mode scenario source that the
existing `compileScenario` already evaluates, so the compiler is untouched.

`synthesizeAdHocScenario` is the plain-run entry (Optimize ignored, scenario
only); `synthesizeAdHocOptimization` is the optimization entry (full output).
Each `AdHocOptimizedField` carries the generated parameter's deterministic
`adhoc.*` name, its typed domain, its target path, and an attribution label
(`Space › item 0 › x`) — the join key from optimization results back to the
thing the user selected.

## The row grammar

The Initial State section renders one block per place. A coloured place is a
token spreadsheet: one column per colour element, one row per token line.
Rows come in three user-facing kinds (`adHocRowKindOf`), mixing freely
within a place:

- **Fixed** (`#n` in the gutter): one token, one expression per cell.
- **Dynamic** (`i`, blue): a count expression's worth of tokens; a quiet
  strip above the cells carries `×` and the count, and inside the row `i`
  runs from 0 to count − 1.
- **Optimized/controlled count** (`i`, purple): a dynamic row whose count
  carries optimize settings — in the model, `kind: "template"` with
  `count.optimize` non-null.

Column headers toggle **shared columns**: one value supersedes every cell of
that column, the cells render as dimmed derived copies whose clicks edit the
shared value, and un-sharing restores the cells exactly. An uncoloured place
is a single line: its name and a count slot. Variables render in the same
spreadsheet grammar at two scopes — top-level (referenced as
`scenario.<name>`) and per-place (bare identifier) — as gutter + name +
type + value + toggle rows. Parameters are read-only name/type plus an
override slot that shows `default (…)` while empty.

Every table ends in a **phantom line**, slightly shorter than content rows:
clicking its `+` gutter or its message line materializes the entry (a fixed
row, a fresh `variableN`) and opens the natural editor.

## The editing model: actions, reducer, history

Every edit is a **serializable action** dispatched through
`AdHocFormContext.dispatch`. The action vocabulary and the pure reducer live
in core (`ad-hoc-actions.ts`): `setExpression`, `setDomainField`,
`toggleSelection`, variable actions (`add`, `rename` — optionally rewriting
references — `setType`, `delete`, `duplicate`), token-row actions (`add`,
`delete`, `duplicate`, `setKind`), and `shareColumn`/`unshareColumn`. Each
action has a zod input schema (`adHocActionInputSchemas`), mirroring the net
editor's mutation actions. `applyAdHocAction(state, context, action)` is
pure and returns the same reference when an action changes nothing.

The undo history (`use-form-history.ts`) is redux-like: a stack of state
snapshots with a cursor. Dispatch applies the reducer, appends a snapshot,
and hands the new state to the caller's `onChange` — the form stays
controlled. **Undo and redo never dispatch**; they move the cursor and
replay the recorded snapshot, so redo after undo restores the identical
state value. Consecutive dispatches whose `adHocActionCoalescingKey`
matches (typing in one slot — expression, one bound, a rename without
rewrite) collapse into one entry; the key match is identity-based, not
time-based, and goes cold on undo/redo or an external state change, so a
burst never merges into an entry the user has navigated to. The history is
ephemeral: it lives with the form instance and dies with the drawer.
Cmd/Ctrl+Z and Shift+Cmd/Ctrl+Z (or Ctrl+Y) work anywhere in the form except
inside an open text field or Monaco editor, which own their own stacks
while open.

## The interaction model

Cells follow a **select-then-edit** contract: focus selects (plain `:focus`
styling — a pointer click must show it too), and Enter, a second click, or
a double-click opens the editor. The value editor opens **in place**: a
frameless single-line Monaco exactly over the cell, the slot's attribution
path floating above, the mode's toggle pill below. Turning the toggle on
swaps the expression editor for a small bounds spreadsheet in the same slab
— Min/Max/Scale (Step where the domain is integer), each bound an
expression cell with the same select-then-edit contract. Escape peels one
layer at a time: bound edit → bound cell → closed slab → the cell. Only one
editor is open at a time; opening one closes the rest.

**Gutters select rows.** Focusing any gutter selects its whole row (every
cell paints the selection wash) and drives the dependency highlight as if
each cell in the row were focused. A pointer click on a gutter only
selects; Enter or the trailing `⋯` dots affordance (visible on row hover or
focus) opens the row menu — kinds and Delete for token rows, Delete for
variables. Delete/Backspace on a selected gutter deletes directly, moving
focus to the neighbouring row or the phantom line.

**Dependency highlighting** (`dependency-highlight.ts`) is pure reference
extraction over expressions: focusing a value highlights the Variable and
Parameter rows it reads; focusing a Variable or Parameter also highlights
every cell that reads it. Highlight (green wash) and selection (blue wash)
are background images, so they compose over row tints.

## The keyboard contract

Arrow keys walk each table as a grid; moves past an edge continue into the
neighbouring **zone** in document order (grids, section headers, place
headers — the registry in `use-form-navigation`, which skips zones that
decline focus, e.g. collapsed ones). Tab stays native throughout the form;
the one interception is an open gutter menu, where Tab dismisses the menu
back to its gutter, as menus do. Section
and place headers are stops of the walk: Left collapses, Right expands, and
a collapsed place renders as one line with a row/token summary. Inside the
token spreadsheet the vertical walk passes through every line — column
headers, the shared-values line, each dynamic row's count strip, the rows,
the phantom line — and returns to the column a vertical move started from
after crossing a full-width stop. The type select and the bounds Scale
select join the grid: arrows navigate while closed, Enter opens, and the
open list owns its keys. Escape on a selected (not editing) cell is a
no-op.

## Slots: one join key for errors, diagnostics, and cells

A **target** names a value-carrying location (`cell`, `column`, `count`,
`variable`, `netParameter`); a **slot** is a target plus a part
(`expression`, `min`, `max`, `step`, `name`). `adHocSlotKey(slot)` renders a
stable, path-safe string used three ways:

- synthesis errors carry their slot, so the form renders each error on the
  editor it belongs to;
- the [LSP session](layer:core.lsp) names each slot's virtual TypeScript
  document `…/_temp/adhoc/<session>/values/<slotKey>.ts`, so diagnostics map
  back the same way;
- the form computes the same key when rendering, closing the loop.

The same keys anchor undo coalescing: `adHocActionCoalescingKey` derives a
slot key for the actions that type into one slot.

A cell superseded by a shared column passes its **column's** target, so the
shared value's problems surface on every cell it derives.

The worker generates one wrapped document per non-empty slot, with the scope
the generated code will actually have: `parameters.<name>` ambiently,
top-level Variables as `scenario.<name>`, and — inside a place's rows — the
per-place Variables declared **in order** plus `i` and `count`, so a Variable
referencing itself or a later sibling fails in the editor exactly as it would
at run time. Optimize bounds see only the constant scope, so `i` in a bound is
a type error. An open cell is a Monaco document with inline markers; a closed
cell underlines in red and carries the first synthesis error or diagnostic as
its tooltip.

## The expression vocabulary

| Written as          | Resolves to                                                                    |
| ------------------- | ------------------------------------------------------------------------------ |
| `parameters.<name>` | a net parameter (override-aware)                                               |
| `scenario.<name>`   | a top-level Variable (they stand in for scenario parameters)                   |
| bare identifier     | a per-place Variable, in its place's rows                                      |
| `i`, `count`        | per row: position and row count (fixed rows: `i` = list position, `count` = 1) |

In generated code the compiler's `scenario` object (which carries the
generated `adhoc.*` values during optimization) is captured as
`__adhocParams` before the Variables shadow `scenario`, in both the
initial-state body and wrapped override expressions.

`AdHocFormContext` is the internal seam: the form provides the whole editing
state, the `dispatch` write path, the net context, the selection mode, the
LSP session id, per-slot error/URI lookup, the dependency highlight, and the
focused-value reporter, so the components beneath carry only their own value
and location.

## Mounting the form

```tsx
const [state, setState] = useState<AdHocScenarioState>(EMPTY_AD_HOC_STATE);

<AdHocScenarioForm
  state={state}
  onChange={setState}
  context={{ netParameters, places, types }} // from the SDCPN
  selection="none" // "optimize" | "controls" where the toggles apply
/>;
```

Two props shape an **embedding**: `withVariables={false}` removes the
Variables section (an expression referencing `scenario.<name>` then fails as
unknown), and `bare` renders the exposed groups without the collapsible
section chrome, for hosts with their own heading grammar. The Parameters
section removes itself the same way when the context carries no net
parameters. Quick simulation combines all three — `bare`,
`withVariables={false}`, `netParameters: []` — so Simulation Settings shows
exactly one group, the places, under the panel's own "Initial state"
heading, with the panel's parameter inputs staying the single owner of
parameter values.

The form runs its own LSP session against `LanguageClientContext`; with the
default no-op client (tests, stories without the provider) it degrades to
synthesis-only validation. State is plain data — hold it wherever the consumer
already keeps its draft (component state in the drawers, `SimulationContext`
for quick simulation) and hand `output.scenario` to `compileScenario` when the
user runs.

## Invariants worth knowing

- **Nothing is ever thrown away.** Toggling Optimize retains the expression
  and the previous bounds; changing a row's kind retains its count; releasing
  a shared column restores every cell exactly, including held Optimize state.
- **Every edit is one dispatched action**, applied by the pure reducer in
  core; undo replays snapshots and never dispatches.
- **Generated names are deterministic** (`adhoc.<place>.r<row>.<field>`,
  `adhoc.count.<place>`, `adhoc.var.net.<name>`, `adhoc.param.<name>`), so
  optimization results attribute across runs; place-name duplicates among
  participating places are a synthesis error because the generated initial
  state is keyed by place name.
- **The generated scenario is never persisted** — no consumer writes it into
  the net file, and the experiments table shows it as "Ad-hoc scenario".
