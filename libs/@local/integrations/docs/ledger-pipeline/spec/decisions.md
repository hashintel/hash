| D14 | How many tables does a run carry? The plan had one capture file, from "single source". In a definition a "source" is one table, and the aviation example has two. | Several, one capture file per table of the definition. A table without changes gets an empty file. Since D18, one capture query and one capture table per table, and a table without changes gets a query that gives no rows.                                                                                                                                                                                                                      | Paul, 2026-11-19                              |
| D15 | Where does the command line tool live, and what are its commands called?                                                                                          | In the existing app, as `hash-integrations ledger start`, `capture`, `prepare` and `send`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    | Paul, 2026-11-19                              |
| D16 | What does Capture do when a file it is given is missing or is not Parquet?                                                                                        | It fails for good, as the plan has it: the `failure` part is written, and the run is cleared by hand (D7). Claude had proposed to refuse the call and record nothing. Capture does not check the names of the files against the definition. Prepare does. Since D18 the same holds for a query that fails or gives other columns than its table, with the code `capture_query_invalid`.                                                                                                                                                                                                                                                       | Paul, 2026-11-19                              |
| D17 | How is the sync table stored?                                                                                                                                     | As a Delta table under `sync/` in the integration's place in the bucket, partitioned by run, one commit per write. It replaces the Iceberg table with its pointer file of `../plan.md`, step 3. Delta needs no pointer file and no catalog, and its commits are atomic. Read and written through DuckDB since D18.                                                                                                                                                                                                                                                                                                                            | Paul and Fedor, 2026-11-19                    |
| D18 | How do the stages pass their data?                                                                                                                                | As Delta tables in the integration's place in the bucket, read and written through DuckDB with its `httpfs` and `delta` extensions. No stage uploads or downloads a data file. Capture takes one DuckDB query per table from the integration's operator configuration, never from a definition, because a query runs with the bucket's credentials. It appends the rows to the table `capture/{table}`. Prepare copies a run's rows from there into its workspace. The sync table is written and read through DuckDB, and `deltalake-core` and `serde_arrow` leave the workspace. Moving Parquet files by hand between stages does not scale. | Fedor, 2026-11-26, while implementing BE-1211 |
| D19 | What does a second write of a run to a table do?                                                                                                                  | Nothing. Each run's rows are one append, whose commit is tagged with the run id (`delta_set_transaction_version`). A second append of the run, also one by another process at the same time, leaves the rows of the first and returns their number. A retry of Prepare therefore keeps the sync table rows of the attempt that committed first. Write-once tagged appends make retries and concurrent writers safe without overwrites. This reverses Paul's decision of 2026-11-24 that a write replaces the run's rows.                                                                                                                      | Fedor, 2026-11-26, while implementing BE-1211 |
