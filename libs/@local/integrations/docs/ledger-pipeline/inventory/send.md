## 4. Gaps

1. No code cuts a batch when the entity is already in the open batch. Labs and engine (main) plan one write per entity and engine refuses duplicates (`DuplicateWrite`, engine (main) `graph/plan/mod.rs:150-160`); pipeline diffs to one write per entity.
2. No code writes progress after each batch or resumes at a batch count. Resuming needs every earlier row encoded again to recompute the cut; no code skips confirmed batches this way.
3. No code counts a create conflict as done without a patch.
4. No code reads the sync table in send order or checks its row count against `PrepareOutput.rows`.
5. `FakeGraph` cannot apply `add` operations (pipeline `fake.rs:300-309`).
6. No code writes `current.json` with `active` and `last_completed`; the pipeline file holds `committed` and `sending`.

## 5. Questions

1. **A bulk create answered 409.** The bulk endpoints are atomic: the Graph runs all patches of a bulk request in one transaction (`libs/@local/graph/postgres-store/src/store/postgres/knowledge/entity/mod.rs:2161-2193`) and the fake rejects the whole batch (`fake.rs:261-268`; test `fake.rs:354`). The pipeline client discards the body (`client/mod.rs:129-132`), so Send cannot tell which member existed; labs `executor.rs:3303` tests exactly this. Options: count every write of the batch as created; send the writes of that batch again one per request and count each 409 as created; read the body and find the entity.
2. **How the Graph answers a replayed write.** From code and tests, none run for this inventory:
   - _Create of an existing entity._ A one-element bulk create gets 409 on the pinned Graph image (`graph_http/transport.rs:23-26`); a single create gets 409 in `delivery_replay` on main. The bulk create handler documents no 409 and maps no conflict error (`libs/@local/graph/api/src/rest/legacy/entity/mod.rs:324-362`); an unmapped error becomes 500 (`legacy/status.rs:102-117`, `libs/@local/status/rust/src/status_code/http_compat.rs:12-15`). Labs treats a 500 whose body holds `duplicate key` as a conflict (`executor.rs:1737-1747`). Whether the body names the entity is untested; entity UUIDs are unique across webs (`graph_http/README.md:14-19`).
   - _Patch with unchanged values._ The store returns `Unchanged` and writes no edition when properties, property metadata, draft, archived, types and confidence are equal; provenance is not compared (`…/knowledge/entity/patch.rs:413-426`). The pinned-image test confirms it for `replace` patches (`graph_http/scenarios.rs:60-75`); no test covers `add` patches.
   - _Patch of a missing entity._ 404 (`patch.rs:297-302`, handler `legacy/entity/mod.rs:633-636`, test `transport.rs:30-33`). One missing entity fails the whole bulk patch.
   - _Archive of an archived or missing entity._ Archived: `archived` is unchanged, so `Unchanged` and 2xx by the rule above. Missing: 404. Pipeline counts 404 as `Absent` (`delivery.rs:102-103`); labs fails permanently (`executor.rs:1522-1524`); labs treats an archive 409 as done (`:1521`) but no code path that returns 409 for an archive was found.
   - _Wrong kind._ An update for a missing entity gets 404 and a create for an existing one gets 409; with no fallback the first is lost or refused, the second counted as created with its values not applied.
3. **Which statuses retry, end the run, or refuse one write.** The pipeline and labs tables above differ on 499, 500, other 5xx, archive 404 and archive 409. A refused bulk is split into single writes in the pipeline (`delivery.rs:157-168`); removing the create/patch fallback does not decide whether the split stays.
4. **Refused writes.** `Outcome::Rejected` and `SendCounts.rejected` remain in the skeleton; `rejected.parquet` and the link skip (`tally.rs:101-103`) depend on "What happens to a write the Graph refuses". `delivery::batch` receives only bodies, so it cannot see link endpoints.
5. **Provenance input.** Send's contract has no `CaptureOutput`, but the pipeline puts `captured_at` in every body (`stage/plan/mod.rs:63`). Location name: connector id (pipeline) or `"{connector}/{source}"` (labs `batch_sync.rs:833`). Labs row-level authors and dates have no sync-table column.
6. **Update bodies.** Every update carries `archived: false` (labs `client.rs:373`, engine (main) `request.rs:227`), so an update revives an archived entity. An update with no properties: labs sends `"properties": []` for an entity and omits it for a link; engine (main) omits it, citing a Graph rejection. A link update has `entityTypeIds` in engine (main) and pipeline, none in labs.
7. **Oversized body.** One body above `max_bytes` becomes its own batch, and above 2 MiB it is only logged (`write.rs:15`, `:218-220`); labs refused a payload above 4 MiB (labs.md line 599, from the inventory, not rechecked). The skeleton has no code for it.
8. **Stale sender.** The pipeline reads `current.json` before every request (`delivery.rs:59`); the new design detects a stale writer only at the conditional `run.json` write after a batch.
9. **Engine version.** The ledger crate depends on `hash-integrations-engine` (`ledger/Cargo.toml`); on this branch that crate has no `graph/`, on `main` it has the `add` encoder and a client but no `storage/`.
