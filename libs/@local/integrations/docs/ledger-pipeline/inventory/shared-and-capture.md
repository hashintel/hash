### Can `run/store.rs` build a conditional write on `engine`'s public API?

No. A conditional write needs a read that returns a version and a put with `PutMode::Update`. Four things block it:

1. The object store is reachable only through the private field `ArtifactStorage::store` (`engine/src/storage/artifact/mod.rs:37`). The four public methods publish and materialize content-addressed files; none reads bytes with a version or writes with a mode.
2. A caller outside `engine` cannot name the object. `ArtifactKey` has a private field and no public constructor (`engine/src/storage/mod.rs:30`). The only public key is `ArtifactNamespace::artifacts()` (`namespace.rs:41`), and `publish` writes under it at `{prefix}/sha256/{xx}/{sha256}.{ext}` (`reference.rs:128-135`). No public method gives `runs/{run}/run.json` or `current.json`.
3. The only conditional put in `engine` is `bind`, which is `pub(crate)` and supports create-if-absent only (`binding.rs:28-47`).
4. The local backend cannot compare and replace through `object_store`. `ArtifactStorage::local` opens `LocalFileSystem` (`local.rs:10-13`). Labs records that this provider "has atomic Create but no Update support" (`src/blob.rs:1720-1723`), which is why both labs and pipeline lock and compare by hand. The engine does not keep the local root in a public form: `directory()` is `pub(crate)` (`mod.rs:85`).

These are the private APIs `pipeline/README.md:10-11` refers to for "conditional markers". The pipeline's answer was to add `local_root` and the module `mutable` inside its own copy of `storage`. A crate outside `engine` could open a second `object_store` client from the public `S3Bucket` fields and recompute the integration root `tenants/{web}/integrations/{hex(sha256("{web}:{connector}"))}` (`namespace.rs:22-26`), but `namespace.rs:12-14` says the namespace is "the one place that knows the storage layout".

### Parquet writing: `pipeline/src/run/table/`

What it does: `RowFile` writes rows of `Cell` (`Null`, `Text`, `UInt`, `Boolean`) against a fixed list of `Column { name, kind, nullable }` with kinds `Text`, `UInt16`, `UInt32`, `UInt64`, `Boolean` (`run/table/mod.rs:21-57`). It refuses an empty or duplicate column list and a cell of the wrong kind or out of range with `Code::RowInvalid` (`:91-100`, `:116-133`). It buffers 1,024 rows or 8 MiB of text per Arrow batch (`:18-19`, `:143-145`), writes through `ArrowWriter` with `SourceCapture::writer_properties()` (`:103-105`), publishes the local file with `SourceCapture::publish` (`:164-168`) and then stores it with `RunContext::publish`, which gives a content-addressed `ArtifactRef` under `artifacts/` and deletes the local file (`:170-178`, `context.rs:96-108`). `BufferedFile` moves each flush to a blocking task (`buffer.rs:20-83`). `store_query` exports a workspace query to a stored file (`mod.rs:224-234`); `load_table` loads a stored file into a workspace (`:235-250`).

Who uses it today: Plan writes `writes.parquet` and the issues file through `BufferedFile` (`stage/plan/write.rs:185`, `:259`); Send writes the rejected file (`stage/send/tally.rs:86`); Diff writes id files with `RowFile::create_at` (`stage/diff/rows/ids.rs:152`) and its outputs with `store_query` (`stage/diff/files.rs:23-118`); Diff and Plan load stored files with `load_table` (`stage/diff/rows/mod.rs:75`, `stage/diff/prior.rs:27-62`, `stage/plan/mod.rs:79-81`).

Fit for the issues file: the pipeline issues file has seven nullable or required `Text` columns `kind`, `target`, `entity_id`, `key`, `issue`, `property`, `reason` (`stage/plan/write.rs:74-110`) written by `IssueFile` (`:253-290`). The module covers it unchanged.

Fit for the sync table: the `Change` fields map to `Text` (`run_id`, `op`, `entity_id`, `entity_type`, `left_entity_id`, `right_entity_id`, `properties` as JSON text) and `UInt64` (`order_id`). There is no JSON or timestamp kind. Three limits apply:

- `RowFile` calls `SourceCapture::stage` and `SourceCapture::publish`, which are `pub(crate)` in engine (`engine/src/capture.rs:105`, `:114`), and `SourceCapture::writer_properties`, which exists only in the pipeline copy. A copy into the ledger crate must replace these three calls.
- The file always ends up at a content-addressed key. Option 2 of "Prepare retry appends the same rows twice" (names fixed by run and row order) cannot be built on it as it is.
- The ledger `Cargo.toml` lists neither `parquet` nor `arrow-array`, which `RowFile` imports (`run/table/mod.rs:5-10`). It lists `duckdb` with `appender-arrow`.

## 4. Gaps

- **No conditional write in `engine`.** See section 1. `run/store.rs` and `run/current.rs` cannot be written against `engine`'s public API as it is.
- **No key builder for `runs/{run}/run.json`.** The pipeline's private `run()` exists only in its copy of the namespace.
- **No way to find a run's sync-table files.** `PrepareOutput` holds `rows`, `issues` and `issue_count` only (spec lines 156-162); `engine` has no list operation; `publish` names files by content. `sync_table::read::in_send_order` has no source for the file references.
- **No local source root in the skeleton.** `SourceKind::Local { key, .. }` is "a Parquet file under the configured local storage root" (`definition/src/source/mod.rs:122-126`). The pipeline passes the root through `CaptureStore::new(local, ..)`; the skeleton's `capture(context, input)` and `RunContext` (`run/mod.rs:141-148`) carry no root.
- **No `_op` values other than `snapshot`.** No code in the three code bases writes `insert`, `update` or `delete` into `_op`. Labs writes `'snapshot'` (`src/snapshot.rs:78`) and only reads `_op` to refuse `delete` (`src/graph/planner.rs:694-696`). The engine writes `'snapshot'` at staging (`engine/src/workspace/connection/staging.rs:108`) and later only checks that `_op` and `_key` exist as non-null `VARCHAR` (`staging.rs:173-195`). No pipeline stage reads `_op` (`grep` over `pipeline/src/stage`).
- **No code writes the first `run.json` or sets `current.json.active`.** The spec gives this to "the start of the run" and the skeleton has no function for it; pipeline's `start` (`run/mod.rs:143-159`) resolves operations that are out of scope.
- **Missing dependencies.** The ledger `Cargo.toml` lists no `tempfile`, `bytes`, `futures-util`, `parquet` or `arrow-array`, which the pipeline's `mutable` and `table` modules import, and `tokio` only with `time`.

## 5. Questions

1. **A capture file cannot carry `_op` today.** The spec says the change kind comes from the capture's `_op` column with `insert`, `update` or `delete`. Engine staging refuses a source column named `_op`, `_key` or `_content_hash` with `ReservedColumn` (`engine/src/workspace/connection/staging.rs:76-83`) and then sets `_op` to `'snapshot'` for every row (`:108`). Labs refuses `_op`, `_key`, `_before` in a source (`src/snapshot.rs:45-55`). Options: Prepare reads `_op` from the raw file before staging; staging keeps an incoming `_op`; the change kind goes in a column with another name.
2. **The capture formats of labs and the monorepo differ.** A labs capture file already holds `_op`, `_key`, `_before` because the table is built by `snapshot::materialize` before `COPY` (`src/engine/source_capture.rs:128-153`); its loader reads it back with `SELECT * FROM read_parquet(...)` (`src/engine/candidate.rs:205`). A monorepo capture is the source bytes, and `_op`/`_key` are added in Prepare (`stage/diff/rows/mod.rs:75-91`). The spec says "the format of the labs captures". Options: the input file follows the labs format with the three columns; the input file holds only source columns, as the monorepo stores it.
3. **Where conditional writes live.** Spec line 306 leaves it open. Options: add `read_versioned`/`replace_if`, `local_root` and a run key to `engine` (the pipeline copy is a ready patch, plus the change on `main` that has no storage module at all); rebuild in `run/store.rs` on a second `object_store` client from `S3Bucket` and a recomputed root.
4. **The engine on `main` has no storage.** The skeleton imports types that exist only on this branch. Options: land the BE-933 branch's engine storage on `main` first; keep the ledger crate on a branch that carries it.
5. **`copy_from` before `publish` copies the file twice.** `copy_from` makes a local copy (`engine/src/capture.rs:72-78`); `publish` reads a path, hashes it and aborts if the bytes change during upload (`storage/artifact/mod.rs:110-129`, `:234-237`). `SourceCapture::open` alone gives the row count. Options: copy then publish as `engine/src/sources/mod.rs:233-264` does; publish the input file directly and read the footer with `open`.
6. **How a bad local file is classified.** Under the pipeline classifier a missing file becomes `SourceError::Read` with no inner frame, so `StorageUnavailable` (retryable) (`stage/capture/error.rs:45-46`, `:51-61`); an invalid footer becomes `CaptureError::Read`, so `ScratchUnavailable` (retryable) (`run/error.rs:248-258`). The skeleton documents `SourceConfiguration` (permanent) "if a source does not name a readable local Parquet file" (`ledger/src/capture.rs:41`). Options: keep the pipeline codes; map these cases to `SourceConfiguration`.
7. **The 1 MiB limit now covers the definition.** `replace_if` refuses more than 1 MiB (`mutable/mod.rs:24`, `:109-111`). `RunInput.definition` holds the whole YAML, and `run.json` embeds `RunInput`; the pipeline stored the input as a content-addressed `input.json` with no limit (`run/marker.rs:27-48`). `aviation.yaml` is 1,870 bytes. Options: keep 1 MiB; raise it; store the definition as an artifact and reference it.
8. **Conflict handling in the caller.** Pipeline retries eight times then returns `StorageUnavailable` (`run/current.rs:74-91`); labs fails on the first conflict (`src/run_manifest.rs:241-244`); the skeleton returns `false` and says "the caller reads the file again and decides" (`run/store.rs:34-35`). Options: one loop in `run/store.rs`; each stage handles `false`.
9. **Obsolete codes.** `Code` keeps the four-stage codes `BaseMoved`, `Superseded`, `MarkerMissing`, `ArchiveLimit`, `NothingCommitted`, `TargetMissing`, `RequestMismatch`, `InvalidCheckpoint`, `PlanTooLarge`, `InvalidWrites` and the source-reader codes (`ledger/src/run/error.rs:31-96`), and the spec says `Code` is unchanged. Options: keep them for stable persisted text; remove those no new stage returns.
10. **Retry after the local file is gone.** The spec says a Capture retry copies every file again, and the skeleton says a present capture part is returned without reading a file (`ledger/src/capture.rs:35-36`). Between the S3 copies and the `run.json` write there are no bindings, so a crash there followed by removal of the local file loses the capture. Options: accept; keep the pipeline's per-source binding (deferred in the open issues).
