# Prepare: code inventory

This file lists the existing code that the Prepare stage of `hash-integrations-ledger` can reuse, the tests that cover it, what is missing, and the facts that force a decision. The contract is [spec.md](../spec.md); the skeleton is `ledger/src/prepare/`.

Path prefixes: `labs/` is `pocs/integrations_rs` in the labs repository at `40a8d14`. `engine/`, `pipeline/`, `ledger/` and `definition/` are under `libs/@local/integrations/` on branch `codex/ingestion-pipeline`. `engine (main)` is the same crate on `main`, which differs from the branch: `main` has `src/graph/` (`EntityUpsert`, `LinkUpsert`, `GraphOperation`) and no `src/storage/`; the branch has `src/storage/` and no `src/graph/` (`engine/src/lib.rs:19-28`). `labs.md` is `docs/pipeline/reference/labs.md`. Every line reference was read for this file unless it is marked "from the inventory, not rechecked".

## 2. Also needed by another stage

- `RunContext::fetch`, `publish`, `scratch_file`, `open_workspace` (pipeline `run/context.rs:92-133`). The ledger `RunContext` has the same fields and no methods (`ledger/src/run/mod.rs:141-148`). Capture publishes files; Prepare fetches captures, opens a workspace and publishes the issues file and sync table files.
- The error mapping helpers `artifact`, `statement`, `capture`, `preparation`, `open`, `close`, `scratch` (pipeline `run/error.rs:225-297`). The ledger `run/error.rs` has `Code` and `StageError` but none of these functions (`ledger/src/run/error.rs:137-225`).
- `RunInput::parse_definition` (pipeline `run/mod.rs:129-131`). The ledger `RunInput` has no such method. Capture reads the definition too.
- `RowFile`, `Cell`, `Column`, `ColumnKind` (pipeline `run/table/mod.rs:22-222`) and `BufferedFile` (`run/table/buffer.rs:13-84`). Prepare uses them for the ID file and the issues file; the sync table writer and reader can use them.
- `load_table` and `store_query` (pipeline `run/table/mod.rs:224-250`): Send, if it reads sync table files through a workspace.
- `sync_table::write::append` (`ledger/src/sync_table/write.rs:17-22`) is written by Prepare and read by Send; nothing in the three code bases writes `Change` rows.
- The entity and link kind: the skeleton has `rows::Kind` (`ledger/src/prepare/rows.rs:15-21`) and `sync_table::Operation` (`ledger/src/sync_table/mod.rs:20-29`); pipeline has `Kind` and `Target` (`run/target.rs:21-26`, `:124-127`).

## 4. Gaps

1. No code carries the `_op` value of a capture file into the target tables. engine `stage_table` refuses an `_op` or `_key` source column and writes `'snapshot'` (`engine/src/workspace/connection/staging.rs:75-111`). No code maps `insert`, `update`, `delete` to `Operation`.
2. Link tables carry no `_op`. `check_metadata` does not run on link steps (`engine/src/workspace/connection/pipeline.rs:57-101`), and pipeline's own test has a link step that drops `_key` (`rows_missing_ids_and_endpoints`). labs builds the link table from the endpoint and property columns only, so `_op` is dropped there too (`labs/src/graph/link_pipeline.rs:93-97`). Nothing can tell `CreateLink`, `UpdateLink` and `ArchiveLink` apart.
3. No code builds an archive from a row. labs fails on a `delete` row (`src/graph/planner.rs:694-696`); pipeline archives only what the diff finds missing (`stage/diff/files.rs:33-43`). For Prepare to derive the entity ID of a `delete` row, the row has to survive every SQL step of its pipeline (`check_metadata` keeps `_op` but a `WHERE` clause can drop the row) and carry a non-blank value in the sink's `entityId` column, which is a column of the pipeline output, not the source primary key (`pipelines.rs:85-90`); a link archive needs both endpoint columns.
4. Nothing archives the old link when a foreign key changes, or the links of a deleted row. `_before` exists only in labs, where it is always `CAST(NULL AS JSON)` (`src/snapshot.rs:76-85`) and only checked for presence (`src/steps.rs:188-212`); engine and pipeline have no `_before` column.
5. Nothing keeps the order of the captured rows. pipeline orders change files by entity ID (`stage/diff/files.rs:122`), ids are joined on `rowid` of the last SQL table, and labs orders by entity ID (`src/graph/sink.rs:356`, from the inventory, not rechecked). The capture has no sequence column, so `Change.order_id` has no source for several changes to one entity.
6. The size check on `TargetRows.sources` does not exist.
7. No writer exists for `Change` rows or for an issues file of `Issue` values; `sync_table::write::append` is `unimplemented!()`.

## 5. Questions

1. **How `_op` reaches the target tables.** engine `stage_table` refuses a source column `_op` or `_key` and sets `_op = 'snapshot'`; labs loads the capture with `SELECT *` and keeps the file's `_op`. Options: (a) the capture file holds `_op` under another column name and Prepare renames it after staging; (b) Prepare skips `stage_table`, loads the file with `create_table` and passes that table to `prepare_pipeline`, which then requires `_op` and `_key` as non-null `VARCHAR` in the file (engine public API, no engine change); (c) change engine `stage_table` to keep a given `_op`. Engine tests `staging_composite_keys` and `staging_invalid_columns` assert the current behaviour.
2. **A row with a null or blank source ID.** pipeline leaves the row out and lists it as `missing_id` or `missing_endpoint`; the skeleton fails with `RowKey`; labs derives an ID from `""` and from `"null"`. Options: fail the run, leave the row out and list it in the issues file, or derive an ID.
3. **Several rows with one entity ID in a target.** The skeleton fails with `DuplicateEntityId`; the open issue "Several changes to one entity in a run" chose to send every change, which needs such rows. pipeline checks across all targets, labs per sink. Options: drop the check, keep it per target, or keep it across targets.
4. **The kind of a link change.** Link rows carry no `_op` (Gap 2). Options: require link SQL to keep `_op` and check it like entity steps; take the kind from the row of the source the link reads; write every link row as a create.
5. **The issues file.** Today it has seven columns and two issue kinds, and `key` can hold source values (the test asserts `["sensitive-key"]` is kept). The skeleton `Issue` has `entity_id` and `ConversionFailure` only and no target or key. Options: keep the seven columns; keep the skeleton fields; and whether rows left out for a missing ID (Question 2) go in the same file. `PrepareOutput.issues` is documented as present only "when a conversion failed" (`ledger/src/prepare/mod.rs:23`).
6. **When and per what the source check runs.** The set is per pipeline, so all sinks of a pipeline and every checkpoint it writes get the same set, and it is known only after the pipeline's SQL ran. Options: check per sink as computed today, or compute the sets from the definition before any SQL runs.
7. **Where link IDs come from.** pipeline `derive_link_ids` returns the IDs alone; engine (main) `LinkUpsert::new` derives the same IDs but also needs provenance and properties, and the branch's engine has no `graph` module. The spec names only `derive_entity_id` from engine.
8. **labs or pipeline conversion rules.** The spec takes expected values from labs first, but pipeline differs: a blank `boolean` coercion is `false` in labs and left out in pipeline; an unknown unit without fallback is the bare amount in labs and a `MeasureUnit` failure in pipeline; `01/15/2024` is `2024-15-01` in labs and a failure in pipeline. With per-property `add` updates, a left-out property keeps its old value in the Graph.
9. **Text of a non-text ID.** A `TIMESTAMP` ID is `2026-11-09T10:30:00Z` in pipeline and `2026-11-09 10:30:00` in labs, so the two derive different entity IDs for the same row. It matters only if entities written by labs must be addressed again.
