Ledger pipeline: how one run moves data

Three stages take changed rows to the Graph. Every stage reads from S3, writes its result to S3, and then records its completion in one status file. Pick a stage to see what it touches.

Hover an arrow to see the data it carries. Click a box in a green lane, the changed rows or the Graph API to see everything it holds at the selected stage. Both green lanes are the same S3 bucket, one per integration.

4changed rows captured
→
5changes in the sync table
→
4batches sent
→
3 · 1 · 1created · updated · archived in the Graph

Three rules hold for every stage

  • A stage writes its result to S3 first and its part of run.json second.
  • A part that is present in run.json means that stage is complete. A retry runs the stage again and reads run.json.
  • The next run starts only after this run has completed all three stages.

1 · Capture

Stores the changed rows in S3, so that Prepare can run again without asking the source. It reads no source system and changes no row.

Reads

Local Parquet file itemsone row per changed source record
_op id name weight related_to
insert A-1 Widget null B-1
insert B-1 Gadget heavy null
update C-1 Sprocket 2.5 null
delete D-1 null null null

Does

  • Copies each file to S3 unchanged.
  • Reads the row count from the Parquet footer.
  • Records the capture time.

      3 · Send
      
      
      
        Builds the Graph requests from the run's rows and sends them in batches.
        The requests are not stored: the same rows always give the same batches,
        so a retry needs only the number of confirmed batches.
      
      
    
      
    
      
      
      The 5 changes become 4 batches, sent in this order
      
      
      
        
      
          
      Batch 0POST /entities/bulk
      
          
      
            create A-1create B-1
          
      
          
      Entity creates and updates are sent first.
      
        
      
        
      
          
      Batch 1PATCH /entities/bulk
      
          
      
            update C-1
          
      
          
      New batch: create switches to update.
      
        
      
        
      
          
      Batch 2POST /entities/bulk
      
          
      
            create link A-1 → B-1
          
      
          
      
            New batch: links follow entities, so both endpoints exist.
          
      
        
      
        
      
          
      Batch 3PATCH /entities/bulk
      
          
      
            archive D-1
          
      
          
      New batch: entity archives are sent last.
      
        
      
      
      
    
      
    
      
      
      
        
      Reads
      
        
      
          Sync tableS3 data · the 5 rows of this run
        
      
        
      
          batch part of run.jsonat most 128 writes and 1.5 MB per batch
        
      
        
      
          send_progress part of run.jsonwhere to resume after a stop
        
      
      
      
      
      
        
      Does
      
        
        
          
      • Sorts the rows by operation, then by order_id.
        • 
          
      • Encodes each row as a request body.
        • 
          
      • 
            Starts a new batch when the operation changes, when create switches
            to update, at a limit, or when an entity is already in the batch.
          
        • 
          
      • 
            Counts a create that the Graph answers with a conflict as done.
          
        • 
        
      
      
      
      
      
        
      Writes
      
        
      
          Graph API4 requests · 3 created, 1 updated, 1 archived
