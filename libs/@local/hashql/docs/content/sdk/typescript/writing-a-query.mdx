---
title: Writing a HashQL query
description: Build a release briefing by selecting tasks, filtering them and combining related queries.
---

In [Using the TypeScript SDK](/docs/hashql/sdk/typescript/using-draft), we built a summary of a task supplied as an input. While we could keep supplying those values ourselves, a query language that only computes over its inputs doesn't let us ask questions of the database. HashQL's integration with the HASH graph lets us query its entities and transform the results. So how do we move from computing with values to querying the graph?

Suppose we're preparing a release briefing. We want to know which tasks remain unfinished, which of those are blocked, and which still need an owner. All of these share a common root: we must find the tasks that belong to one release. So let's just start by that!

This guide expects that you are already [familiar with the basics of HashQL](/docs/hashql/intro), and the [Draft API of the TypeScript SDK](/docs/hashql/sdk/typescript/using-draft).

<Callout title="Following the examples">

We're working on a fictional graph database, feel free to create your own graph dev environment and seed the database withsw data, or follow along only through the guide. Creating the database is out of scope for this guide, but may be added in the future if requested.

</Callout>

## Start with the tasks

The HASH graph is bi-temporal, which means that time is tracked on two axes: transaction time, when the system recorded something, and decision time, when it was decided to be true.

You can think of these as a Cartesian plane. Each entity version occupies a rectangle, with an interval on each axis. A query pins one axis to a timestamp and selects an interval on the other, drawing a line through that plane. Entity versions whose rectangles intersect the line belong to the selected temporal view.

<TemporalAxes />

Looking at _when_ is just as important as looking at _what_. We want to know the evolution of the data over time, so we can understand how it has changed. That means that the temporal axes are actually an input into the query. So let's set up the temporal input first.

```ts title="release-briefing.ts" data-example="setup"
import { JExpr, Program, Prelude } from "@local/hashql";
import type { Type } from "@local/hashql";
import * as Draft from "@local/hashql/Draft";
import { Option, Result, pipe } from "effect";

const axes = Prelude.graph.QueryTemporalAxes;
```

<Callout>

Currently the prelude is not automatically generated, you must instead reference the type yourself:

```ts
const axes = Program.TypeExpression.fromType<Program.Query.QueryTemporalAxes>(
  Option.getOrThrow(
    JExpr.Type.reference("::graph::temporal::QueryTemporalAxes"),
  ),
);
```

</Callout>

[`QueryTemporalAxes`][query-temporal-axes] describes which axis is pinned to a timestamp and which varies over an interval. Our `axes` value describes this input's type, we don't set it as part of our program, because we're interested in the values at different points in time.

<Callout>

In general, as outlined in [using the TypeScript SDK], try to remove as much variance from your programs as possible. This means that generally your program should have the temporal axes as an input.

</Callout>

Now we can construct our first query:

```ts tab="TypeScript (Draft)" tab-group="hashql-language" data-example="all-tasks"
const briefing = Draft.program({ axis: axes }, ($, { axis }) =>
  $.query.entities(axis).collect(),
);
```

```text tab="Functional notation" tab-group="hashql-language"
(collect
  (entities (input axis QueryTemporalAxes)))
```

```text tab="Reference notation" tab-group="hashql-language"
head::entities(input(axis, QueryTemporalAxes))
  |> tail::collect
```

Queries inside of HashQL follow a pattern of head -> body -> tail. The head decides where we start our query, for example [`entities`][query-entities] starts a graph computation over all the entities in the knowledge graph at any given point in time. The body transforms the result (more on that later), and the tail then decides how to materialise the result (in functional programming terms, head creates an effect, body transforms the result inside of the effect, and the tail then executes the effect), for example [`collect`][query-collect] asks for those entities as a list.

<Callout>

Currently the only head supported is [`entities`][query-entities], and the only tail supported is [`collect`][query-collect].

</Callout>

With the query that we have now we return all the entities in the graph, but those are not the ones that we're interested in, so how do we transform our set of entities to only those that we are?

This is where the body operations come in. Each graph works on vertices in the knowledge graph, and each body operation transforms each vertex that we have selected, either by removing it or by keeping it. An analogy for this is the [map-reduce pattern] from functional programming. In our example, the head returns a [`Graph<Entity<?>>`][graph-type], which is a graph that only contains entities, and where the properties of it are [unknown].

<Callout>

Currently the only body operation supported is [`filter`][query-filter]

</Callout>

Before we start filtering, let's first take a look at how we can take a look at the query that we have written so far.

### Serialize the program

The [intro to the TypeScript SDK] already shows how to serialize the query program, to boil it down we first take our expression fragment (which is in itself a valid HashQL program), and mark it as a [`Program`]. We then compile it to [J-Expr] using the [`Program.compile`][program-compile] function, which may fail, for example because an identifier is not valid HashQL.

For our example, this would look like this:

```ts title="Produce J-Expr" data-example="serialize"
const queryText = pipe(
  briefing,
  Result.map(Program.program),
  Result.flatMap(Program.compile),
  Result.getOrThrow,
);

console.log(queryText);
```

<details>
<summary>Generated J-Expr</summary>

```json
[
  "::graph::tail::collect",
  [
    "::graph::head::entities",
    [
      "::kernel::special_form::input",
      "axis",
      "::graph::temporal::QueryTemporalAxes"
    ]
  ]
]
```

</details>

What's important is that the program that we compiles was not executed, it was merely translated to a [`Program`] that can be run on the server. We also haven't verified that the program is truly well-formed. The TypeScript SDK tries its hardest to catch any errors at construction time, but each program still goes through a compilation step on the server, which may surface issues that are not caught by the TypeScript SDK.

Let's keep this serialisation block at the end of our file, and periodically check how it changed. When we show new snippets we always replace the `briefing` declaration, while retaining the setup and any helpers we've added.

## Ask about one release

The first query selects too much: we're reviewing Meridian, not Northstar. We need a predicate that compares each task's release with the release we're interested in.

Before writing that predicate, we need to describe the properties it reads. The table uses short labels such as `release`, but HASH identifies properties by their base URLs. Our example schema uses `https://example.com/types/property-type/release/` for the release name, with corresponding URLs for `status` and `assigned`.

### Set up the example

Add this helper after the imports and before `briefing` to access the three Task properties used by our query:

<details>
<summary>Declare the task fields</summary>

```ts title="Task property declarations" data-example="fields"
const taskFields = (
  entity: Program.Expression.Expression<
    Program.Query.Entity,
    Program.Inputs.Empty
  >,
) => {
  const properties = entity.$projectUnsafe("properties");

  return {
    release: Program.Expression.assume<Type.PrimitiveString>()(
      properties.$projectUnsafe(
        "https://example.com/types/property-type/release/",
      ),
    ),
    status: Program.Expression.assume<Type.PrimitiveString>()(
      properties.$projectUnsafe(
        "https://example.com/types/property-type/status/",
      ),
    ),
    assigned: Program.Expression.assume<Type.PrimitiveBoolean>()(
      properties.$projectUnsafe(
        "https://example.com/types/property-type/assigned/",
      ),
    ),
  };
};
```

</details>

The helper constructs field accesses using the Task schema above: `release` and `status` are strings, and `assigned` is a Boolean.

### Filter by the release input

We could write `"Meridian"` into the predicate, but the same question will be useful for other releases. Let's make `release` an input instead:

```ts tab="TypeScript (Draft)" tab-group="hashql-language" data-example="release"
const briefing = Draft.program(
  { axis: axes, release: String },
  ($, { axis, release }) =>
    $.query
      .entities(axis)
      .filter("task", ($, task) => $.eq(taskFields(task).release, release))
      .collect(),
);
```

```text tab="Functional notation" tab-group="hashql-language"
(let release (input release String)
  (collect
    (filter (entities (input axis QueryTemporalAxes))
      (fn () (task: _) Boolean
        (eq task.release release)))))
```

```text tab="Reference notation" tab-group="hashql-language"
let release = input(release, String) in
head::entities(input(axis, QueryTemporalAxes))
  |> body::filter((task) -> task.release == release)
  |> tail::collect
```

With `release` supplied as `"Meridian"`, T-105 drops out. The remaining tasks are T-101 through T-104. Supplying `"Northstar"` instead selects only T-105, without changing the program we send.

[`filter`][query-filter] introduces a closure over each vertex. In Draft, `"task"` names that closure's parameter. The callback receives a construction context and a handle for the parameter, then constructs a Boolean expression with `$.eq`. Draft invokes the callback while building the program. The generated HashQL closure is what tests each task when the query runs.

This is the same distinction between TypeScript logic and HashQL logic that we explored in the SDK guide. Writing `taskFields(task).release === release` would compare two expression handles in JavaScript. `$.eq` constructs the comparison we want the graph query to perform.

<Callout>

In the functional and reference tabs, `task.release`, `task.status` and `task.assigned` abbreviate the property-URL accesses declared by `taskFields`. They aren't built-in fields on every HASH entity. `eq` and `ne` are the core comparison functions.

</Callout>

## Keep the unfinished work

We have the right release, but T-104 is already done. Add another filter to keep tasks whose status isn't `"done"`:

```ts tab="TypeScript (Draft)" tab-group="hashql-language" data-example="unfinished"
const briefing = Draft.program(
  { axis: axes, release: String },
  ($, { axis, release }) =>
    $.query
      .entities(axis)
      .filter("task", ($, task) => $.eq(taskFields(task).release, release))
      .filter("task", ($, task) => $.ne(taskFields(task).status, "done"))
      .collect(),
);
```

```text tab="Functional notation" tab-group="hashql-language"
(let release (input release String)
  (collect
    (filter
      (filter (entities (input axis QueryTemporalAxes))
        (fn () (task: _) Boolean
          (eq task.release release)))
      (fn () (task: _) Boolean
        (ne task.status "done")))))
```

```text tab="Reference notation" tab-group="hashql-language"
let release = input(release, String) in
head::entities(input(axis, QueryTemporalAxes))
  |> body::filter((task) -> task.release == release)
  |> body::filter((task) -> task.status != "done")
  |> tail::collect
```

Our selection now contains T-101, T-102 and T-103. The first filter narrows the graph computation to one release. The second narrows it to unfinished work within that release. Neither operation changes the stored tasks.

Notice that `collect` still comes last. Each filter takes a graph computation and returns another graph computation, so we can keep composing them. Only after describing the selection do we ask for its vertices as a list. We could also combine the predicates with `and`, but separate filters give each part of our question its own predicate.

## Turn the list into a briefing

We can now answer the first question. What about blocked tasks and tasks without an owner?

Both are subsets of the unfinished work. Rather than repeat the selection for each answer, we can name it with a HashQL binding and use that binding in three places. This is the same expression-reuse technique from the SDK guide, applied to a graph computation.

```ts tab="TypeScript (Draft)" tab-group="hashql-language" data-example="briefing"
const briefing = Draft.program(
  { axis: axes, release: String },
  ($, { axis, release }) => {
    const releaseTasks = $.let(
      "releaseTasks",
      $.query
        .entities(axis)
        .filter("task", ($, task) => $.eq(taskFields(task).release, release)),
    );
    const unfinished = $.let(
      "unfinished",
      $.query(releaseTasks).filter("task", ($, task) =>
        $.ne(taskFields(task).status, "done"),
      ),
    );

    return Program.Structural.struct({
      unfinished: $.query(unfinished).collect(),
      blocked: $.query(unfinished)
        .filter("task", ($, task) => $.eq(taskFields(task).status, "blocked"))
        .collect(),
      unassigned: $.query(unfinished)
        .filter("task", ($, task) => $.isFalse(taskFields(task).assigned))
        .collect(),
    });
  },
);
```

```text tab="Functional notation" tab-group="hashql-language"
(let releaseTasks
  (filter (entities (input axis QueryTemporalAxes))
    (fn () (task: _) Boolean
      (eq task.release (input release String))))
  (let unfinished
    (filter releaseTasks
      (fn () (task: _) Boolean
        (ne task.status "done")))
    (unfinished: (collect unfinished),
     blocked: (collect
       (filter unfinished
         (fn () (task: _) Boolean
           (eq task.status "blocked")))),
     unassigned: (collect
       (filter unfinished
         (fn () (task: _) Boolean
           (eq task.assigned false)))))))
```

```text tab="Reference notation" tab-group="hashql-language"
let releaseTasks =
      head::entities(input(axis, QueryTemporalAxes))
        |> body::filter((task) ->
          task.release == input(release, String)),
    unfinished = releaseTasks
      |> body::filter((task) -> task.status != "done")
in
(
  unfinished: unfinished |> tail::collect,
  blocked: unfinished
    |> body::filter((task) -> task.status == "blocked")
    |> tail::collect,
  unassigned: unfinished
    |> body::filter((task) -> task.assigned == false)
    |> tail::collect
)
```

There are two changes here. First, `releaseTasks` and `unfinished` name graph computations. We haven't collected either one yet. Second, the returned struct collects each view separately, after applying any additional predicate it needs.

Why wrap the bindings in [`$.query`][context-query] again? `$.let` returns an expression handle referring to the binding. That handle retains its HashQL type, but it isn't the fluent query builder we started with. `$.query(unfinished)` gives us the query-building methods for that graph expression, so we can continue filtering it or collect its result.

The struct contains three lists of entities. Showing only their task labels, our example graph gives us:

```json title="Expected briefing for Meridian"
{
  "unfinished": ["T-101", "T-102", "T-103"],
  "blocked": ["T-102"],
  "unassigned": ["T-102", "T-103"]
}
```

T-102 appears in every list: it is unfinished, blocked and unassigned. That's what we want! Each field answers a different question about the same release. The lists overlap, and their order here is only for readability: the query hasn't requested an ordering.

## Use the briefing

Keep the serialisation block after the final `briefing` declaration. Its output now describes the bindings and all three graph computations in one program. The host integration supplies `axis` and `release` when submitting it. Draft constructs the program, while transport and execution belong to that integration.

Changing the inputs changes the question without rebuilding its structure. With the same temporal view and `release` set to `"Northstar"`, the expected briefing is:

```json title="Expected briefing for Northstar"
{
  "unfinished": ["T-105"],
  "blocked": ["T-105"],
  "unassigned": []
}
```

Before connecting the query to an execution environment, try predicting how the Meridian result should change. Mark T-102 as assigned, move T-103 to Northstar, or complete every Meridian task. Which lists change, and which stay the same? These small examples give us concrete expectations to check against the returned entities.

We now have the complete briefing we set out to construct. The next sections explore questions we could add to it, rather than further steps required to finish this program.

## Taking the query further

### Who should we talk to?

The `assigned` flag tells us whether a task has an owner, but not who that person is. To answer that question, our schema needs an ownership relationship between a task and a person. The query would follow that relationship and include the owners in its result:

```json title="An ownership-enriched result"
{
  "task": "T-102",
  "title": "Confirm the rollout window",
  "owners": []
}
```

A list lets us represent both an unassigned task and a task with multiple owners. Whether multiple owners are valid is a schema decision. We also need to decide how to represent a relationship whose person the caller isn't allowed to see, rather than silently treating it as no owner.

<Callout title="Relationship traversal">

Draft's current query builder provides filtering and collection, but no ownership traversal builder. [Graph query heads][graph-heads] track part of the wider work. This extension also needs the relationship schema, traversal operations and backend support before we can write its Draft example.

</Callout>

### Is the release getting healthier?

We made `axis` an input for a reason. We can ask the same questions about a previous review's temporal view and the current one, keeping the release input unchanged.

Suppose T-101 and T-102 were blocked at the previous review, while only T-102 is blocked now. Comparing the two blocked sets tells us that T-101 left the set. A count alone wouldn't identify that task, and equal counts could hide one task being resolved while another becomes blocked.

The host can compare the two returned briefings using stable entity identities. The T-labels in this example are display labels, not the identities a real integration should join on. Performing the comparison within HashQL would require the corresponding collection operations and an execution path that supports them.

### Give me the short version

The lists also give the host enough information to summarise the current review:

```json title="Desired summary for Meridian"
{
  "unfinishedCount": 3,
  "blockedCount": 1,
  "unassignedCount": 2,
  "needsAttention": true
}
```

Here, `needsAttention` means that at least one unfinished task is blocked or unassigned. If we also want a count of distinct tasks needing attention, adding the blocked and unassigned counts won't work: T-102 would be counted twice. We'd need the union of those sets, compared by entity identity.

<Callout title="Summary operations">

The host can compute this summary from the returned lists. To construct it entirely through Draft, we still need a complete typed collection-counting API and backend support. [Generated library declarations][library-declarations] and [aggregate SQL emission][aggregate-emission] address different parts of that work.

</Callout>

## Where to go next

The query follows a small pattern: start a graph computation, refine it with predicates, then choose the values to return. Bindings let us share a selection across related questions, while inputs let us ask those questions about another release or temporal view.
