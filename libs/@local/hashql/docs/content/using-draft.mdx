How do we author HashQL programs in TypeScript? The HashQL SDK provides three layers of abstraction, each building on the previous one. The higher-level APIs help us catch errors before our programs reach the server.

<Mermaid
  chart="
graph LR
    jexpr[J-Expr] --> program[Program]
    program --> draft[Draft]
"
/>

J-Expr is the transport syntax used between the SDK and the server. The [`J-Expr`] API builds expressions in this syntax without checking their HashQL types. [`Program`] builds on J-Expr with a purely functional interface over a typed expression tree. [`Draft`] provides a more convenient imperative interface for constructing programs from those expressions.

The distinction between [`Program`] and [`Draft`] is analogous to writing Redux reducers with and without Immer. Without Immer, reducers explicitly construct the next state without mutating the previous one, often using spread syntax to copy the affected objects. Immer gives us a mutable representation of that state, called a _draft_, and records our changes to produce the next immutable state. HashQL's [`Draft`] follows the same idea: we write declarations in order, and it assembles the expression tree for us. That's where the name comes from.

The lower-level [`Program`] and [`J-Expr`] APIs are considered unstable, so we'll focus on [`Draft`] for program construction. We'll still use [`Program`]'s expression helpers and serialisation where needed.

## Getting started

The HashQL SDK makes extensive use of the excellent [effect] library and therefore adopts some of its conventions and idioms. However, you don't need to be familiar with [effect] itself to use the SDK.

To get started, import the SDK:

```ts
import * as Draft from "@local/hashql/Draft";
```

You can also import individual symbols. Most commonly, you'll want to import [`program`][draft-program], the function we'll use to create a [`J-Expr`] program that can then be sent to the server.

```ts
import { program } from "@local/hashql/Draft";
```

## Building our first J-Expr program

The primary entry point for building a J-Expr program is the [`program`][draft-program] function. It takes two arguments: a definition of the program's inputs and a closure that constructs the program. We define the input names and types here, then supply their values when we send the program to the server for execution.

The closure itself takes two arguments: the [construction context][draft-context] (conventionally called `$`) and handles representing the program inputs. Any behaviour outside [`Program`], such as scope management, is handled through `$`. Expect to use it often—hence the short name.

Suppose we want to build a simple program that increments a task's revision number. We'll define the inputs first, then construct the program using a closure:

```ts title="revision.ts" data-example="revision"
import { Program } from "@local/hashql";
import * as Draft from "@local/hashql/Draft";
import { Result, pipe } from "effect";

const revisionInputs = { revision: BigInt };

const built = Draft.program(revisionInputs, ($, { revision }) => {
  const { add } = $.prelude();
  return add(revision, 1n);
});
```

You can also inline the input definitions directly into the `program` call. In this example, we define them separately, and the closure receives the corresponding handles as its second argument: an object keyed by field name. We destructure this object to access `revision` within the closure. Here, `revision` represents the program's input, not its value. That value will be supplied when the resulting HashQL program runs.

The HashQL SDK aims to be as user-friendly as possible and supports both explicit types and common JavaScript type constructors. In our example, `BigInt` maps to [`Program.Prelude.builtin.types.Integer`][builtin-prelude], which we could use instead.

The closure is evaluated immediately. Rather than propagating exceptions, [`program`][draft-program] catches them and returns a [`Result`] value that we can use to handle errors. Construction and serialisation can also fail for other reasons, such as an invalid binding name or a reference used outside its scope. These failures share the [`ProgramError.Construction`] error type, with a distinct, typed reason for each case.

The prelude is the set of symbols, such as [`add`][builtin-prelude], that are automatically imported and available in every J-Expr program. The full list of prelude symbols is available in the [`Program.Prelude`][builtin-prelude] reference. Advanced users can also override the default prelude using the [`Draft.withPrelude`] function. Note, however, that this function **does not** modify the prelude loaded by the server during execution. The supplied declarations must match the corresponding server definitions, or the SDK may accept a call that the server rejects.

The value produced by successful construction is an [`Expression`]. It can be used in other HashQL operations and records the input and output types, allowing multiple HashQL fragments to be composed naturally. Once we've finished composing expressions, [`Program.program`] wraps the root expression as a complete [`Program`]. [`Program.compile`] then serialises it to J-Expr JSON, reporting construction or serialisation failures through its [`Result`].

To serialise our expression, we use [`Result.map`] for [`Program.program`] because it returns a plain value. [`Program.compile`] returns another [`Result`], so we use [`Result.flatMap`] for that step. We finish with [`Result.getOrThrow`] to return the JSON string or throw if construction or serialisation failed. In an Effect workflow, we can instead use [`Effect.fromResult`] to handle the result as a typed effect.

```ts title="Serialize the program" data-example="serialize"
const serialized = pipe(
  built,
  Result.map(Program.program),
  Result.flatMap(Program.compile),
  Result.getOrThrow,
);

console.log(serialized);
// => ["::core::math::add",["::kernel::special_form::input","revision","::kernel::type::Integer"],{"#literal":1}]
```

## Detour: Using HashQL logic and TypeScript logic together

You can mix HashQL logic and TypeScript logic in the same program, but only the HashQL expression ultimately returned from [`Draft.program`][draft-program] is executed on the server. This allows us to model concepts such as macros and build-time functions or conditionals (similar to `#ifdef` in C/C++ or feature flags in Rust). Here, build time means when our TypeScript code calls `Draft.program`, not when TypeScript itself is compiled.

Suppose we want to make incrementing the revision optional. There are two ways to do this:

```ts
const maybeIncrement = Draft.program(
  { revision: BigInt, enabled: Boolean },
  ($, { revision, enabled }) => {
    const { add } = $.prelude();

    return $.if(enabled, {
      then: () => add(revision, 1n),
      else: () => revision,
    });
  },
);
```

Both branch callbacks run during construction to build their expressions. The server later evaluates `enabled` and selects one of the HashQL branches.

This approach is self-contained: the program declares both inputs it needs. However, the caller must supply both inputs on every call. Sometimes, we want to make this decision when constructing the expression instead. We can do this by moving the conditional out of the HashQL program and into the TypeScript construction logic. This is where build-time conditionals come in.

```ts
const buildProgram = (enabled: boolean) =>
  Draft.program({ revision: BigInt }, ($, { revision }) => {
    const { add } = $.prelude();

    if (enabled) {
      return add(revision, 1n);
    } else {
      return revision;
    }
  });
```

Both approaches produce the same result for matching input values, but they make the choice at different times. The first sends a conditional to the server. The second chooses which expression to construct before sending it. We can reuse our serialisation pipeline as a helper to compare the outputs:

```ts
import type { Type } from "@local/hashql";

const compile = <T extends Type.Any, I, E>(
  built: Result.Result<Program.Expression.Expression<T, I>, E>,
) =>
  pipe(
    built,
    Result.map(Program.program),
    Result.flatMap(Program.compile),
    Result.getOrThrow,
  );

console.log(compile(maybeIncrement));
// => ["::kernel::special_form::if",["::kernel::special_form::input","enabled","::kernel::type::Boolean"],["::core::math::add",["::kernel::special_form::input","revision","::kernel::type::Integer"],{"#literal":1}],["::kernel::special_form::input","revision","::kernel::type::Integer"]]

console.log(compile(buildProgram(false)));
// => ["::kernel::special_form::input","revision","::kernel::type::Integer"]

console.log(compile(buildProgram(true)));
// => ["::core::math::add",["::kernel::special_form::input","revision","::kernel::type::Integer"],{"#literal":1}]
```

The conditional logic inside `Draft.program` changes the compiled output sent to the server. As a rule of thumb, express as much logic as possible in HashQL. Use TypeScript control flow during construction when HashQL does not yet support the construct you need or when you need to make decisions based on configuration-time values.

The reason is simple: each program goes through a compilation step on the server. If a query remains unchanged, its compilation artefacts can be cached and reused. Keeping the decision as an input lets different calls reuse one compiled program. Making the decision during construction produces separate programs for the different configurations.

We can also use this technique to construct reusable fragments that act as macros:

```ts
const incrementTwice = Draft.program(revisionInputs, ($, { revision }) => {
  const { add } = $.prelude();
  const increment = (value: typeof revision) => add(value, 1n);

  return increment(increment(revision));
});

console.log(compile(incrementTwice));
// => ["::core::math::add",["::core::math::add",["::kernel::special_form::input","revision","::kernel::type::Integer"],{"#literal":1}],{"#literal":1}]
```

The helper takes the same kind of expression as `revision` and constructs an addition each time we call it. Calling it twice produces two nested HashQL additions. Remember that the TypeScript helper runs only during construction, so the server receives those additions rather than a call to `increment`.

## Assemble a task summary

For our task summary program, we need to express structured values rather than just a single integer. Our tasks should have a title, a revision and two flags: `blocked` and `done`. We can model this in the HashQL SDK using the [`Program.Structural.struct`] function, which creates a HashQL struct type definition. Its keys must be valid HashQL identifiers, and its values must be field expressions: either `String`, `Number`, `BigInt`, `Boolean` or another HashQL type expression.

```ts
const task = Program.Structural.struct({
  title: String,
  revision: BigInt,
  blocked: Boolean,
  done: Boolean,
});
```

Let's build on our previous program to return the task's title and next revision.

```ts
const updateTask = Draft.program({ task }, ($, { task }) => {
  const { add } = $.prelude();

  return Program.Structural.struct({
    title: task.title,
    nextRevision: add(task.revision, 1n),
  });
});
```

<Callout>You cannot destructure the fields of the `task` parameter.</Callout>

A language that can only construct values isn't very useful, so let's combine some of the functionality described in the [introduction to HashQL] with one of our helpers: `eq`.

```ts title="Choose a label from the task's fields" data-example="summary-attention"
const built = Draft.program(inputs, ($, { task }) => {
  const { add } = $.prelude();
  const needsReview = $.eq(task.blocked, true).and($.not(task.done));
  const attention = $.if(needsReview, {
    then: () => $.literal("review"),
    else: () => $.literal("clear"),
  });

  return Program.Structural.struct({
    title: task.title,
    nextRevision: add(task.revision, 1n),
    attention,
  });
});
```

In addition to providing access to the prelude, `$` offers several constructors and helpers, documented in [`Draft.Context`]. In particular, it gives us access to `$.eq`, which maps to the HashQL function `::core::cmp::eq` and compares two values for equality. You can also call this function directly from the prelude, but the `$` version is more convenient and should be preferred because it enables fluent chaining and composition of HashQL boolean expressions.

```ts
// Function call vs. fluent comparison.
```

Our example combines these helpers to choose a value based on the task's fields. If the task is blocked and not completed, we set `attention` to `"review"`; otherwise, we set it to `"clear"`.

## Assemble a task summary

Let's give the program a task with a title, a revision and two flags. The summary should propose its next revision and mark blocked, unfinished tasks for review. Keep the imports and serialization block, but replace the revision schema and program with these:

```ts title="Describe the task input" data-example="setup"
const inputs = {
  task: {
    title: String,
    revision: BigInt,
    blocked: Boolean,
    done: Boolean,
  },
};
```

The nested record describes a struct. The callback now receives a `task` handle whose fields TypeScript knows. Reading `task.title` constructs field access, and reading `task.revision` gives us the Integer expression we need for addition.

First, return just the title and proposed revision:

```ts title="Build the summary" data-example="summary"
const built = Draft.program(inputs, ($, { task }) => {
  const { add } = $.prelude();

  return Program.Structural.struct({
    title: task.title,
    nextRevision: add(task.revision, 1n),
  });
});
```

[`Program.Structural.struct`](/docs/hashql/reference/hashql/Program/Structural#struct) combines the field expressions into a struct expression. Its argument is a JavaScript record of handles. The result is a handle for the HashQL struct that the program will return.

Now add the review label. Replace the callback with this version:

```ts title="Choose a label from the task's fields" data-example="summary-attention"
const built = Draft.program(inputs, ($, { task }) => {
  const { add } = $.prelude();
  const needsReview = $.eq(task.blocked, true).and($.not(task.done));
  const attention = $.if(needsReview, {
    then: () => $.literal("review"),
    else: () => $.literal("clear"),
  });

  return Program.Structural.struct({
    title: task.title,
    nextRevision: add(task.revision, 1n),
    attention,
  });
});
```

`needsReview` combines two predicates. `attention` uses that Boolean expression to construct a HashQL `if`. For a blocked, unfinished task at revision `4`, the described result keeps its title, proposes revision `5` and sets `attention` to `"review"`. It returns a summary rather than updating the task.

Both branch callbacks run during construction, so Draft can build both branches. HashQL evaluates only the selected branch when the program executes. Keep network requests, logging and other host-side work outside these callbacks unless you intend them to happen during construction. A JavaScript `if (task.blocked)` would test the handle object, not the task's Boolean field.

## Extract reusable construction

The review rule is useful beyond this one callback. We can extract it into an ordinary TypeScript helper. Add this after `inputs`, before the program:

```ts title="Reuse the review predicate" data-example="expression-helper"
type Task = Draft.Body.Handles<typeof inputs>["task"];

const needsReviewFor = (task: Task) =>
  Program.Operators.eq(task.blocked, true).and(
    Program.Operators.not(task.done),
  );
```

[`Draft.Body.Handles`](/docs/hashql/reference/hashql/Draft/Body#Handles) derives the handle type from our schema. That keeps the helper's `task` consistent with the callback's `task`, including its required input. The helper needs only expressions, so it uses [`Program.Operators`](/docs/hashql/reference/hashql/Program/Operators) without taking a context.

Inside the callback, replace the inline predicate with `const needsReview = needsReviewFor(task)`. The generated program stays the same. The helper runs in TypeScript each time we call it and returns the expression it constructed.

We can also reuse the conditional label. This helper uses `$.if` to construct scoped branches, so it takes the caller's context:

```ts title="Reuse the conditional label" data-example="context-helper"
type TaskContext = Draft.Body.Context<
  Program.Prelude.Builtin,
  Draft.Body.Requirements<typeof inputs>
>;

const attentionFor = ($: TaskContext, task: Task) =>
  $.if(needsReviewFor(task), {
    then: () => $.literal("review"),
    else: () => $.literal("clear"),
  });
```

[`Draft.Body.Context`](/docs/hashql/reference/hashql/Draft/Body#Context) describes the `$` that our program receives. Its parameters retain the prelude and the input requirements. These helpers deliberately share one schema. A general helper can parameterize those relationships, but should preserve them rather than erase them to an unrestricted context or untyped expression. The program checks that expressions emitted through `$` fit its declared inputs.

With both helpers in place, we can build different summaries from the same pieces. Replace the program with this factory, leaving the helpers above it:

```ts title="Choose the summary's fields" data-example="host-configuration"
const buildSummary = (includeRevision: boolean) =>
  Draft.program(inputs, ($, { task }) => {
    const fields = {
      title: task.title,
      attention: attentionFor($, task),
    };

    if (includeRevision) {
      return Program.Structural.struct({
        ...fields,
        nextRevision: $.prelude().add(task.revision, 1n),
      });
    }

    return Program.Structural.struct(fields);
  });

const built = buildSummary(true);
```

The two kinds of choice now work together. `includeRevision` determines the output fields during construction. The generated HashQL still contains the conditional that chooses `attention` from the task's fields at execution time.

These helpers reuse construction. They don't declare callable HashQL functions inside the generated program. For that, Draft needs [typed HashQL function construction](https://linear.app/hash/issue/BE-1015), which is not implemented yet.

### What the input schema promises

Our schema describes the names and types the program expects. It doesn't contain task data or parse incoming JavaScript values. `String`, `BigInt` and `Boolean` are type definitions here.

The returned expression's TypeScript type retains every declared schema entry as a requirement, including entries the callback doesn't use. [`Draft.Body.Requirements`](/docs/hashql/reference/hashql/Draft/Body#Requirements) describes that record. Use an empty schema, `{}`, for a program built entirely from constants and declarations that require no inputs.

## Decide where a binding belongs

So far, our TypeScript variables have held expressions. They haven't declared HashQL bindings. That distinction matters when we reuse a handle: reusing an expression inserts its syntax at each use, while reusing a binding inserts references to its name.

To see the difference, return to the first revision example. Replace its program with:

```ts title="Give the addition a HashQL name" data-example="query-binding"
const built = Draft.program(revisionInputs, ($, { revision }) => {
  const { add } = $.prelude();
  const nextRevision = $.let("nextRevision", add(revision, 1n));
  return nextRevision;
});
```

The same serialization block now produces:

```json title="Generated J-Expr with a binding" data-output="query-binding"
[
  "::kernel::special_form::let",
  "nextRevision",
  [
    "::core::math::add",
    ["::kernel::special_form::input", "revision", "::kernel::type::Integer"],
    { "#literal": 1 }
  ],
  "nextRevision"
]
```

The addition is the initializer of a `let`, and the body refers to `nextRevision`. Replacing the declaration with `const nextRevision = add(revision, 1n)` would give us the first example's output again: just the addition, with no HashQL binding.

The context places declarations around the returned expression in call order. This applies to `$.let`, `$.type`, `$.newtype` and `$.import`, including declarations whose returned handles we never use. Constructing an expression and then discarding its handle adds nothing by itself.

### Use the context of the body you mean

A helper that declares a binding needs to know where that binding belongs. Nested branch callbacks receive their own context for this purpose. Here is a small, separate program using the same imports:

```ts title="Keep a declaration inside its branch" data-example="branch-context"
const built = Draft.program({ review: Boolean }, ($, { review }) =>
  $.if(review, {
    then: (branch) => {
      const label = branch.let("label", "review");
      return label;
    },
    else: () => $.literal("clear"),
  }),
);
```

Its output puts the `let` inside the `then` branch's body:

```json title="Generated J-Expr with a branch-local binding" data-output="branch-context"
[
  "::kernel::special_form::if",
  ["::kernel::special_form::input", "review", "::kernel::type::Boolean"],
  ["::kernel::special_form::let", "label", { "#literal": "review" }, "label"],
  { "#literal": "clear" }
]
```

Calling the captured outer `$.let` instead would place the declaration outside the conditional. JavaScript nesting alone doesn't decide the HashQL scope: the context we call does. The same rule applies to declarations inside [query filters](/docs/hashql/troubleshooting#a-declaration-inside-my-filter-is-in-the-wrong-scope).

The `else` callback can use `$.literal` from the outer context because it only constructs a literal expression. There is no declaration to place. When passing a context into a helper that declares names, pass the branch or filter context if its declarations should stay there.

## Choose a composition style

The summary used context helpers to build its predicate. We used standalone operators when extracting that predicate into a helper. A **combinator** takes expressions and constructs another expression, so this work doesn't inherently need a declaration context. These three alternatives build the same predicate inside the task callback:

```ts title="Context helpers" tab="Context" tab-group="draft-composition" data-example="context-composition"
const needsReview = $.eq(task.blocked, true).and($.not(task.done));
```

```ts title="Standalone chaining" tab="Fluent" tab-group="draft-composition" data-example="fluent-composition"
const { Operators } = Program;
const needsReview = Operators.eq(task.blocked, true).and(
  Operators.not(task.done),
);
```

```ts title="Data-last composition" tab="Pipe" tab-group="draft-composition" data-example="pipe-composition"
const { Operators } = Program;
const needsReview = pipe(
  task.blocked,
  Operators.eq(true),
  Operators.and(Operators.not(task.done)),
);
```

Choose the context form when already working with `$`, or the standalone form when a helper only needs expressions. A pipe can make a longer sequence of transformations easier to read. All three forms retain the operands' input requirements. `pipe` runs these TypeScript functions during construction, as the direct calls do.

### Why some Boolean expressions have fluent methods

Both `$.prelude().eq(task.blocked, true)` and `$.eq(task.blocked, true)` emit a call to HashQL equality. The prelude's `eq` returns an ordinary Boolean expression. The operator builder returns a Boolean expression with `.and`, `.or` and `.not` methods. It also requires matching operand descriptors, while the current prelude declaration allows different descriptors.

Binding a predicate with `$.let` produces an ordinary Boolean reference too. To continue composing it, use a standalone operator. This can replace the predicate declaration in the task summary:

```ts title="Compose a bound predicate" data-example="bound-predicate"
const blocked = $.let("blocked", $.prelude().eq(task.blocked, true));
const needsReview = Program.Operators.and(blocked, $.not(task.done));
```

The fluent methods belong to the builder that supplies them, not to every expression whose HashQL type is Boolean.

## Share library declarations

We started with `add` from the built-in prelude. That prelude also includes primitive types, `List`, `Dict`, UUID-related declarations and equality. It is a small set of typed declarations. [Generated standard-library declarations](https://linear.app/hash/issue/BE-1013) will provide broader coverage.

The prelude exposes modules as well. Inside the task callback, these expressions address the same addition function:

```ts title="Use the prelude or its math module" data-example="prelude-views"
const throughPrelude = $.prelude().add(task.revision, 1n);
const throughModule = $.modules().math.add(task.revision, 1n);
```

An SDK module is a handle for a HashQL module. To emit a HashQL import, use [`$.import`](/docs/hashql/reference/hashql/Draft/Context#Context.import). For example, this can replace the prelude lookup in the task summary:

```ts title="Import addition under a local name" data-example="module-import"
const { sum } = $.import($.modules().math, { add: "sum" });
const add = sum;
```

The emitted import names the function `sum`. The TypeScript variable `add` lets the rest of our callback continue using its existing spelling. Neither operation renames the original function: `$.prelude()` still has `add`. Omit the selection to import all exports, or pass a name array to select exports without renaming them.

### Give several programs the same prelude

[`Draft.withPrelude`](/docs/hashql/reference/hashql/Draft#withPrelude) creates a program constructor with your chosen declarations. This separate example reuses the existing addition handle under the host-side name `incrementBy`:

```ts title="Choose a small prelude" data-example="custom-prelude"
const { program: reviewProgram } = Draft.withPrelude({
  values: { incrementBy: Program.Prelude.builtin.values.add },
});

const customBuilt = reviewProgram({ revision: BigInt }, ($, { revision }) => {
  const { incrementBy } = $.prelude();
  return incrementBy(revision, 1n);
});
```

`incrementBy` still refers to `::core::math::add`. The property name chooses how our TypeScript code accesses the handle. No import or new HashQL function is emitted.

The custom prelude **replaces** the built-in one. Its `$.prelude()` has `incrementBy`, not the usual `add`, `Uuid` or `Integer` entries. The context still provides `$.let`, `$.literal` and its other construction operations. `withPrelude` copies the supplied export records when called, so changing those records later doesn't change the constructor.

For declarations not already in the built-in prelude, [`Program.Module.define`](/docs/hashql/reference/hashql/Program/Module#define) describes a module's exports and paths. The SDK trusts those signatures. The functions themselves must exist where the declarations say they do: describing them neither implements them nor validates their server-side definitions.

## Work with typed accessors

The task examples use `task.title` to construct field access. An [expression handle](/docs/hashql/reference/hashql/Program/Expression#Expression) carries the HashQL type it represents and the inputs it requires. That type determines which projections, indexing operations and function calls TypeScript offers.

Inside the task callback, these two forms construct the same access:

```ts title="Project the same field two ways" data-example="accessors"
const title = task.title;
const explicitTitle = task.$project("title");
```

`$project` is useful when a field's name collides with a handle operation, such as a real struct field named `$index`. Tuple handles similarly support fixed positions and `$project`.

Lists and dictionaries use `$index` for a computed position or key. This separate program looks up a title at an Integer position:

```ts title="Construct a list lookup" data-example="indexing"
const indexed = Draft.program(
  { titles: Program.Prelude.builtin.types.List(String), position: BigInt },
  (_, { titles, position }) => titles.$index(position),
);
```

<Callout title="An index can be absent">
  HashQL's language-level result is an Option. The current SDK describes the
  result with a nullable descriptor instead. This example demonstrates lookup
  construction only, not how to consume its result. The [language
  introduction](/docs/hashql/intro#looking-up-an-element-with-index) explains
  the intended semantics.
</Callout>

When a descriptor cannot establish an access, `$projectUnsafe` and `$indexUnsafe` return expressions with an unknown descriptor and leave validity to the HashQL compiler. [`Program.Expression.assume`](/docs/hashql/reference/hashql/Program/Expression#assume) can supply an assumed descriptor, but it doesn't validate the value or emit a HashQL `as` assertion. Prefer the typed accessors when the structure is known.

## Declare types in a constructed body

The context can declare types alongside values. This separate program gives a task title a nominal `TaskTitle` type and returns a value made by its constructor:

```ts title="Declare and construct a nominal type" data-example="nominal-type"
const named = Draft.program({}, ($) => {
  const TaskTitle = $.newtype("TaskTitle", String);
  const title = $.let("title", TaskTitle("Update the API reference"));
  return title;
});
```

`TaskTitle` is one handle with two roles: a type expression and a callable constructor. `$.type` instead declares a structural alias and returns its type expression. As with value bindings, the context determines where these declarations belong.

`Program.Structural` constructs struct, tuple, list and dictionary values. A plain JavaScript record is not itself an expression that today's `$.let` accepts. Use the structural constructor first, as we did when returning the task summary.

## Take the construction tools into a query

[Writing a HashQL query](/docs/hashql/writing-a-query) applies these tools to a graph. `$.query.entities(axis)` starts a query builder, `.filter(...)` constructs a predicate with a fresh context, and `.collect()` describes a list result. The same expression, scope and input relationships apply there.

Use the [API reference](/docs/hashql/reference/hashql/Draft) for individual signatures and [troubleshooting](/docs/hashql/troubleshooting) when construction or execution fails.
