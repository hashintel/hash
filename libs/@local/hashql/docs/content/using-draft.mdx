How do we author HashQL programs in TypeScript? The HashQL SDK provides three layers of abstraction, each building on the previous one. The higher-level APIs help us catch errors before our programs reach the server.

<Mermaid
  chart="
graph LR
    jexpr[J-Expr] --> program[Program]
    program --> draft[Draft]
"
/>

J-Expr is the transport syntax used between the SDK and the server. The [`J-Expr`] API builds expressions in this syntax without checking their HashQL types. [`Program`] builds on J-Expr with a purely functional interface over a typed expression tree. [`Draft`] provides a more convenient imperative interface for constructing programs from those expressions.

The distinction between [`Program`] and [`Draft`] is analogous to writing [Redux] reducers with and without [Immer]. Without [Immer], reducers explicitly construct the next state without mutating the previous one, often using spread syntax to copy the affected objects. [Immer] gives us a mutable representation of that state, called a _draft_, and records our changes to produce the next immutable state. HashQL's [`Draft`] follows the same idea: we write declarations in order, and it assembles the expression tree for us. That's where the name comes from.

The lower-level [`Program`] and [`J-Expr`] APIs are considered unstable, so we'll focus on [`Draft`] for program construction. We'll still use [`Program`]'s expression helpers and serialisation where needed.

## Getting started

The HashQL SDK makes extensive use of the excellent [effect] library and therefore adopts some of its conventions and idioms. However, you don't need to be familiar with [effect] itself to use the SDK.

To get started, import the SDK:

```ts
import * as Draft from "@local/hashql/Draft";
```

You can also import individual symbols. Most commonly, you'll want to import [`program`][draft-program], the function we'll use to create a [`J-Expr`] program that can then be sent to the server.

```ts
import { program } from "@local/hashql/Draft";
```

## Building our first J-Expr program

The primary entry point for building a J-Expr program is the [`program`][draft-program] function. It takes two arguments: a definition of the program's inputs and a closure that constructs the program. We define the input names and types here, then supply their values when we send the program to the server for execution.

The closure itself takes two arguments: the [construction context][draft-context] (conventionally called `$`) and an object containing handles that represent the program inputs. Any behaviour outside [`Program`], such as scope management, is handled through `$`. Expect to use it often—hence the short name.

Suppose we want to build a simple program that increments a task's revision number. The prelude provides `add`, the HashQL equivalent of the `+` operator. We'll define the inputs first, then construct the program using a closure:

```ts title="revision.ts" data-example="revision"
import { Program } from "@local/hashql";
import * as Draft from "@local/hashql/Draft";
import { Result, pipe } from "effect";

const revisionInputs = { revision: BigInt };

const built = Draft.program(revisionInputs, ($, { revision }) => {
  const { add } = $.prelude();
  return add(revision, 1n);
});
```

You can also inline the input definitions directly into the `program` call. In this example, we define them separately for clarity. The closure receives a handle for each declared input in its second argument, an object keyed by input name. We destructure this object to access `revision` within the closure. Importantly, `revision`, like any input handle, does not hold a value supplied during program construction. Instead, it acts as a proxy for a value supplied when the program runs on the server.

The HashQL SDK aims to be as user-friendly as possible and supports both explicit types and common JavaScript type constructors. In our example, `BigInt` maps to [`Program.Prelude.builtin.types.Integer`][builtin-prelude], which we could use instead.

[`Draft.program`][draft-program] evaluates the closure immediately and returns a [`Result`]. A result has two variants: [`Success`] (also known as `Ok`) and [`Failure`] (also known as `Err`), representing the outcome of the evaluation. For [`Draft.program`], a successful result contains an [`Expression`], while a failed result contains a construction failure.

Importantly, the expression is not yet a standalone [`Program`]. It can be used within other HashQL programs as a reusable fragment. Calling [`Program.program`] turns the expression into a [`Program`], which can then be compiled into the underlying J-Expr JSON representation using [`Program.compile`]. This function also returns a [`Result`], containing either the serialised JSON or a compilation failure.

To serialise our expression, we use [`Result.map`] for [`Program.program`] because it returns a plain value. [`Program.compile`] returns another [`Result`], so we use [`Result.flatMap`] for that step. We finish with [`Result.getOrThrow`] to return the JSON string or throw if construction or serialisation failed. In an Effect workflow, we can instead use [`Effect.fromResult`] to handle the result as a typed effect.

```ts title="Serialize the program" data-example="serialize"
const serialized = pipe(
  built,
  Result.map(Program.program),
  Result.flatMap(Program.compile),
  Result.getOrThrow,
);

console.log(serialized);
// => ["::core::math::add",["::kernel::special_form::input","revision","::kernel::type::Integer"],{"#literal":1}]
```

### Handle construction failures

[`program`][draft-program] catches exceptions raised during program construction rather than propagating them, returning a [`Result`] value to the caller. In this respect, it is similar to [`Result.try`]. This allows it to bridge naturally between [effect] and native JavaScript with minimal friction.

Construction and serialisation can also fail for other reasons, such as an invalid binding name or a reference used outside its scope. These failures are also returned explicitly through a [`Result`] value rather than thrown as exceptions. Each construction failure is represented by a distinct, well-typed case in [`ProgramError.Construction`], allowing for structured error handling.

### Choose declarations from the prelude

The prelude is a set of symbols, such as [`add`][builtin-prelude], that are automatically imported and available in every J-Expr program. It is controlled by the server, not the program itself, and therefore does not change between invocations. The full list of prelude symbols is available in the [`Program.Prelude`][builtin-prelude] reference.

Advanced users can override the default prelude declarations using the [`Draft.withPrelude`] function. Note, however, that this function **does not** modify the prelude loaded by the server during execution. The supplied declarations must match the corresponding server definitions, or the SDK may accept a call that the server rejects.

## Detour: Using HashQL logic and TypeScript logic together

You can mix HashQL logic and TypeScript logic in the same program, but only the HashQL expression ultimately returned from [`Draft.program`][draft-program] is executed on the server. This allows us to model concepts such as macros and construction-time functions or conditionals (similar to `#ifdef` in C/C++ or feature flags in Rust).

Suppose we want to make incrementing the revision optional. There are two ways to do this:

```ts
const maybeIncrement = Draft.program(
  { revision: BigInt, enabled: Boolean },
  ($, { revision, enabled }) => {
    const { add } = $.prelude();

    return $.if(enabled, {
      then: () => add(revision, 1n),
      else: () => revision,
    });
  },
);
```

Just like normal HashQL programs, each branch given is evaluated during construction of the HashQL program, and the selection of the branch taken is done on the server.

This approach is self-contained: the program declares both inputs it needs. However, the caller must supply both inputs on every call. This is the preferred approach, but sometimes, we want to make this decision when constructing the expression instead. We can do this by moving the conditional out of the HashQL program and into the TypeScript construction logic. This is where construction-time conditionals come in.

```ts
const buildProgram = (enabled: boolean) =>
  Draft.program({ revision: BigInt }, ($, { revision }) => {
    const { add } = $.prelude();

    if (enabled) {
      return add(revision, 1n);
    } else {
      return revision;
    }
  });
```

What is different here is that the conditional is absent from the output that is ultimately sent to the server, and depends on the value of `enabled` supplied by the caller. Let's define our serialisation pipeline we used earlier as a helper and compare the outputs of the two approaches:

```ts
import type { Type } from "@local/hashql";

const compile = <T extends Type.Any, I, E>(
  built: Result.Result<Program.Expression.Expression<T, I>, E>,
) =>
  pipe(
    built,
    Result.map(Program.program),
    Result.flatMap(Program.compile),
    Result.getOrThrow,
  );

console.log(compile(maybeIncrement));
// => ["::kernel::special_form::if",["::kernel::special_form::input","enabled","::kernel::type::Boolean"],["::core::math::add",["::kernel::special_form::input","revision","::kernel::type::Integer"],{"#literal":1}],["::kernel::special_form::input","revision","::kernel::type::Integer"]]

console.log(compile(buildProgram(false)));
// => ["::kernel::special_form::input","revision","::kernel::type::Integer"]

console.log(compile(buildProgram(true)));
// => ["::core::math::add",["::kernel::special_form::input","revision","::kernel::type::Integer"],{"#literal":1}]
```

We can see that the conditional logic inside `Draft.program` changes the actual program sent to the server. As a rule of thumb, express as much logic as possible in HashQL. Use TypeScript control flow during construction when HashQL does not yet support the construct you need or when you need to make decisions based on configuration-time values.

The reason is simple: each program goes through a compilation step on the server. If a query remains unchanged, its compilation artefacts can be cached and reused. Keeping the decision as an input lets different calls reuse one compiled program. Making the decision during construction produces separate programs for the different configurations.

We can also use this technique to construct reusable fragments that act as macros:

```ts
const incrementTwice = Draft.program(revisionInputs, ($, { revision }) => {
  const { add } = $.prelude();
  const increment = (value: typeof revision) => add(value, 1n);

  return increment(increment(revision));
});

console.log(compile(incrementTwice));
// => ["::core::math::add",["::core::math::add",["::kernel::special_form::input","revision","::kernel::type::Integer"],{"#literal":1}],{"#literal":1}]
```

The helper takes the same kind of expression as `revision` and constructs an addition each time we call it. Calling it twice produces two nested HashQL additions. Remember that the TypeScript helper runs only during construction, so the server receives those additions rather than a call to `increment`.

## Assemble a task summary

For our task summary program, we need to express structured values, rather than just rely on a single integer. To make use of that we use [structs], which are similar to records in TypeScript. Our tasks should have a title, a revision and two flags: `blocked` and `done`.

We can construct this struct type with [`Program.Structural.type`], or inside of [`Draft.program`] using [`$.type`]:

```ts
const taskType = Program.Structural.type({
  title: String,
  revision: BigInt,
  blocked: Boolean,
  done: Boolean,
}).pipe(Result.getOrThrow);
```

The constructor returns a [`Result`], with a [`ProgramError.Construction`]. This error can happen when the identifier chosen for a field is not a valid HashQL identifier. For the purposes of our program we then [`Result.getOrThrow`] to unwrap the error. It is in general acceptable to do this for constant type expressions, but otherwise [`effect`] programs should make use of e.g. [`Effect.fromResult`] to handle errors.

The result is that `taskType` is now a [`TypeExpression`] (not an [`Expression`]!), which describes the struct type.

<Callout>
  Inputs also support [shorthand type definitions][structural-definitions], as
  we used for `revision` above.
</Callout>

We then use this type and pass it to the `task` input of `summarizeTask`. This does two changes: callers that consume this expression must now provide that shape, and the handle will now have the type that `taskType` described. Let's use it in our example:

```ts
const summarizeTask = Draft.program({ task: taskType }, ($, { task }) => {
  const { add } = $.prelude();

  return Program.Structural.struct({
    title: task.title,
    nextRevision: add(task.revision, 1n),
  });
});
```

[`Program.Structural.struct`] is the way that we create a struct value from the field expressions that we provide. HashQL operates in three "universes": modules, types, and values. Where [`Program.Structural.Type`] is the type version of the struct constructor, [`Program.Structural.struct`] is the value version. You can then use normal JavaScript field notation on these struct values to access their fields, which in turn returns an expression handle.

<Callout>

You are currently unable to destructure via the `..rest` operator, e.g. `const {...rest} = task` will break.

</Callout>

Now that we have a more structured way to access task fields, as well as construct algebraic data types (ADTs), we can extend our program, let's say that we introduce a new field `attention` that depends on the task's flags. We want blocked, unfinished tasks to receive the label `"review"`, and every other task to receive `"clear"`:

```ts title="Choose a label from the task's fields" data-example="summary-attention"
const summarizeTaskWithAttention = Draft.program(
  { task: taskType },
  ($, { task }) => {
    const { add } = $.prelude();
    const needsReview = $.eq(task.blocked, true).and($.not(task.done));
    const attention = $.if(needsReview, {
      then: () => $.literal("review"),
      else: () => $.literal("clear"),
    });

    return Program.Structural.struct({
      title: task.title,
      nextRevision: add(task.revision, 1n),
      attention,
    });
  },
);
```

To be able to increase the readability aspect, `$` does not only offer access to the modules, or the prelude, but also provides a set of helper functions for common operations. You can still use the full HashQL API from [`Program`], but the [`Draft.Context`] has a lot of helper functions made available for convenience, and enables you to write more readable HashQL programs through e.g. fluid predicate composition.

In our example `$.eq` maps to the HashQL function `::core::cmp::eq` and compares two values for equality. The interesting part is that it doesn't return just a `Boolean` value, but instead returns a [`Program.Operators.Boolean`], this means that you can create a chain of predicates using `.and`, `.or` and `.not`.

As said prior, you are not constrained by the SDK to just use the helper functions, an alternative way to write the same condition would be:

```ts title="Function calls and fluent predicates" data-example="predicate-comparison"
const { eq } = $.prelude();
const viaPrelude = $.and(eq(task.blocked, true), $.not(task.done));
const viaHelper = $.eq(task.blocked, true).and($.not(task.done));
```

At the end of the callback, both forms produce identical HashQL calls, `$` is simply a convenience wrapper that you can use to write more pleasant to read and maintain HashQL code. Use of `$` is considered idiomatic for the TypeScript SDK, and therefore recommended over the prelude imports, which is why we're going to continue using it in our examples.

It's important to make the distinction, that this function that we have created does currently not interact with the graph at all. To do so, we use graph effects, which are explained in more depth under the [writing a query] chapter.

## Naming parts of a program

Just like with control-flow which differentiates between runtime and construction-time, variables in a [`Draft`] differentiate between the two as well. What's important to keep in mind is that HashQL does no interpolation of the function definition, no integration into the bundling, etc. It is just using builders, and that also means that your conventional `const attention =` as in our example above is not part of the HashQL program itself. It is just a regular JavaScript variable that holds an expression handle. Any time that the variable is mentioned we don't mention the variable, but instead insert the expression that it stands for.

Let's see how that works in a smaller example:

```ts title="Reuse an expression" data-example="repeated-expression"
const repeatedRevision = Draft.program(revisionInputs, ($, { revision }) => {
  const nextRevision = $.prelude().add(revision, 1n);

  return Program.Structural.struct({
    nextRevision,
    auditRevision: nextRevision,
  });
});

console.log(compile(repeatedRevision));
// => {"#struct":{"nextRevision":["::core::math::add",["::kernel::special_form::input","revision","::kernel::type::Integer"],{"#literal":1}],"auditRevision":["::core::math::add",["::kernel::special_form::input","revision","::kernel::type::Integer"],{"#literal":1}]}}
```

As you can see, the expression is inserted twice, this is often good enough, as it makes it easy to have expressions "travel around", but there are sometimes cases where this is insufficient. For example when we have a computation that is very complex, that is shared across multiple parts of the program, or mentioned multiple times. HashQL supports the notion of `let` bindings (similar to `const` due to their immutability), which allows you to define a named expression.

Let's try it:

```ts title="Reuse a HashQL binding" data-example="named-expression"
const namedRevision = Draft.program(revisionInputs, ($, { revision }) => {
  const nextRevision = $.let("nextRevision", $.prelude().add(revision, 1n));

  return Program.Structural.struct({
    nextRevision,
    auditRevision: nextRevision,
  });
});

console.log(compile(namedRevision));
// => ["::kernel::special_form::let","nextRevision",["::core::math::add",["::kernel::special_form::input","revision","::kernel::type::Integer"],{"#literal":1}],{"#struct":{"nextRevision":"nextRevision","auditRevision":"nextRevision"}}]
```

You can see here that our `let` binding was actually inserted, and then referenced. This is how HashQL supports reuse of complex expressions across multiple parts of the program.

<Callout>

It is convention to name the binding the same as the `const` variable it is assigned to.

</Callout>

Anything that is mentioned _after_ the `let` binding is able to reference it naturally. What is important to note is that HashQL has the notion of shadowing (indeed due to it's immutable nature it is very common), but there is no inherent link between the binding name and the `const` variable it is assigned to. This means that it is very possible in a [`Draft`] program to create something like this:

```ts title="Reuse a HashQL binding" data-example="named-expression"
const namedRevision = Draft.program(revisionInputs, ($, { revision }) => {
  const nextRevision = $.let("nextRevision", $.prelude().add(revision, 1n));
  const nextRevision2 = $.let("nextRevision", "foo");

  return Program.Structural.struct({
    nextRevision,
    auditRevision: nextRevision,
  });
});
```

This will compile, but the type of `nextRevision` inside the struct we expect to be `Integer`, even though the one in scope (assigned to `nextRevision2`) is a `String`. This will not compile on the server, but is something that we can detect on the client. This is one of the reasons why HashQL returns a [`Result`] on construction: this is a construction time error and results in a [`ProgramError.Construction`] error. This is also why we recommend that the name of the binding is the same as the name of the variable in scope: this makes it easier to reason about the type of the binding and will lead to a compile error in TypeScript.

## Keep declarations in their intended scope

Our attention label uses two branch callbacks. So far, each has returned a literal, but a branch can also contain declarations. The branch callback receives its own context so we can put those declarations inside that branch.

For a small example, let's take the review decision as an input and declare a label only in the `then` branch:

```ts title="Declare a name inside a branch" data-example="branch-context"
const branchAttention = Draft.program({ review: Boolean }, ($, { review }) =>
  $.if(review, {
    then: (branch) => branch.let("label", "review"),
    else: () => $.literal("clear"),
  }),
);

console.log(compile(branchAttention));
// => ["::kernel::special_form::if",["::kernel::special_form::input","review","::kernel::type::Boolean"],["::kernel::special_form::let","label",{"#literal":"review"},"label"],{"#literal":"clear"}]
```

The generated `let` is inside the `then` expression. It is not enough for the JavaScript call to be written inside the branch callback: we must use the context of the HashQL body where the declaration belongs. Compare that with calling the captured outer `$`:

```ts title="Declare through the outer context" data-example="outer-context"
const outerAttention = Draft.program({ review: Boolean }, ($, { review }) =>
  $.if(review, {
    then: () => $.let("label", "review"),
    else: () => $.literal("clear"),
  }),
);

console.log(compile(outerAttention));
// => ["::kernel::special_form::let","label",{"#literal":"review"},["::kernel::special_form::if",["::kernel::special_form::input","review","::kernel::type::Boolean"],"label",{"#literal":"clear"}]]
```

This time, the `let` wraps the entire conditional. Both branch callbacks run during construction, as we saw in the detour, and this callback records its declaration in the outer context. The two examples deliberately put the name in different scopes. Use the branch's context when its declarations should stay inside that branch.

The outer `$.literal` in the `else` branch is fine: it constructs an expression without declaring a name. The context choice matters for declarations such as `$.let`, `$.type`, `$.newtype` and `$.import`, not for every helper accessed through `$`.

## Extract a helper with the types it needs

The review rule is useful beyond one summary. We already know that a TypeScript helper can construct a reusable expression. This time, the helper needs access to the task's fields, so we also need a type for its argument.

We can derive that type from our input definition with [`Draft.Body.Handles`]:

```ts title="Extract the review rule" data-example="expression-helper"
const taskInputs = { task: taskType };
type Task = Draft.Body.Handles<typeof taskInputs>["task"];

const needsReviewFor = (task: Task) =>
  Program.Operators.eq(task.blocked, true).and(
    Program.Operators.not(task.done),
  );
```

`Task` is the type of our input handle, not a TypeScript object containing task data. Deriving it from `taskInputs` keeps the helper's fields in step with the program's input definition. It also retains the requirement for an input named `task`.

The helper doesn't need a context because it only combines expressions. [`Program.Operators`] provides the same predicate constructors we used through `$`, including their fluent methods. These operations are **combinators**: they take expressions and return another expression. The helper can therefore work with just the task handle, without accepting a `$` it doesn't use.

### Pass a context when the helper declares a name

Suppose we want to extract construction of the attention label too, this time giving the label a HashQL binding. The helper needs a context for that declaration. [`Draft.Body.Context`] describes the context a program callback receives:

```ts title="Extract a helper that declares a binding" data-example="context-helper"
type TaskContext = Draft.Body.Context<
  Program.Prelude.Builtin,
  Draft.Body.Requirements<typeof taskInputs>
>;

const attentionFor = ($: TaskContext, task: Task) =>
  $.let(
    "attention",
    $.if(needsReviewFor(task), {
      then: () => $.literal("review"),
      else: () => $.literal("clear"),
    }),
  );
```

The first type argument describes the prelude, and the second describes the inputs the program permits. [`Draft.Body.Requirements`] derives those input requirements from our schema. This helper uses the same prelude and input schema as our task programs.

Calling a TypeScript helper doesn't create a new HashQL scope. `attentionFor` puts its binding in the context we pass to it and returns a reference to that binding. If we call it inside a branch and want the declaration to stay there, we pass that branch's context, just as we did with `branch.let`.

We can now assemble our summary using the extracted helpers:

```ts title="Build the summary from reusable pieces" data-example="reusable-summary"
const reusableSummary = Draft.program(taskInputs, ($, { task }) => {
  const attention = attentionFor($, task);

  return Program.Structural.struct({
    title: task.title,
    nextRevision: $.prelude().add(task.revision, 1n),
    attention,
  });
});
```

## Take these pieces into a query

We can now construct expressions, give them names in the intended scope, and extract helpers whose types retain their input requirements. [Writing a HashQL query](/docs/hashql/writing-a-query) applies these tools to graph data. A query filter receives its own construction context, so a helper that declares names follows the same rule there as it does inside a branch.

The reference covers construction tools we haven't needed for this summary:

- [`Program.Structural`] describes tuple, list and dictionary construction alongside structs. Arrays in structural shorthand describe tuples, while lists and dictionaries use explicit constructors.
- [`Program.Expression`] describes typed field projection and indexing. Use `$project` when a field name collides with a handle operation, such as a struct field named `$index`.
- [`Draft.withPrelude`] supplies a different set of SDK declarations. It replaces the built-in prelude for that constructor, not the definitions on the server. Reusing a built-in declaration under a different property name changes how TypeScript accesses it, not the HashQL function it calls.
- [`Draft.Context`] also provides `$.type` for a structural alias and `$.newtype` for a nominal type and its constructor. These declarations belong to the context where we make them, just like `$.let`.

For construction errors and scope mistakes, [troubleshooting](/docs/hashql/troubleshooting) gives examples of the failure and its correction.
