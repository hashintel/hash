A Draft program passes through more than one checker. An error in your editor, a construction failure and an error returned by the HashQL runtime tell you different things. Start with the stage that actually failed.

| What you see                                  | What has run                             | What to inspect                                                            |
| --------------------------------------------- | ---------------------------------------- | -------------------------------------------------------------------------- |
| A TypeScript diagnostic                       | The host-language type checker           | Argument types, input declarations and expression handles                  |
| A failed `Result` from Draft or serialization | The SDK's construction and syntax checks | The construction error and the scope of referenced bindings                |
| An error from the HashQL execution interface  | The server's compiler or runtime         | The submitted program, input values, graph schema and execution diagnostic |
| A valid but unexpected result                 | The execution path                       | Predicate meaning, temporal selection and the expected data                |

A pass at one stage is not a pass at the next. In particular, [`Program.compile`](/docs/hashql/reference/hashql/Program#compile) serializes J-Expr. It does not send the query to a server.

## Handle a construction failure

Keep the result of construction and serialization until the place where your application decides how to report a failure:

```ts data-example="construction-result"
import { Program } from "@local/hashql";
import * as Draft from "@local/hashql/Draft";
import { Result } from "effect";

const draft = Draft.program({}, ($) => {
  const count = $.let("count", 2n);
  return count;
});

const serialized = Result.flatMap(
  Result.map(draft, Program.program),
  Program.compile,
);

const message = Result.match(serialized, {
  onSuccess: (text) => `Constructed program: ${text}`,
  onFailure: (error) => `Construction failed: ${error.reason._tag}`,
});

console.log(message);
```

The example prints the constructed program. If you change the binding name to `"not a name"`, it takes the failure branch instead. The [construction error reference](/docs/hashql/reference/hashql/Program/ProgramError#Construction) describes the reasons and their associated information. The short tag above is useful for this demonstration, but an application's diagnostic can retain the complete error.

Do not assume a callback returning normally means that construction succeeded. Draft can retain a failure on an expression until the program is serialized. Likewise, a `try`/`catch` around your callback is not a replacement for handling its returned `Result`.

## My condition has the wrong type

A HashQL condition must produce a Boolean. It does not use JavaScript's truthiness rules:

```ts data-example="invalid-condition"
import * as Draft from "@local/hashql/Draft";

Draft.program({}, ($) =>
  // @ts-expect-error HashQL requires a Boolean condition.
  $.if(2n, {
    then: () => "selected",
    else: () => "not selected",
  }),
);
```

The `@ts-expect-error` marks a deliberately rejected example. Replace `2n` with a Boolean expression such as `$.eq(2n, 2n)` to construct the conditional.

The same distinction applies when choosing literals. A JavaScript `bigint`, written `2n`, represents a HashQL Integer. A JavaScript `number`, written `2`, has the SDK's Number descriptor. Choose the host value that expresses the type you mean rather than adding assertions until TypeScript stops complaining.

## My TypeScript `if` always takes the same branch

An expression handle is a JavaScript object. A TypeScript `if` tests that object now, while the program is being built. It does not inspect the value that the HashQL expression will produce later.

Use host-language branching to choose **which program to construct**. Use [`$.if`](/docs/hashql/reference/hashql/Draft/Context#Context.if) to put a conditional **inside the constructed program**.

```ts data-example="hashql-condition"
import * as Draft from "@local/hashql/Draft";

const program = Draft.program({ enabled: Boolean }, ($, { enabled }) =>
  $.if(enabled, {
    then: () => "enabled",
    else: () => "disabled",
  }),
);
```

Both branch callbacks run during construction. Only the selected HashQL branch evaluates when the resulting program runs. Keep network requests, logging you expect per execution, and other host-side work out of these callbacks unless you deliberately want it to happen during construction.

## Serialization reports a stale reference

A handle remembers which binding it refers to. Reusing a name can make that handle point at a binding that is no longer visible:

```ts data-example="stale-reference"
import { Program } from "@local/hashql";
import * as Draft from "@local/hashql/Draft";
import { Result } from "effect";

const draft = Draft.program({}, ($) => {
  const first = $.let("count", 1n);
  $.let("count", 2n);
  return first;
});

const serialized = Result.flatMap(
  Result.map(draft, Program.program),
  Program.compile,
);
```

`serialized` is a failure with the `StaleReference` reason. At the final reference, the HashQL name `count` denotes the second binding, not the first one the handle recorded.

Give the bindings distinct names if both must remain available. If you meant to return the new value, retain and return the second handle instead. The same problem can occur when a handle escapes its branch or program, or when a filter parameter shadows a name from the enclosing scope.

## A declaration inside my filter is in the wrong scope

Use the context supplied to the filter callback for declarations that depend on its parameter:

```ts title="Inside a query filter"
.filter("task", (predicate, task) => {
  const status = predicate.let("status", taskFields(task).status);
  return predicate.ne(status, "done");
})
```

This fragment belongs to the [release-briefing query](/docs/hashql/writing-a-query#turn-the-list-into-a-briefing), where `taskFields` is defined. Calling the outer `$.let` instead would put the declaration outside the filter's closure, where `task` is not in scope. A callback's lexical access to the outer JavaScript variable does not change where that context emits its HashQL declarations.

## My entity doesn't expose the fields I expected

The built-in SDK entity descriptor currently describes its fields as unknown. This is not a claim that the stored entity has no properties. It means the SDK lacks the declaration needed to give those accesses their precise TypeScript types.

The [worked guide's setup](/docs/hashql/writing-a-query#set-up-the-example) makes its fixture assumptions explicit. In a real application, declarations must match the actual entity schema and the query must select appropriate entities. [`assume`](/docs/hashql/reference/hashql/Program/Expression#assume) is a trusted declaration, not a data validator and not the language's checked `as` operation.

Generated standard-library declarations are tracked in [BE-1013](https://linear.app/hash/issue/BE-1013/generate-sdk-module-declarations-from-the-hashql-standard-library). Application-specific property types still need their own source of truth.

## A language feature has no Draft method

The language and its construction APIs have different coverage. A feature described by the [language introduction](/docs/hashql/intro) is not necessarily available as a dedicated Draft builder yet.

For example, general HashQL function construction is tracked in [BE-1015](https://linear.app/hash/issue/BE-1015/build-typed-hashql-functions-in-draft). Query filters already construct the specific closures their predicates need. That does not imply that Draft can build an arbitrary standalone function.

Draft has no dedicated `as` builder today. An annotation on `$.let` annotates a binding. `assume` changes an SDK descriptor. Neither should be presented as the missing Draft operation. The lower-level [J-Expr API](/docs/hashql/reference/hashql/JExpr) has a different construction contract.

## The program serializes, but the server rejects it

Keep the generated J-Expr, the input names and their declared types, and the server's diagnostic together. Check that named functions and types exist in the execution environment, that input values match their declarations, and that the query's property accesses match the selected graph data.

Declarations made through `Program.Module` or `TypeExpression` can refer to names that the server does not provide. Serialization does not check server availability. Do not fix a missing server declaration by changing only a TypeScript type assertion.

For a small reproduction, remove one query step at a time while preserving the failing expression and its inputs. The first checkpoint of the [worked guide](/docs/hashql/writing-a-query#start-with-the-tasks) is a useful shape: one graph source and one collection operation.

## The result is empty, incomplete or in an unexpected order

First check the release input and temporal view. An entity outside the selected time slice cannot appear merely because its properties match. Check visibility with the identity under which the query actually executes too.

Then inspect each predicate separately. A blocked task may also be unassigned, so independent lists can overlap. A name in the result may be a display label rather than a stable identity. Finally, do not infer an ordering from one observed result when the program requested none.

The [release fixture](/docs/hashql/writing-a-query#the-question-and-the-data) gives you a small set whose expected membership you can calculate by hand. It is a check on the question you meant to ask, not proof that an execution environment contains the same data.
