The event simulation worker advances one run and posts the events it records.
The editor's Quick Simulation runs in it. `messages.ts` in this folder defines
every message, `event-simulation.worker.ts` is the worker's end, and
`createEventSimulation` in `../runtime.ts` is the host's end. The shape
follows the [frame worker's protocol](doc:core.simulation.worker/protocol)
with time in place of frame counts: the host demands a time where that
protocol acknowledges frames.

A time is in the unit of the run's clock: simulated seconds for a timed net,
steps for an untimed one. `clock` of the `EventSimulation` handle says which.

## Messages

**Host to worker**, the type `ToEventWorkerMessage`:

| Type     | Payload                                                                                                    | Effect                                                                                                                                                  |
| -------- | ---------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `init`   | `sdcpn`, `extensions`, `initialMarking`, `parameterValues`, `seed`, `maxTime`, `hirArtifacts`, `simulator` | Builds the stepper of the selected simulator and a trace recorder over it, posts `events` with the initial event, then `ready`. Resets the demand to 0. |
| `start`  | none                                                                                                       | Starts the compute loop. Ignored while the loop runs and after `complete` or `error`. Answered with `error` when nothing is initialized.                |
| `pause`  | none                                                                                                       | Stops the loop, posts what is pending as `events`, then `paused`. The run and its trace recorder stay.                                                  |
| `stop`   | none                                                                                                       | Discards the run. A later `start` is answered with `error`.                                                                                             |
| `demand` | `time`                                                                                                     | Sets the time the worker may compute to. The latest demand stands, a lower one included.                                                                |

**Worker to host**, the type `ToEventMainMessage`:

| Type       | Payload                 | What the host does with it                                                                                       |
| ---------- | ----------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `ready`    | none                    | Sets the status to `Ready` and resolves the promise of `createEventSimulation`.                                  |
| `events`   | `events`, `coveredTime` | Appends the events to the trace store and publishes `eventCount`, `coveredTime` and the latest event in `trace`. |
| `paused`   | `time`                  | Sets the status to `Paused`.                                                                                     |
| `complete` | `reason`, `time`        | Sets the status to `Complete` and emits the reason, `deadlock` or `maxTime`, on the handle's `events` stream.    |
| `error`    | `message`, `itemId`     | Sets the status to `Error` and emits it. Before `ready` it also rejects the promise and disposes the handle.     |

`events` may be empty: `coveredTime` then says the worker advanced through a
stretch in which nothing fired. `itemId` names the SDCPN item an error of
`init` blames, where the thrown error carries one, and is `null` for an error
of the loop.

An event is a `TraceEvent` of `../trace.ts`: its index, its time, its kind
(`initial`, `firing` or `reference`), the transitions that fired, the state as
a frame buffer, and the derivative of every token of a place with dynamics.
The string pool of the run stays in the worker, so an event carries the
strings interned since the event before it as `newStrings`, and the trace
store applies them in order.

The last batch leaves before `complete`: the loop flushes what is pending and
then posts the message that ends the run. A host that stops listening on
`complete` has every event.

## Demand by time

The worker computes nothing past the latest demand. `computeLoop` in
`event-simulation.worker.ts` reads `demandedTime` before every slice of work:

```js
while (isRunning) {
  if (recorder.time >= demandedTime) {
    flushIfDue(false);
    await delay(10); // wait for a demand
    continue;
  }
  // advance until the batch is full, the demand is met or the slice is over
  flushIfDue(stopped);
  if (stopped) return; // after posting `complete` or `error`
  await delay(0); // let pause, stop and demand in
}
```

- After `init` the demand is 0, so a started worker waits until the first
  `demand`. Starting a run is two steps, `start` and a `demand`.
- The demand bounds the loop, and an advance is never cut short to meet it. A
  stepper that draws random numbers per span has to take the same spans
  whenever it is asked, so the last advance may carry the run past the demand.
- A lower demand does not rewind: what is computed stays, and the worker
  waits. The test in `event-simulation.worker.test.ts` holds both points.
- One slice of advances lasts at most `COMPUTE_SLICE_MS`, 12 ms. The loop then
  yields, so a `pause` or a new `demand` is read within that time.

In the editor, `EventPlaybackProvider` of
[event playback](layer:react.event-playback) sends the demands. Its target is
the viewed time plus the lead of the play mode, from `EVENT_PLAY_MODE_LEAD`
in [playback](layer:core.playback):

| Play mode       | Lead              | Demand                                                                                   |
| --------------- | ----------------- | ---------------------------------------------------------------------------------------- |
| `viewOnly`      | none              | Never sent: the trace is viewed as far as it is computed.                                |
| `computeBuffer` | 2                 | Sent again once the target has moved by a sixtieth of a unit.                            |
| `computeMax`    | positive infinity | Sent with every change of the playback state: the worker computes to the end of the run. |

A change of mode sends a demand afresh. That takes the worker's target back
down when the mode leaves `computeMax`.

## When a batch leaves

The worker collects advances and events and posts them as one `events`
message. `shouldFlush` in `flush-policy.ts` decides when:

| A batch leaves when                                           | Constant            | Reason                                                                                        |
| ------------------------------------------------------------- | ------------------- | --------------------------------------------------------------------------------------------- |
| It holds 2,000 advances                                       | `FLUSH_ADVANCES`    | That many advances are worth a message, with or without an event among them.                  |
| It holds 256 events                                           | `FLUSH_EVENTS`      | A burst of firings streams and does not arrive as one large message.                          |
| It holds an advance and 100 ms have passed since the last one | `FLUSH_INTERVAL_MS` | A worker that keeps up with a demand that rises every frame would otherwise post every frame. |
| The run stops, by completion or by an error                   | none                | The host has every event before it hears that the run is over.                                |

`pause` flushes whatever is pending without asking the policy. Each post makes
the host's stores publish and their readers render, so the interval bounds
the host's work per second while the worker keeps up with playback.
`flush-policy.test.ts` holds the four rows.

## Lifecycle

The handle's `status` store holds the host's state:

```text
Initializing ──ready──▶ Ready ──run()──▶ Running ──paused──▶ Paused
                                    ▲                    │
                                    └────── run() ───────┘
                          Running ──complete──▶ Complete
                          any     ──error─────▶ Error
```

`run()` sets `Running` and sends `start` without waiting for the worker. The
worker keeps a smaller status of its own, in which `complete` and `error` are
final: a `start` after either is ignored, and the host's `Running` would then
name a run the worker no longer advances. The editor does not call `run()` on
such a run: `EventPlaybackProvider` holds the play mode at `viewOnly` once
the status is `Complete` or `Error`.

`dispose()` sends `stop` and terminates the transport. An abort of the
`signal` given to `createEventSimulation` disposes the handle, and rejects the
promise with an `AbortError` when it comes before `ready`.

A `start` that follows a `pause` starts a new loop. Each loop has a number,
and a loop that wakes from a wait to find a newer one stops, so two loops
never advance one recorder.

## What the host's end does

`createEventSimulation` does four things around the messages:

- **Prepares the net.** It removes what the disabled extensions cover and
  sends that net in `init`. It flattens the component instances for the trace
  store only, so the store's frame layout matches the one the worker builds
  after flattening.
- **Queues until the worker boots.** `createWorkerTransport` in
  `../../worker-transport.ts` holds the messages sent before the worker
  exists. A test passes a `transport` in place of `createWorker`.
- **Keeps every event.** `createInMemoryEventTraceStore` in
  `../trace-store.ts` refuses an event whose index is not the next one, and a
  string delta whose base is not the size of its pool.
- **Publishes.** `status` and `trace` are stores and `events` is a stream, as
  [the store block](layer:core.store) defines them.

[The life of a run](doc:react.simulation/simulation-session) describes how the
React layer starts a run on this runtime and reads the state at the viewed
time.
