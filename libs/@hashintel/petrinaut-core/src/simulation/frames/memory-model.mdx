A frame is the state of a net at one point of a run: the token count of each
place, the timer and the firing count of each transition, and the tokens.
Everything the simulation computes is stored in raw `ArrayBuffer`s read through
typed-array views. There is no object graph of tokens: tokens are packed structs,
decoded to JavaScript objects only at the read boundary.

## The frame format

One `ArrayBuffer` per frame, read through section-typed views. The frame stores
**no IDs and no time**: decoding requires the layout derived from the SDCPN
(place and transition order, per-place stride and field layout), and time travels
beside the buffer, as the `time` of the event that carries it.

`createEngineFrame()` computes every offset and is the only frame constructor;
`readEngineFrame()` recreates the same views for reading. Both are in
`internal-frame.ts`.

The frame is internal to Core: it is no public API and no stable storage
format, and it can only be read with the layout of the net it was built for.
The layout of each colour's token comes from `tokens/token-layout.ts` in
[the token values block](layer:core.tokens).

Header fields worth knowing: `magic` (`0x5046524d`, a corrupt-frame guard),
`version` (currently `2`, asserted on decode), `placeCount`/`transitionCount`
(checked against the layout on read), and `byteLength` (checked on read).

### Token packing

Each coloured place owns a contiguous run of $\mathit{count} \times \mathit{strideBytes}$ starting at
its byte offset, giving $O(1)$ access to any place. Uncoloured places have stride
0 and only a count.

| Element type | Physical                  | Notes                                                                                                                                                         |
| ------------ | ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `real`       | `f64`, 8 B                |                                                                                                                                                               |
| `integer`    | `f64`, 8 B, rounded       | Exact within $\pm 2^{53}$. `i32` was rejected for silent wraparound; `i64` because bigint is contagious into user code.                                       |
| `boolean`    | `u8`, 1 B                 | Not bit-packed: that would break byte-granular copies for marginal savings.                                                                                   |
| `uuid`       | `u64 × 2`, 16 B           | Two little-endian lanes via a shared `BigUint64Array`, combined to one `bigint` at the boundary. Never routed through `number`.                               |
| `string`     | `u64` pool reference, 8 B | The frame stores an ID into an append-only per-run intern pool. The pool lives on the instance, not the frame, so frames stay fixed-stride and byte-copyable. |

Fields are ordered per colour by decreasing alignment, and the stride is rounded
up to 8 bytes. One module owns all token-byte indexing; every whole-token move is
a byte-range copy.

The playground below runs the engine's own codec on one token. Change a type or
a value and read the layout, the padding and the bits it produces: an `integer`
written as `2.7` reads back as `3`, and a `string` leaves only its pool ID in the
bytes.

## Reading a frame

A host reads a frame through a `SimulationFrameReader` of `../api.ts`. An
[execution trace](layer:core.execution-trace) returns one, for a run and for
an execution a host reports alike: `getEventState(index)` for the state an
event recorded, and `getStateAt(time)` for the state at any time the trace
covers.

Inside Core, `compileSimulationFrameReader` in `frame-reader.ts` derives the
layout from the net once and returns the function that wraps one frame:

```ts
const createReader = compileSimulationFrameReader(sdcpn, stringPool);
const reader = createReader(engineFrame, frameNumber, frameTime);
```

A reader holds typed-array views over the buffer and copies nothing.
`getPlaceTokenCount` reads the count of one place, `getPlaceTokens` builds
`TokenRecord`s when it is called, and `getRawView` hands the views to a
compiled metric.

A `string` field holds an ID, so a reader decodes it with the string pool of
the run. That pool stays in the worker that computes the run. Each event of a
trace carries the strings interned since the event before it as `newStrings`,
and the trace store applies them in order to a copy of the pool, which it
gives its readers.

| ------------------ | ----------------------------------------------------------------- | --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| SDCPN document     | Plain JS objects (editor state)                                   | Main                                                                        | Structured-cloned into the worker at `init`. Later edits do not reach a run.                     |

| Run buffers        | 2 × `MonteCarloFrameBuffer` per run                               | The worker of the run, or the calling thread of an experiment in local mode | Current and next, for the whole run. No message carries them.                                    |
| Frame of an event  | `ArrayBuffer`: a 64-byte header, typed sections and packed tokens | Event worker → Main                                                         | Copied out of the current run buffer when a state is recorded. Kept by the trace store.          |
| Interpolated frame | A copy of an event's frame                                        | Main                                                                        | Made by `getStateAt` for a time after the event, in a net with dynamics. Its reader owns it.     |
| Metric aggregates  | Accumulator states per sample                                     | Monte Carlo → Main                                                          | Posted as `metricFrames`. No frame of a run goes with them.                                      |
| Compiled user code | Versioned HIR buffer programs                                     | With the run buffers                                                        | Instantiated when a run is built, once per run, from the artifacts the language worker compiled. |

A run buffer is no frame of the format above. It has no header, and its token
region has spare capacity so that a step can add tokens without a new
allocation. Its token bytes have the same packing.

**A run of the event trace** advances in the two buffers of
`../monte-carlo/run-state.ts`. When its stepper stops at a state worth
keeping, `engineFrameFromRunFrame` in `../event-trace/worker/run-frame.ts`
copies the current buffer into a frame, and the worker posts it in the next
`events` message. The message is structured-cloned, and the worker drops its
copy after the post. The trace store in `../event-trace/trace-store.ts` keeps
every event for the life of the run's handle, so its size grows with the
number of states the stepper records.

**A run of an experiment** keeps its two buffers and no frame besides them.
`createMonteCarloFrameReader` in `../monte-carlo/frame-reader.ts` reads the
current buffer in place for the metrics, which the worker evaluates.
[Two execution paths](doc:two-execution-paths) gives the reason no frame of
an experiment crosses to the main thread.

**The compiled model** of `../compiled-model.ts` runs in the calling thread.
`computeNextFrame` returns a new frame for each step, and the model keeps the
latest one.
