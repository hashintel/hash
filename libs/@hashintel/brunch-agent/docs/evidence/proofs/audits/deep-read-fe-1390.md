## Builder's account

**What the commit contains** (Observed). Four new files, no modifications to existing behavior: `/Users/lunelson/Code/hashintel/brunch-lite/packages/core/src/capture-store.ts` (784 lines, the whole model), `/Users/lunelson/Code/hashintel/brunch-lite/packages/core/test/capture-store.test.ts` (422 lines, 12 cases), `/Users/lunelson/Code/hashintel/brunch-lite/packages/binding-flue/src/local-capture-store.ts` (76 lines, the storage-port implementation), `/Users/lunelson/Code/hashintel/brunch-lite/packages/binding-flue/test/local-capture-store.test.ts` (79 lines, 2 cases), plus 30 re-exports from `packages/core/src/index.ts` and one from the binding's index. `bun test` at HEAD is green (82 pass, 0 fail).

**The event model** (Observed). A `CaptureStoreSnapshot` is exactly three arrays — `captures`, `issues`, `events` (`capture-store.ts:133`), matching CONTEXT.md's "captures, issues, events" verbatim. Every write path appends: `applySweep` pushes new envelopes (`:588-592`), the three event commands append to `events`, `open-issue` appends to `issues`. Nothing in the module mutates or removes a record. There is no stored status anywhere; `deriveCaptureStatus` (`:457`) reads `retracted` from a retraction event, `superseded` from either a `supersedes` link pointing at the capture or a resolution naming it as a loser, and `active` otherwise. `deriveIssueStatus` (`:477`) reads `closed` from a resolution or `issue-closed` event. Both are pure functions of the snapshot, so equivalent state yields equivalent status regardless of discovery order.

**Capture identity is two-headed, deliberately** (Observed). A minted `id` (`capture-${randomUUID()}`) for reference, and a content-derived `dedupKey` (`captureDedupKey`, `:416`) computed over canonicalized provenance (sorted evidence spans, or the `basis` object) plus content — with `epistemicStatus`, `confidence`, and `alternativeGroup` excluded. The dedup logic (`:541-559`) has three distinct skip conditions: an exact retry (same key _and_ same supersedes/status/confidence/group), a duplicate with no supersession link (same key, any status), and a duplicate inside the same batch. The second is the load-bearing one: re-proposing the same evidence and payload with a _different_ epistemic reading and no `supersedes` link is silently skipped, which forces revision through explicit supersession. The store therefore contains multiple captures sharing one `dedupKey` by design (`test/capture-store.test.ts:65-74` asserts exactly that), and `parseCaptureStoreSnapshot` enforces uniqueness only on `id`, never on `dedupKey`.

**The command/refusal surface** (Observed). `applyCaptureStoreCommand` (`:628`) is a pure `(snapshot, command) => result`, five commands (`apply-sweep`, `open-issue`, `close-issue`, `resolve-conflict`, `retract-capture`) against eight refusal codes (`:168-190`). Refusals carry repair facts, not just messages: `superseded-target-not-active` returns `currentHeadIds`, computed by a fixpoint walk over links and resolutions (`currentHeads`, `:485`). Atomicity is structural rather than defended — the function builds a candidate array and returns it or returns a refusal, so a partial sweep has no representation. Advisories (`:594-620`) are computed per sweep, scoped to pairs where at least one side is newly applied, and never stored; the test asserts `snapshot.events` stays empty when advisories fire.

**How the binding implements the port** (Observed). `LocalCaptureStore` wraps the pure function: read the file, apply, write only if `ok`. Serialization is a module-level `Map<path, Promise>` (`local-capture-store.ts:14`) that chains each `execute` behind the previous one and stores an error-swallowing `settled` promise so `read()` can await the in-flight write without inheriting its rejection. The write is `writeFile` to `${path}.${uuid}.tmp` with `flag: 'wx'` then `rename` (`:61-73`). A missing file reads as an empty snapshot; any other read error propagates. Every read goes through `parseCaptureStoreSnapshot`, so the file is validated on the way in, not just on the way out.

**What the tests actually pin** (Observed). Six harness invariants are named in test titles — 2, 4, 5, 7, 9, 10 — each by one hand-written example. Beyond those: advisory reasons for same-evidence and near-identical payloads; defaulted/external-lookup captures refusing a user span; resolution accounting when three captures conflict; two persisted-snapshot rejections (a conflicting issue closed by a bare `issue-closed` event, a stale dedup key, a forking supersession graph); retraction refusing `user-affordance-payload` evidence. The binding tests pin reopen-and-read, no `.tmp` residue, concurrent writes serializing, and a refused sweep leaving the prior file intact.

**What a newcomer would misunderstand.**

- `dedupKey` looks like a primary key and is not (see above). Two active captures can share one.
- A sweep that skips everything still returns `ok: true` with `appliedCaptureIds: []`. There is no refusal code for "your revised epistemic reading was dropped; supersede capture X instead" — `skippedDedupKeys` reports the key but never the colliding capture's id, so a caller cannot mechanically find what to supersede. Silent-skip-on-success is the single most misreadable behavior in the module.
- `EvidenceSpan.pointer` looks harness-derived and is not: it is whatever the caller passed. Spec §5 says the pointer is "derived by the harness, which alone can see the entry projection", and §8.2 says "sequence numbers and range bounds never appear in the model-facing tool contract". Nothing in this branch derives or resolves anything; `entryStart`/`entryEnd` are required inputs. That is only safe because no model-facing sweep tool exists yet — nothing in the file says so.
- `EPISTEMIC_STATUSES` (`:13`) is exported and never used inside the module. The validators hard-code their picklists (`:224`) and literals (`:236`, `:243`), so adding a status to the array changes nothing and no test catches the divergence. `ABSENCE_STATES` and `ISSUE_TYPES` are genuinely wired into the schemas.
- The whole 784-line module carries **zero comments and zero spec citations**, in a repo where `packages/core/src/index.ts`, `packages/binding-flue/src/index.ts`, and `packages/binding-flue/src/capabilities.ts` all open with spec-cited headers. Every non-obvious ruling here (excluding status from the dedup key, the three-way skip test, resolution accounting by length-plus-membership) is unexplained in place.

**Where it is thin, brittle, or unresolved** (Observed unless marked).

- **No clock.** No record carries a timestamp or sweep-batch identity. Array order is the only ordering, and there is no session or high-water-mark input to `apply-sweep`. §9.3's re-entry briefing needs "captures created/superseded and issues opened/closed since this session's last sweep"; today that is computable only by remembering an array length. (Inferred: this will force either a stamp on records or a sweep-batch record.)
- **Cross-process concurrency is unguarded.** `writesByPath` is in-process only, and the read-modify-write does no version check or file lock. Two processes on one file lose writes silently, last writer wins. §9.6 asks only for "whole-sweep-atomic application and refusals with serialized writes", and the ticket-13 shape it blesses is exactly this, so it is conformant — but the optimistic staleness guard §9.2 relies on (the supersession refusal) protects only superseding sweeps. Plain appends, `open-issue`, and event commands have no staleness detection at all.
- **No fsync or directory sync.** `rename` gives atomic visibility, not durability; a crash can lose the whole write (not corrupt it).
- `resolve-conflict` aliases the caller's array into the snapshot (`:717`, `evidence: command.evidence`) where `retract-capture` copies it (`:759`, `[...command.evidence]`) and `applySweep` uses `structuredClone` (`:590`). This is the one mutable-aliasing hole, and it is exploitable — see the probe under the refactor-queue note.
- `confidence: string` with only a non-empty check (`:57`, `:196`). Spec §5 says confidence is "qualitative, never a scalar-for-everything"; the type accepts `"0.93"`. The prohibition is prose-only.
- `normalizedPayloadText` (`:524`) fires only when the payload _is_ a string (`typeof value === 'string'`). §6.2 promises "a flat-record plugin gets duplicate detection free"; a flat record `{ actor: "dispatcher" }` gets no near-identical advisory at all.
- The advisory scan is O(n²) with `deriveCaptureStatus` inside each iteration, re-run over the entire store on every sweep. (The refactor queue lists advisory-scan performance as explicitly out of scope, so this is known.)
- `parseCaptureStoreSnapshot` casts valibot's output (`:297`) because `v.unknown()` for `value` cannot express `JsonValue`; the `isJsonValue` loop that follows is what makes the cast true, and nothing marks that dependency.

**Contradictions worth stating outright.**

1. **The snapshot schema forecloses the session-log archive.** §9.6 is explicit that the port's scope is "the capture store plus the session-log archive" and that the milestone-one local store "holds the session-log archive alongside captures, issues, and events". `snapshotSchema` is a `strictObject`, so adding the archive later is a breaking format change plus a parser change, not an extension. Meanwhile `packages/binding-flue/src/index.ts`'s header claims the package "owns the storage-port implementation (spec §9.6)" — true of the capture-store half, false of the archive half, with no marker.
2. **`resolve-conflict` rejects `user-affordance-payload` evidence** (`:726`, pinned by `test:283-297`). §8.5 says "the true user's utterance", which supports this reading — but §5.1/C4 rules that a structured tap _is_ transport-explicit user input, and §9.4 lists user-affordance-payload alongside true-user for capture evidence. Consequence: a user who resolves a conflict by tapping a choice strip cannot close it. That is a defensible strict reading, but it is an adjudication the branch made silently, and it interacts with the unclosable-conflict holes below.
3. **The evidence-range ordering rule exists at one of three sites.** `entryEnd >= entryStart` is checked in `validateProposal` (`:447`) only — not in `evidenceSpanSchema` (`:200`), therefore not on persisted snapshots, and not on `resolve-conflict` or `retract-capture` evidence. A reversed range is refused in a capture proposal and accepted in a resolution record.
4. **CONTEXT.md vocabulary is respected**, with two additions and one absence. `basis: { type: 'declared-default' | 'documented-transformation' }` coins a field name for what the spec describes in prose only — fine, but it is now envelope vocabulary that the glossary does not contain. And the phrase "storage port" appears nowhere in the code: the type is `CaptureStore`, so a newcomer grepping the glossary's term finds nothing.

## Write-time tiering assessment

Against penciled item 7's three tiers:

**Deterministic tier — one of three checks present.**

- _Quoted excerpt appears verbatim in the pointed-at entry range_: **absent**, and not merely unimplemented — architecturally unreachable from here. The store's only inputs are the snapshot and the command; it has no entry projection, and `packages/` contains no anchoring code at all (grep for `excerpt`/`anchor`/`entryStart` outside `capture-store.ts` returns nothing). The capability that would supply it (capability 8, "read the durable entry projection with provenance-discriminating entry kinds", `capabilities.ts` id 8, `absorbed`) is declared and unused. Since §5 puts quote-to-entry resolution "exactly once, at sweep application", this check's natural home is precisely the seam this branch built — and it was left empty.
- _Anchors only on true user / affordance-payload entries_: **declared, not verified.** The `source` picklist makes the claim typed; nothing tests it against reality. §9.4 promises that on Flue this is "mechanically enforced, since signals appear structurally non-user in the entry projection". That enforcement does not exist.
- _`explicit` requires at least one span_: **present and structural.** `explicit` occurs only in the union branch that carries `evidence: minLength(1)` (`:222-225`), so an explicit capture without a span is unrepresentable rather than merely refused. This is the tier-1 check the branch genuinely earns.

**Semi-mechanical tier — entirely absent.** No lexical containment between excerpt and payload, no "does the quote support the value" check of any kind. The nearest neighbor, `normalizedPayloadText`, compares _two captures' payloads to each other_, not a payload to its own evidence — a cross-capture equivalence heuristic, not a support check. Penciled item 7's own example (a quote reading "every week or two" cannot support a payload of "10 days") would pass this store without comment.

**Residue tier — correctly located, but two messages dress tier-3 and tier-1's declaration as guarantees.** The store does carry interpretation uncertainty as labels and issues and never claims to have verified interpretation fidelity. But two refusal strings assert facts the code did not establish:

- `invalid-envelope`: _"A capture must have valid provenance and exactly one value or absence."_ The XOR half is genuinely mechanical. "Valid provenance" means: a non-empty excerpt string, positive integers, and a `source` label the caller chose. Nothing about provenance was validated.
- `parseCaptureStoreSnapshot`: _"${event.type} events must cite the true user's utterance."_ (`:325`) The check is `source === 'user'` on a self-declared field. The message states a verified fact about the world; the code checked a string.

This is the tier-1 dressing penciled item 7 warns about, in its mildest form — messages rather than mechanism. The fix is cheap (say what was checked) and worth doing before any consumer starts quoting these strings to a model, because a model reading "valid provenance" will not go looking for the verification that is missing.

**FE-1405's envelope-friction question, answered from the code.** Epistemic status is **strictly capture-scoped, and the type system makes per-field status unrepresentable** — not merely unmodelled.

- `epistemicStatus` is a single top-level field on the capture (`:65-84`), and it is the _discriminant_ of the proposal union: it selects which provenance shape the capture must carry. `explicit | inferred | tentative` ⇒ `evidence` required, `basis` forbidden; `defaulted` ⇒ `basis: declared-default` required, `evidence` forbidden; `external-lookup` ⇒ `basis: documented-transformation`. Because each branch is a `v.strictObject`, a capture cannot carry both `evidence` and `basis`. So the exact case FE-1405 names — actors stated explicitly, duration inferred by the interviewer, in one activity capture — has **no legal shape**: it would need one span-backed field and one inference-backed field in the same envelope.
- The payload half is `{ value: JsonValue }` — opaque, with no annotation slot. A plugin could smuggle per-field status inside the payload, and there are two reasons that misfires. First, §6.2 already names payload-smuggled envelope semantics as the plugin-`validate` smell. Second and sharper: the payload is inside `captureDedupKey` (`:425-428`) while `epistemicStatus` is deliberately outside it. Smuggling status into the payload therefore moves it _into_ capture identity, so revising one field's epistemic reading would mint a fresh dedup key and apply as a brand-new capture — silently, with no supersession — which is precisely the behavior §5 excludes status from the key to prevent. The idempotence design and the smuggling workaround are in direct opposition.
- The only envelope-legal expressions of mixed status are: split into one capture per status (which pushes granularity policy into the plugin's payload design, and §6.2 already flags compound payloads as making supersession lossy), or use `alternativeGroup` to hold several readings of the same evidence — which models competing interpretations, not differently-grounded fields.

So the friction FE-1405 predicted is real, and the code answers it more sharply than the spec prose does: this is not a missing field but a load-bearing structural coupling between status and provenance shape. Confirming Lu's filing note — it is kernel canon (spec §5), and any amendment touches the union, the dedup key's exclusion rule, and the tier-1 `explicit`-requires-span guarantee together.

## Commit-message backfill

```
FE-1390: Make capture history append-only and transactional

Captures, issues, and events now accumulate in one snapshot that is
only ever appended to. No record is mutated or removed, and every
status the rest of the system reads — active/superseded/retracted,
open/closed — is computed from supersession links and stored events at
read time rather than written down. Corrections therefore cannot erase
what they correct, and a re-swept range cannot double-capture: capture
identity is a content key over evidence and payload with epistemic
status excluded, so revising the reading of unchanged evidence has to
supersede an active head explicitly instead of overwriting it quietly.

The command surface is one pure function from snapshot plus command to
either a new snapshot or a typed refusal, which is what makes atomicity
structural: a partial sweep has no representation, so one invalid
proposal refuses the whole batch and nothing is written. Refusals carry
the facts a caller needs to retry — a stale supersession names the
current active heads. The Flue binding implements the storage port over
that function in the shape the skeleton proved: a JSON file, tmp and
rename, writes serialized per path, and a parse on every read that
re-derives dedup keys and rejects forking or cyclic supersession
histories.

Tests drive the public command function and the local store on disk.
Harness invariants 2, 4, 5, 7, 9 and 10 (spec §14.1) each get a named
case, and the binding suite proves a reopened store reads back what was
written, that concurrent writes serialize, and that a refused sweep
leaves the previous file intact.

Two halves of the port are deliberately not here: the session-log
archive (§9.6), which the current strict snapshot schema will have to
widen for, and any check that an excerpt really appears in the entries
its pointer names — pointers are trusted as given, and no harness code
consumes the store yet.
```

## PR body

Adds the capture store — the durable, session-independent truth of a target-document — as an append-only snapshot of captures, issues, and events, with every status derived at read time instead of stored. Writes go through one pure command function that returns either a whole new snapshot or a typed refusal, so a sweep applies completely or not at all, and the Flue binding implements the storage port over it with a JSON file, tmp-and-rename, and per-path serialized writes. Capture identity is content-keyed with epistemic status excluded, which makes re-sweeps idempotent and forces revised readings through explicit supersession. The session-log-archive half of the storage port (spec §9.6) and write-time verification of evidence pointers are not in this branch, and nothing consumes the store yet.

## Where the refactor queue's critique lands

I probed each claim rather than taking it on faith (script at `/private/tmp/claude-501/-Users-lunelson-Code-hashintel-brunch-lite/0c0505fd-18df-4b61-90e0-4fdb7906c109/scratchpad/probe.ts`, run against the real module).

**Confirmed: conflicts with no legal close, two distinct ways.**

1. _A `conflicting` issue with exactly one reference is born unclosable._ `open-issue` checks only that references are non-empty and exist (`:637-647`). Then `close-issue` refuses with `resolution-required` (`:684`), and `resolve-conflict` cannot succeed at any arity: `resolutionSchema` requires `loserCaptureIds` to be non-empty (`:277`), while the accounting check requires `citedCaptureIds.length === issue.references.length` (`:727`) — winner plus at least one loser is ≥ 2, references is 1. Probe output: `close-issue → resolution-required`, `resolve(winner only) → invalid-resolution`, `resolve(A vs B) → invalid-resolution`. The snapshot stays readable, so this is a permanent open issue, not a corruption. Refactor-queue commit 7 is the right fix.
2. _A well-formed two-capture conflict becomes unclosable the moment either side is superseded or retracted._ Nothing in `applySweep` or `retract-capture` consults open issues, and `resolve-conflict` requires every cited capture to be `active` (`:730`). Probe: with an open conflict over {A, B}, a sweep carrying `supersedes: A` **succeeds**, after which `close-issue` refuses and `resolve-conflict` refuses. Retracting A instead succeeds too, with the same result. This is refactor-queue commit 8's premise, and it is worse than an unclosable-issue bug: the contradiction disappears from the active set with no resolution record citing the user, which is exactly what harness invariant 2 forbids. Invariant 2's letter is enforced (a conflict never closes without a user-cited record) while its spirit is bypassed (the conflict is silently resolved by correction, and the issue is left as permanent litter).

**Confirmed: list-shaped data treated as a set.** `references` is validated as an array, never de-duplicated (`:258`, `:637`), but the resolution accounting compares by length plus membership rather than set equality (`:727-729`). Probe: a conflicting issue with `references: [A, A]` accepts a resolution naming winner A and loser **C, an uninvolved capture** — and C derives `superseded` afterwards. So duplicate references let a resolution supersede a capture that was never in conflict. Refactor-queue commit 6 is precisely aimed.

**Confirmed, but by a different mechanism than the doc names: "a command can return success for a snapshot the next read rejects."** I could not construct this from rule divergence — I tried to reach a forking or cyclic supersession graph (which only the parser checks) through legal commands, and the active-head requirement plus the same-batch `targetedCaptures` guard (`:572`) blocks every route I found. The realizable path is the aliasing hole instead: `resolve-conflict` stores the caller's `evidence` array by reference (`:717`) where `retract-capture` copies it (`:759`) and `applySweep` clones (`:590`). Probe: accept a resolution, then mutate the caller's span to `source: 'agent'`; the stored event mutates with it, and `parseCaptureStoreSnapshot` on the result throws `Invalid type: Expected ("user" | "user-affordance-payload") but received "agent"`. The durable file is exposed only through a narrow window (`#writeFile` awaits `mkdir` before stringifying), but the in-memory snapshot handed back to the caller — and any store implementation that holds one — is fully exposed. This belongs in the queue and is not currently in it.

**Confirmed: three separate rule sets, and they are not ordered.** Each site enforces something the others do not. Command-time only: evidence-range ordering (proposals alone), and cited-capture activity in resolutions. Parse-time only: dedup-key freshness, id uniqueness per family, forking and cyclic supersession graphs, and — notably — nothing about range ordering or capture activity.
