## Production change and identity seam

Other execution scopes return the original provider stream even when the evidence instrument is configured.

The environment value is a strict JSON configuration containing an absolute `ledgerPath` and a `runId`. The existing sibling `attempt-ledger.md` must exist. Configuration alone does not allocate anything: the existing JSON reservation must match the run, have `status: "active"`, and contain positive bounded `perCall.maxOutputTokens` and `perCall.reservedUsd`. Released, absent, invalid, underfunded or exhausted reservations refuse before native invocation. The current real reservation is released and lacks these new per-call fields, so it cannot accidentally become an active instrument reservation.

The installed Flue execution contract supplies submission identity in the outer `agent` interceptor, then conversation/operation/turn identity in the nested `model` interceptor. A scoped `AsyncLocalStorage` merges those known fields and requires an actual model operation at provider invocation. Each attempt retains `instanceId`, runtime `conversationId`, `submissionId`, `operationId`, and `turnId`, plus run, request sequence, requested provider/model and token/cost bounds. Missing identity refuses rather than synthesizing an ID. `instanceId` is checked against the mounted principal/conversation-derived route; `submissionId` against the SDK receipt; conversation, operation and turn against the runtime's `turn_request`. The exact issued IDs and checks' input/output are in [fixture-results.json](fixture-results.json). No wall-clock matching, session-ID-only join or content log supplies attribution.

The installed native adapter's supported `fetch` and `onPayload` seams enforce one SDK dispatch, `maxRetries: 0`, the reserved output ceiling (without increasing an already narrower requested cap), and the unchanged serialized model ID. A second dispatch is refused, including an attempted SDK retry. Flue can still attempt its own retry machinery, but an unresolved attempt blocks its next native launch; no additional paid attempt is silently dispatched. The existing one-use paid A1 launcher remains retired and unchanged.

An eager `upstream.result()` observer attaches once **below admission**. The single iterator snapshots cumulative usage without becoming a competing consumer. Completion and terminal events are two views of one native outcome, not additional calls. Accounting does not publish output, restore withheld proposals or drive continuation. Publication/admission outcome remains Flue's responsibility and can be joined using the stored IDs; no second publication history is created.

## Existing-ledger extension and historical compatibility

There is one production accounting authority: the existing `usage-ledger.json` and its existing Markdown attempt journal. No database, service or parallel paid ledger was added. The fixture ledgers are explicitly TEST INPUT/OUTPUT and remain outside that shared authority.

- Existing unversioned `status: "complete"` rows remain supported, with their original usage and `actualUsd` values. A focused test copies the real five-row ledger into a fresh disposable directory, adds one synthetic request there, and checks that the five historical rows remain equal and that only the fixture totals increase. It also checks the original file's bytes remain unchanged. Existing historical rows are not retrofitted with invented request identity.
- New rows have `accountingVersion: 1`. `sequence` is the existing call-array ordinal, including local attempted preparations; `runId` and runtime identity identify the attempt. `invocation` and `transport` independently distinguish positively not-invoked/not-dispatched preparation from an underlying invocation or SDK dispatch. `status` is `not-started`, `unknown`, or `complete`.
- Preparation first persists a `not-started` row. Immediately before provider invocation, it persists `unknown` plus `invocation: "started"`; immediately before SDK dispatch, it persists `transport: "started"`. A synchronous local preparation failure is classified not-started only when the wrapped transport did not dispatch. A crash after the unknown marker, even before dispatch, is not retroactively declared free by another process.
- A normal completed native response with positive usage/cost, matching provider/model, usage within bounds and every cost component matching the installed Pi `calculateCost` catalogue estimator settles `complete`. Comparison uses a cloned usage object; the instrument never replaces a discrepant native observation with a guessed paid settlement. Even a positive internally consistent underreported cost remains unknown. Native error/abort, zero usage, zero estimated cost, exceeded bounds, missing result or uncertain cancellation retain their reservation. A complete response already accounted before cancellation remains complete. A late result after unresolved cancellation is retained but **does not release** the reservation; this instrument does not invent an owner-approved fallback settlement for uncertain spend.
- `usage` is the latest native usage snapshot; `partialUsage` preserves the last observed cumulative partial separately from the native `terminal.usage`. A zero terminal error therefore does not erase the positive partial observation. Partial and final snapshots are never summed. `cacheWrite1h` is a subset of cache writes and reasoning is a subset of output; both are preserved without counting them again in `totalTokens`. Only identity, bounds, statuses and known usage fields are persisted; message text, tools, diagnostics, headers and credentials are not.
- `spentCalls` includes complete and unresolved started calls; `remainingCalls` already deducts both. `outstandingReservedCalls` is the unresolved subset of `spentCalls`, **not an additional call charge**. `spentUsd` remains the sum of completed catalogue estimates; `remainingUsd` is the dollar limit minus that sum. `outstandingReservedUsd` is the unresolved hold, conservatively raised to an observed partial/terminal estimate if it exceeds the original reservation. Available unencumbered dollars are `remainingUsd - outstandingReservedUsd`. These v1 meanings are explicit; the released historical ledger's five complete rows and zero outstanding totals are unchanged.
- The one active run's existing `reservation.calls`/`reservation.usd` remain allocation ceilings, not another call list. Every launch checks the run allocation and shared 200-call/US$100 maxima. Totals are checked against rows on every reread; changing a number to an inconsistent or invalid value does not create budget.
- JSON replacement uses a flushed temporary file, rename and directory flush. Before journal append, the same row persists `journalPending: true`; only after the existing Markdown attempt journal is appended/flushed does a second flushed JSON replacement clear that marker. A pending marker refuses every reread, even if the row's native usage is complete or the journal later becomes writable again. A crash after append but before marker clearance also stops conservatively. This is explicit uncertainty across two files, not a claim that two writes are atomic. An existing temporary file is not overwritten or interpreted as an alternate authority. Observer/write failures also poison the current instrument. No automatic journal reconstruction or new recovery authority is introduced.

The input reservation uses the selected catalogue model's entire context window, rather than pretending to know exact input tokenization before a request. With the pinned Sonnet catalogue, the worst input/cache rate includes one-hour writes at twice the input rate; output is reserved at its catalogue rate. The fixture uses a 1,000,000-input-token ceiling, 16 output tokens and a US$7 reservation, covering a US$6.00024 catalogue envelope. This deliberately refuses the old US$1-per-call envelope. It is conservative for the selected catalogue bounds, **not a tokenizer proof for arbitrary payloads, provider acceptance of a 16-token request, or a provider invoice guarantee**. `actualUsd` is retained for historical compatibility but means the native adapter's catalogue estimate, not billed money. Input/output usage reported beyond the declared bounds remains unresolved and stops further launches.
