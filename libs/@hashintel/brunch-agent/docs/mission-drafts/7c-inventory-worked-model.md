## Visible product advance

A product manager can open a stable Inventory purchasing worked-model bundle, receive or resume an independently owned copy, inspect a legible sophisticated SDCPN with its retained Brunch conversation and workpiece, ask why consequential content exists, correct it in ordinary language, see compiler-clean model changes and coherent layout, close/reopen, and obtain a clean copy without altering the template or another user's copy.

## Contract stratum

This mission closes one Inventory-level product path across six coupled contracts:

1. **Tool authority and topology.** One discoverable catalogue records every model-facing name, owner, definition home, mount condition, execution host and persisted-history consequence. Brunch-owned names follow the accepted `brunch_<operation>` rule; canonical Petrinaut action/command names remain camelCase; Flue built-ins remain substrate-owned. The package tree and always-on guidance follow the selected ownership rather than historical file growth.
2. **SDCPN mutation capability.** `mutate_petrinet` admits the canonical Petri-net operations the Inventory model actually needs, including corrections, without claiming parity with unrelated Petrinaut product features. Petrinaut Core remains the schema/action authority; the SDCPN plugin owns formalism-specific selection and guidance; the browser host executes and observes.
3. **Compilation feedback.** A structurally applied mutation is not a type-checked model. Every batch that writes code or changes a dependency of code reaches a version-correlated Petrinaut diagnostics result before Brunch relies on it. A bounded wait may return `pending`; it never becomes “clean” by timeout. Brunch can explicitly request the eventual result and repair it.
4. **Layout.** Petrinaut's existing asynchronous ELK layered layout makes newly constructed topology legible. Fresh construction may lay out without confirmation; existing user-arranged content requires the existing confirmation policy. Type/parameter/dynamics-only batches do not relayout. Layout effects and the final observed hash are recorded; no hidden post-result mutation makes the next base stale.
5. **Explanation guidance.** A why question about model content uses the mounted recorded explanation capability instead of answering from memory when that capability is available. Always-on SDCPN guidance owns recognition and routing; the activated job skill owns the detailed read-then-why protocol; the tool description owns its input/refusal contract.
6. **Worked-model catalogue and copies.** Approved bundle templates and owned working sessions use Postgres through the production store contract. Startup updates templates idempotently under stable IDs. Opening `?bundle=<stable-id>` creates or resumes an independently owned working copy while preserving conversation, workpiece, evidence, mutation, document and incarnation identities. A stable bundle ID selects content; it is not user authorization unless explicitly designed and reviewed as a capability credential.

## Throughline proof floor

- Freeze an Inventory-derived minimal code-bearing slice: one coloured type with elements, parameters, places/arcs, a stochastic transition lambda or kernel, and one differential equation.
- Apply one batch whose schema is canonical and whose code is deliberately type-incorrect.
- Observe the mutation as structurally applied while diagnostics independently report the error.
- Correct the dependency or code through a fresh observed batch and obtain a version-correlated clean result.
- Apply ELK according to the fresh-net policy and verify the reported final hash includes its position effects.
- Ask why about one created and one corrected element through ordinary language; the model calls the mounted explanation path and interprets its structured result.

This floor proves the coupled carrier. It does not establish Inventory completeness, template copying, deployment, semantic fidelity or PM utility.

## Risks and assumptions

- **ASSUMPTION:** one selected mutation carrier remains learnable as the Inventory operation set grows. **Impact if false:** full union visibility degrades tool following. **Cheapest validation:** provider/product probe with representative calls; compare one union with capability-grouped or deferred loading before selecting a new topology.

- **RISK:** relayout after a reported post-hash silently invalidates the next base. **Impact:** ordinary correction refuses as stale. **Cheapest validation:** assert the reported final hash equals a fresh browser observation after layout.
- **RISK:** automatic layout repeatedly destroys user spatial meaning or causes multi-chunk jitter. **Impact:** a technically valid model is unusable. **Cheapest validation:** fresh-net and prearranged-net browser cases under the explicit policy.
- **RISK:** renaming model-facing tools breaks retained histories and continuations. **Impact:** existing sessions cannot resume or explain prior records. **Cheapest validation:** inventory persisted names, then choose no rename, a bounded dual-read, or an explicit pre-release reset with owner acceptance.
- **RISK:** private-format template copying corrupts cross-store identities. **Impact:** why/workpiece/mutation records attach to the wrong document or owner. **Cheapest validation:** inspect Flue/Postgres native identity contracts before implementing copy; stop rather than string-rewrite exports.
- **ASSUMPTION:** a stable bundle key plus principal resolves the needed product entry. **Impact if false:** catalogue routing and authorization become entangled. **Cheapest validation:** two-principal route/ownership spike against Postgres.

## Carried evidence and rejected alternatives

- Mission 7b proved the selected structural batch through the product path, including one live 25-operation generation and one ordinary remove/add correction.
- The full 41-operation schema measured 69,897 compact bytes / about 16,581 tokens. This is a cost and model-following strain, not a documented provider cap. A 64 KiB refusal is rejected until a real boundary exhibits it.
- Petrinaut's current generic AI guidance already distinguishes schema mutation from TypeScript compilation and requires `getNetCompilationErrors` after code writes. Ordinary batched Brunch does not currently mount that read, and the AI SDK diagnostics-context wrapper does not deliver its synthetic text through Flue's client-tool-result continuation. Schema admission alone is therefore rejected as dynamics capability.
- Petrinaut already implements `applyAutoLayout` with asynchronous ELK layered layout. Unconditional relayout after every batch is rejected because it can move user-authored layouts, add provenance noise and create hidden post-result hashes.
- Petrinaut Core defines individual remove actions. Ordinary Brunch exposes them only as `mutate_petrinet` variants; the old headless six-tool refusal is a historical proof boundary, not a product prohibition.
- `?scenario=` is already the simulation-scenario location inside a document. Overloading it for a worked bundle is rejected; `?bundle=` is the current candidate.
- Core workpiece guidance is universal; recorded SDCPN why recognition is target-specific. Putting all why detail into universal core merely because the tool has a `brunch_` prefix is rejected. Final placement follows the authority reconciliation.
