## What is known — Petrinaut terrain at HEAD

Read on 2026-09-16 after FE-1667 (#9678) and FE-1668 (#9654) merged. Every line here is a current-state claim to re-verify before cutting.

**Two request shapes exist, and only the narrower one reaches an AI.** `petrinautExperimentRequestSchema` is the `createExperiment` tool input: `name`, `scenarioId`, `scenarioParameterValues` (per identifier `{mode:"fixed", value}` or `{mode:"range", min, max}` with numeric bounds only), `runCount` ≤ 100,000, `seed`, `dt`, `maxTime`, `metricIds` (1–20, unique), and `execution` as `{mode:"simulate"}` or `{mode:"optimize", objectiveMetricId, direction, steps ≤ 100, runsPerStep ≤ 1000}`, with steps × runsPerStep ≤ 10,000. It has **no constraints, no constraint policy, no units, no typed integer or boolean domains**. It requires a **saved scenario and saved metrics**; the tool description tells the model to read the net first for their ids. The canonical `petrinautOptimizationManifestSchema` has everything the request lacks: a sole objective metric with direction, typed continuous/integer/boolean domains, an optional `constraints` list and `constraintPolicy.alpha`, and study limits (≤ 1,000 trials, ≤ 100 seeds per trial, ≤ 5,000,000 total steps).

**Constraint semantics are fixed by the runtime, not by names.** A `parameters` constraint is one boolean expression over `scenario.*` and `parameters.*`, checked before a step simulates; a violating step is infeasible, costs one step, simulates nothing and is reported as pruned. A `state` constraint is a metric-shaped body returning a boolean, observed on **every sampled frame** of every run; a run passes when it held throughout. A step is **clear** when at least 1 − α of its runs passed, α ∈ (0, 1) with default 0.05, one α for the whole experiment. Both kinds are **reported, never enforced on the objective**: the optimizer's best step can be a limited step. Because α is strictly positive, a literal "never" is not representable; the tightest achievable is α < 1 ⁄ runsPerStep, which means every run in a step must pass, and even then the semantics are "no violation observed in these runs", not exclusion.

**Objective semantics.** The objective is one metric's value averaged over a step's runs **on the last sampled frame**. A metric is a pure function of `state` and net `parameters` (scenario parameters are not in scope). Anything time-integrated, cumulative or peak-valued is therefore a construction fact, not an experiment setting: the net must carry a place or token attribute that accumulates it, or the condition cannot be measured.

**Execution and UI.** The stock assistant runs `createExperiment` immediately: the panel calls `experimentHost.runExperiment(request)` on the tool call and the card offers **Cancel** and **View experiment**, not approve-then-run. The Create Experiment drawer is the only surface that authors constraints; it takes `open`/`onClose` only, has no prefill API, and its Constraints section appears only with both the Parameter sweeps and In-browser optimization settings on and a saved scenario selected. The panel already has one user-gated tool pattern — `applyAutoLayout` with `askUserFirst: true` shows a Yes/No prompt — so a "draft, then the user presses Run" lifecycle has a precedent inside the panel. `ExperimentHostContext` and `ExperimentsContext` are exported from `@hashintel/petrinaut/react`, so a host-side tool can reach `runExperiment` without a new core API. The stock [experiment card](../../../petrinaut/src/ui/views/Editor/panels/ai-assistant-panel/ai-assistant-contents/experiment-card.tsx) is **not** a drop-in for a drafted state: its props are bound to a stock tool call, its progress and its result, so a new state there is upstream UI work. The panel does expose a host-owned [interactive tool widget](../../../petrinaut/src/ui/types/ai-interactive-tool.ts) extension that renders before and after submission; a website-owned draft widget through that extension is the smaller route and does not touch Chris's card.

**Preparation is already separable from execution.** [`prepareExperiment`](../../../petrinaut/src/react/experiment-host/prepare-experiment.ts) resolves the saved scenario and metric references, type-checks each parameter against the saved scenario parameter's declared `type` (so an integer-typed parameter already yields an integer sweep domain through `buildParameterAxis` and the optimization builder; only boolean parameters reject ranges), and builds the optimization input **without starting computation** — but it hard-codes `constraints: []` and `constraintPolicy: null`. [`runExperiment`](../../../petrinaut/src/react/experiment-host/run-experiment.ts) `structuredClone`s the live definition **at invocation**, not earlier, so whatever the user approves is bound to the model at the moment Run is pressed. A core constraint carries both authored `code` and lowered `hir`, with `hir` regenerable from `code` as a no-op; an AI must author source and let the browser lower it against a specific model.

**Experiments are session state, not document entities.** Scenarios and metrics are part of the net: `scenarios` and `metrics` arrays sit on the SDCPN type and in the [file format](../../../petrinaut-core/src/file-format/types.ts), so they save, load and travel with the document. An experiment does not. `ExperimentsProvider` holds `ExperimentRecord[]` in React state, created by `createExperiment` and gone on reload; there is no experiment *definition* in the net type, the file format or the mutation surface. So the colleague's "routine entity" stance cannot be realized literally in the document today; it is realized in how the agent treats configuration during modelling (see the guidance principle below), and a literal document-model version would be an upstream change in Chris's package.

**Brunch has no experiment tool, and cannot yet author scenarios or metrics.** Brunch mounts `read_petrinaut_docs`, `read_petrinaut_net`, `read_petrinaut_diagnostics`, `layout_petrinaut_net` and `mutate_petrinaut_net` on the server and the browser executes them through the website wrappers; nothing experiment-shaped exists in the plugin, the catalogue or the skill. The mounted [`mutate_petrinaut_net` operation union](../../packages/plugin-sdcpn/src/mutate-petrinet.ts) covers places, transitions, arcs, types, type elements, differential equations and net parameters only — **no scenario or metric operations** — and the browser wrapper parses that union before executing. Since every experiment binds to a saved scenario and saved metrics, exposing those operations is a prerequisite of any design here, not a nicety. The FE-1668 website demo (`ai-experiments-demo`) is a scripted transport for the stock assistant, not a Brunch path.

## Contract stratum — the Ledger-to-experiment correspondence

The whole "scaling" question reduces to one closed mapping. Petrinaut offers exactly five destinations: **a parameter domain**, **the sole objective**, **a parameter constraint**, **a state constraint**, and **run settings**. Every condition the Ledger records either lands in one of them with a stated fidelity, or lands in an explicit `unsupported` list with the reason. No per-condition-class machinery is warranted; the guidance is a table, not a type system.

| Ledger condition class (where it lives) | Petrinaut destination | Fidelity and mandatory disclosure |
| --- | --- | --- |
| Tunable decision variable with bounds ("we could hold 2–6 days of stock") — Goals/constraints; Activities | `scenarioParameterValues[id] = {mode:"range", min, max}` on a **saved scenario parameter** | Exact for a continuous or integer quantity: the sweep domain is derived from the saved scenario parameter's declared `type`, so a count needs an integer-typed parameter, not rounding in metric or lambda code — never teach the agent to round. A boolean switch is unsupported (boolean parameters reject ranges); say so. The scenario parameter must exist first, with the right type — a construction prerequisite, not a configuration step. Units are not carried anywhere; the draft must state the unit and any conversion. |
| Quantity to maximize or minimize ("minimize total holding cost") — Goals/measures; Objective dependencies | `execution.optimize.objectiveMetricId` + `direction`; the metric must be one of `metricIds` | The optimizer reads the metric's **last-frame mean**. A total over the horizon or a peak needs an accumulating place or attribute in the net; without it the objective silently measures the end state. Disclose which of last-frame, accumulated or peak the metric actually is. |
| Absolute avoid-state ("never stock out", "never exceed 40 °C") — Goals/thresholds; Policies | `state` constraint: `return state.places.X.count >= 1;` observed every frame; `constraintPolicy.alpha` as tight as the user's meaning | Not exclusion. Best available: α < 1 ⁄ runsPerStep so every run in a step must pass, and the disclosure "the optimizer reports violation rates and may still select a violating point." Substituting a penalty in the objective **does not pass** (7d). If the user's meaning is a guarantee, record it as unsupported and configure the observed-rate version beside it. |
| Tolerable-rate restriction ("stock-outs on at most 5 % of days") — Goals/thresholds | `state` constraint with α set to the tolerance, **only if** the condition is per-run; a per-day rate is a metric the net must accumulate | α is per-step-across-runs, not per-time-within-run. A "5 % of days" condition is a time fraction inside a run and needs an accumulating attribute plus a final-frame condition. Disclose the mismatch when it exists. |
| Relation among parameters or a budget over parameters ("reorder point below capacity", "sum of allocations ≤ budget") — Goals/constraints | `parameters` constraint over `scenario.*` and `parameters.*`, checked before a step runs | Exact. Infeasible steps are pruned and named. Only scenario and net parameters are in scope. |
| Soft preference ("prefer fewer orders if cost is equal") — Goals/measures; Policies | Fold into the objective metric code as a weighted term, **or** record as a reported state constraint | Legitimate for genuinely soft preferences, and only there; the weight is an agent inference that must be declared as such with its basis. Never use this for a hard restriction. |
| Completion-by-time or service-level condition ("90 % of orders within two days") — Objective dependencies; Time | State constraint at the final frame **or** metric | A state constraint is checked on every frame, so an end-of-horizon condition is mis-stated by it (violated early, before work completes). No final-frame-only constraint exists. Express as a metric over accumulated token attributes and disclose that it is measured, not constrained. |
| Horizon and resolution ("plan over one quarter, daily granularity") — Boundary, horizon; Time | `maxTime`, `dt` in simulation seconds | Exact once the unit conversion is declared. A horizon that the net's rates do not match is a construction fact to surface. |
| Initial state, regime and operating conditions ("start with current stock", "peak season") — Boundary conditions; Policies/contextual regimes | The **saved scenario** (initial state, parameter overrides) named by `scenarioId` | The scenario is a construction prerequisite. Configuration must not invent one; if none exists, construct and settle it first, then configure. |
| Confidence appetite ("we need to be fairly sure") — Accuracy expectation; Assumption appetite | `runCount`, `runsPerStep`, `seed`, `steps` | Heuristic. Declare the chosen numbers as agent inference with the budget limits they respect. |
| What the result must not claim — Purpose and posture | Not representable in any experiment field | Belongs in the configuration's presentation text and in the Ledger; the card must carry it so the user reads the experiment's limits beside its settings. |

Mandatory declarations on every drafted configuration: the unit and conversion for each numeric field; whether each metric is last-frame, accumulated or peak; for each state constraint, the observed-rate disclosure; for each element, the Ledger locator it derives from; and the `unsupported` list with a one-line reason each. These are the model-visible and user-visible contract; they are what makes "correspondence to the user's meaning" inspectable rather than asserted.

## Pragmatic design assessment

Five shapes were considered against the 7d proof bar, the ownership rule and least mechanism. A is recommended and accepted as the practical approach now, in the refined form below.

**Oracle consultation (2026-09-16).** Lu asked whether A or E is genuinely the better design, not merely the more convenient one. The verdict: A's *session lifecycle* is right for the present scope, but its *preparation* must be Petrinaut's, not Brunch's. The A/E framing had bundled two independent decisions — authoring versus executing an experiment, and whether definitions persist with the document. A is right on the first and silent on the second; it becomes a dead end only if Brunch grows a second experiment-management system (its own resolution, validation, revision list, eventual persistence). E is cheaper than "nothing exists yet" suggests, because scenarios and metrics already set the schema, serialisation and mutation pattern, but it owes things A does not: a definition entity distinct from a run record (a definition can produce many runs, and after reload its existence says nothing about whether it ran — so "Drafted — not run" is not a persistent status), stale-reference semantics when scenarios, metrics or parameters change, and a Simulate-view listing. Both are multi-day; E plausibly adds a few days, and Chris's availability likely dominates that difference. So E is not "impractical", but it is not the destination either: propose a **thin E** upstream as an option and let the decision turn on the reversal evidence below.

**A. Brunch client tool + prepared session proposal + user-pressed Run (recommended; accepted by Lu, 2026-09-16; refined after the oracle).** One new Brunch tool, browser-executed like the existing five, whose input is the AI request shape extended with constraint **source** per space, `constraintPolicy`, `basis` locators and `unsupported`. The browser hands the experiment fields to Petrinaut's own preparation (`prepareExperiment`, exposed or factored upstream as prepare-without-run) against the live model, holds the one current prepared proposal in panel memory, and renders it in a **Drafted — not run** state with a **Run** action — through the host-owned interactive-widget extension the panel already offers, since the stock card is bound to the stock tool's call/progress/result. A later tool call replaces the proposal (create-and-revise; no draft list). Run re-prepares against the model as it is at that moment, shows any material difference, then calls `experimentHost.runExperiment`. Brunch owns only provenance (`basis`), declarations and `unsupported` — elicitation semantics, not experiment semantics. Meets every clause of the proof bar. Its dependencies are the exposure of preparation and, for a constrained proposal, constraint carriage through preparation (the oracle gap above); until the latter lands, a proposal with constraints can be inspected but not faithfully run, and the widget must say so rather than run without them. What survives a later move to E: the preparation path, the correspondence table, the guidance and most of the presentation. What would be discarded: the session store and the tool adapter — acceptable loss.

**E. Experiment definition as a first-class net entity (the literal reading of the colleague's stance; set aside by Lu, 2026-09-16, as not practical now; recast by the oracle as a thin option to propose, not a destination).** A definition array beside `scenarios` and `metrics` on the SDCPN type and file format, restricted to the saved-scenario/saved-metric workflow the AI request already assumes; add/update/remove operations; a run-from-definition host method; a listing in the Simulate view. Brunch would then author experiments through `mutate_petrinaut_net` like any other entity, and constraints would ride on the definition into every run. What makes it more than a field: the definition-versus-run identity split, the semantics of dangling references, and the UI to inspect, revise and run saved definitions. Entirely in Chris's packages. The preparation-boundary work in A is needed under E too, so it is not charged against A. Choose E now only on the reversal evidence: **users expect to reopen, compare, revise or rerun named configurations as part of the saved model**, or **Chris will land thin E in the same delivery window**, making the session adapter avoidable. One hedge is kept regardless: A's payload keeps the core-owned experiment fields separable from the Brunch envelope, so if E lands the payload becomes a mutation operation and the guidance does not move.

### Guidance principle: experiments are routine modelling entities

This is what the colleague's stance actually asks of Brunch, and it lands in the skill and prompt design rather than in schemas. From the user's point of view — and therefore from the agent's — configuring an experiment is not a special optimization phase entered after modelling is finished; it is one of the ordinary things you do while modelling, in the same breath as adding a scenario or a metric. Consequences for the guidance reference and the modelling flow:

- **Elicit it as construction, not as an appendix.** When the Ledger's goals, thresholds, tunable quantities and horizon are settled enough to construct the net that carries them, the agent proposes the experiment that measures them in the same construction pass — the scenario the conditions need, the metrics that read them, and the experiment that ties them together — instead of waiting for the user to ask for "optimization".
- **Name it in the same vocabulary.** The skill teaches experiments alongside places, transitions, dynamics, kernels, scenarios and metrics as things a model has, with the correspondence table as the rule for how a Ledger condition becomes one. "We should add an experiment for this" should be as ordinary a suggestion as "we should add a place for this".
- **Keep the user-run boundary.** Routine authoring does not mean routine execution. The agent drafts and revises freely; running remains the user's action. The principle raises the frequency of configuration, not of simulation.
- **Let readiness drive it, not sequence.** Because construction is incremental, an experiment can be drafted early against a partial net and revised as the net grows; the `unsupported` list is the honest record of what the net cannot yet measure, and shrinking it is a normal modelling task.
- **Design A serves this directly, with one honesty rule.** A drafted, inspectable, unrun experiment in the panel is the artifact a "routine entity" stance needs today, without waiting for a document-model change. But A keeps a narrower promise than E — *configuring* experiments is ordinary modelling; the configuration is **not** part of the saved model and does not survive reload — and the guidance must teach the promise the product actually keeps. The agent says "I've drafted an experiment for this session", not "I've added an experiment to the model", until E exists.

**B. Prefill the Create Experiment drawer.** Reuses the only constraint-authoring UI and its Optimize button as the user's run action. Rejected as the first cut: the drawer has no prefill API, is gated behind two user settings and the Simulate view, and the change is entirely in Chris's package. Retain as the natural later "Open in Create Experiment" action on the drafted card.

**C. Stock `createExperiment` then Cancel.** Rejected by the 7d proof bar explicitly; it also cannot carry constraints.

**D. A Brunch-side experiment schema or persisted entity.** Rejected by the 7d ownership rule (no parallel schema) and by the proof bar (no persistence required). The draft's validation is core's schema plus the compile service; Brunch adds only the `basis`/`unsupported` envelope, which is elicitation provenance, not experiment semantics.

**Guidance, not machinery, for the many condition classes.** The correspondence table becomes one skill reference for `sdcpn-modelling` (working name `experiment-configuration.md`), stating: which Ledger sections to read; the table as rules; the mandatory declarations; the refusals (never invent a scenario or metric — construct and settle first; never encode a hard restriction as a penalty; never call a run; place anything unmappable in `unsupported`); and the shape of the explanation the user sees. Deepen into typed condition slots in the Ledger only if repeated runs show the Markdown sections cannot be retrieved reliably for this purpose — the spine's rule, unchanged.

## Throughline proof floor

For one accepted Inventory objective and one avoid-state with units and hard/soft meaning: Brunch, through ordinary conversation, produces one drafted configuration whose declarations a reader can check against the Ledger; Petrinaut's preparation validates it against the live model; the panel shows it unstarted; the user asks for one change and the proposal is replaced, not duplicated; the host trace shows no simulation; the user presses Run and the experiment runs as configured against the model as it is then (or, if constraints are present and carriage has not landed, Run is refused with the reason). This proves a working configure-revise-run throughline for one example. It does not prove experiment credibility, portfolio breadth, Mission 11's handoff, persistence or any optimizer result.
