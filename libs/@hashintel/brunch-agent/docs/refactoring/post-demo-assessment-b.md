# The two agents optimize different objectives

The stock assistant is a net builder. Brunch is an evidence-faithful elicitation harness that treats net construction as a gated, subordinate side effect. Users who judge "build me a Petri net" are measuring Brunch on the task it deliberately deprioritizes, and every mechanism Brunch adds to protect provenance shows up to that user as latency, refusals, or gaps. Your own 2026-09-16 adjudication in [MISSION.md](file:///Users/lunelson/.herdr/worktrees/hash/alpha/libs/@hashintel/brunch-agent/MISSION.md) ("useful for partial elicitation but not product-scalable") already points the same way; below is the mechanism-level breakdown.

# Six concrete causes

**1. Five-plus model turns per net fragment versus one or two.** Stock ([api/chat.ts](file:///Users/lunelson/.herdr/worktrees/hash/alpha/apps/petrinaut-website/api/chat.ts)) is a single AI SDK `streamText` call whose tools execute client-side in the panel; the model emits many parallel tool calls per step, the browser applies them in milliseconds, and `lastAssistantMessageIsCompleteWithToolCalls` auto-continues. In Brunch every browser tool returns `{awaiting: "client"}, terminate: true`, ending the server turn; the browser executes, posts a client-result signal, and a full new model turn starts. The construction instruction in [flue.ts](file:///Users/lunelson/.herdr/worktrees/hash/alpha/libs/@hashintel/brunch-agent/packages/plugin-sdcpn/src/flue.ts) mandates "at most one browser tool call per proposal" and strictly separates read → mutate → diagnostics → layout → re-read. Measured: `run-SB5pgx` made 19 net mutations in 33 minutes.

**2. The Ledger settlement tax gates every construction step.** `createMutatePetrinetTool` throws "Settle the workpiece before construction." without a `currentRevision`. Settlement means re-uploading the full Markdown (322k argument chars over 46 calls; p50 22.3 s), citing evidence by literal text and `[message <id>]`, and the whole settlement is refused on absent/ambiguous text, a dropped heading, or a >25% shrink. Then each batch op must cite a `basis` with `revisionId`, `sha256`, and UTF-16 `locators` copied verbatim ([declared-basis.ts](file:///Users/lunelson/.herdr/worktrees/hash/alpha/libs/@hashintel/brunch-agent/packages/plugin-sdcpn/src/declared-basis.ts)), plus `observation.toolCallId` and `baseHash` of the last read. Any mismatch refuses the whole batch before anything applies. These are exact-copy failure surfaces stock simply does not have. The model's observed response was to silently shrink the Ledger 14,972→1,725 chars to cut upload cost, which degrades the very artifact the tax protects.

**3. No "make it up" escape hatch.** [petrinautAiPrompt](file:///Users/lunelson/.herdr/worktrees/hash/alpha/libs/@hashintel/petrinaut-core/src/ai.ts) says interview first, but skips the interview when the request is concrete and auto-applies sensible defaults on terse replies. Brunch's policy is the opposite: "Construction may not invent operational facts", "never invent a trigger, source, sink, release rule or numeric default", "do not manufacture an even split", and labelling an assumption does not authorize it. For textbook nets (SIR, café queue, satellite constellation) stock's domain-knowledge defaults are usually right, so users read the result as "more correct"; Brunch instead asks or records a gap.

**4. Brunch's prompts contain no SDCPN runtime know-how.** Stock's prompt carries a full code-surface cheatsheet (lambda/kernel/dynamics/visualizer/metric/scenario shapes, `input.PlaceName`, `parameters.snake_case`, `Distribution.*`, `Uuid.*`), extension-gating rules, the rename-breaks-code warning, a full example SDCPN JSON, and "validate every code-writing change". [pn-construction.md](file:///Users/lunelson/.herdr/worktrees/hash/alpha/libs/@hashintel/brunch-agent/packages/plugin-sdcpn/skills/sdcpn-modelling/references/pn-construction.md) has only an abstract mapping table and one example with `lambdaCode: ""`; grep finds no lambda/kernel/metric/scenario/`input.`/`parameters.` guidance anywhere in Brunch prompts or skills. Mutations validate schema, not runtime contract, so Brunch nets tend toward empty lambdas or compile-error loops that cost more terminate-per-tool round trips (cause 1).

**5. Narrower capability envelope.** Per the [mutation capability matrix](file:///Users/lunelson/.herdr/worktrees/hash/alpha/libs/@hashintel/brunch-agent/docs/reference/architecture/mutation-capability-matrix.md), `mutate_petrinaut_net` admits 22 root-only ops and omits scenarios, metrics, subnets, component instances, positions, `deleteItemsByIds`, `updateArcPlace`, `moveTypeElement`; `setNetTitle` and `createExperiment` are not mounted. Stock's prompt actively drives metrics and scenarios. A user who wants to simulate gets a complete artifact from stock and a structurally incomplete one from Brunch, refused at the schema level.

**6. Context weight and possibly model.** Brunch loads roughly 80k chars of guidance (SYSTEM.md, APPEND_SYSTEM.md, elicitation skill 21k, profile 16.6k, pn-construction 14k, checks 9.5k, template 6k, plus the long `useInstruction` blocks) before any domain content, then re-uploads the Ledger each settlement and retains `read_petrinaut_net` bodies (26 retained ≈ 40% of prompt). `run-SB5pgx` hit 253k cached tokens and compaction. Stock runs on one ~15k-char prompt. Model: stock pins `gpt-5.5-2026-04-23` at medium reasoning; [chat-model.ts](file:///Users/lunelson/.herdr/worktrees/hash/alpha/libs/@hashintel/brunch-agent/apps/brunch-agent/src/chat-model.ts) defaults to `claude-haiku-4-5` unless `BRUNCH_CHAT_MODEL` is set. I found no deployment config setting it (only turbo passthrough and test files), so the production model is unverified; if the deployed website is on the default, that alone would explain a chunk of the quality gap.

# Short answer

The `terminate: true` hand-off itself is not the cost, and it is not the substrate's fault. It is structurally the same thing the stock assistant does: the AI SDK stream ends, the browser runs the tools, and `sendAutomaticallyWhen: lastAssistantMessageIsCompleteWithToolCalls` ([ai-assistant-panel.tsx](file:///Users/lunelson/.herdr/worktrees/hash/alpha/libs/@hashintel/petrinaut/src/ui/views/Editor/panels/ai-assistant-panel.tsx#L1201-L1204)) fires a fresh POST and a fresh model call. Both agents pay one model turn per browser-tool batch. The difference is batch size: stock lets one turn carry N tool calls; Brunch caps it at exactly one, then mandates a five-link chain around it. Those caps are Brunch's own, not Flue's.

# What Flue actually permits

Flue's contract ([agent-api.md](file:///Users/lunelson/.herdr/worktrees/hash/alpha/node_modules/@flue/runtime/docs/reference/agent-api.md#L507)): "a multi-tool batch ends the turn only when every result in it terminates." A batch of N terminating browser calls suspends once. Brunch's own FE-1434 spike ([verdict, 2026-08-19](file:///Users/lunelson/.herdr/worktrees/hash/alpha/libs/@hashintel/brunch-agent/docs/evidence/spikes/fe-1434-suspension-verdict-2026-08-19.md)) proved this: batches of 3 and of 100 terminating client calls each took 2 dispatches and 2 model turns, with all results returned in one `signal`. The result carrier is already an array, `[{toolCallId, toolName, output, metadata?}]` ([client-tool-result.ts](file:///Users/lunelson/.herdr/worktrees/hash/alpha/libs/@hashintel/brunch-agent/packages/transport-aisdk/src/client-tool-result.ts)). So "many browser calls per turn, executed milliseconds apart in the browser, one return signal" is a shape the transport was designed for and verified.

What Flue genuinely does not offer: a native inbound tool-result message (`kind: 'tool-result'` was rejected 400) or a client-executed tool primitive. Hence the `awaiting: client` sentinel plus signal. That part is a real substrate constraint, but it costs one hop per batch, same as stock.

# Where the single-call rule actually comes from

Three separate restrictions are stacked, and only one is Flue-forced:

**Mixed browser/server refusal — Flue-forced.** Decision G1 in the [provenance decision log](file:///Users/lunelson/.herdr/worktrees/hash/alpha/libs/@hashintel/brunch-agent/docs/evidence/design/provenance-and-tooling-decision-log-2026-09-04.md#L135): a non-terminating server tool (`mutate_workpiece`) beside a terminating browser tool keeps the turn alive, so the browser never gets the hand-off. Legitimate. But it only forbids mixing; it says nothing about two browser calls together.

**"Multiple browser calls refused before admission" — Brunch policy, no recorded failure behind it.** Enforced in [provider-admission.ts](file:///Users/lunelson/.herdr/worktrees/hash/alpha/apps/brunch-agent/src/provider-admission.ts#L313-L317) and repeated in the [agent instruction](file:///Users/lunelson/.herdr/worktrees/hash/alpha/apps/brunch-agent/src/agents/chat-agent/agent.ts#L228). It arrived in Mission 7a in a commit titled only "Reject multi-browser proposals before publishing tool inputs", with no rationale in the message; the [7a archive](file:///Users/lunelson/.herdr/worktrees/hash/alpha/libs/@hashintel/brunch-agent/docs/mission-archive/7a-workpiece-construction-explanation-groundwork.md#L80) itself flags it as "preserve… a future tool-surface redesign must explicitly revisit". The instruction's justification ("do not rely on sibling execution order") is a hedge, not an observed failure. Under the context root's own "safeguards must earn their friction" corrective, this one hasn't.

**The read → mutate → diagnostics → layout → re-read chain — forced by Brunch's provenance protocol, not Flue.** `mutate_petrinaut_net` must cite `observation.toolCallId` and `baseHash` from a read that has already executed, and `observationFor` resolves it by scanning history before the call ([agent.ts](file:///Users/lunelson/.herdr/worktrees/hash/alpha/apps/brunch-agent/src/agents/chat-agent/agent.ts#L203-L218)). A read and a mutate therefore cannot share a batch, and a second mutate would fail the base check after the first changes the hash. That is a real data dependency, but Brunch created it by choosing hash-cited optimistic concurrency for provenance. Stock has no such dependency: it mutates the live document directly and reads only when the model wants to.

# So was it modelled incorrectly?

Partly. The substrate was read correctly (terminate + signal is the only hand-off Flue offers, and the mixed-batch limit is real). What was over-applied is the generalisation from "one pending interaction slot" to "one browser call per proposal". FE-1434 explicitly adjudicated the slot as "an external-tool-batch variant containing every call from one assistant turn"; the admission guard later collapsed that batch to a single call and nothing in the record says why.

Two designs were available within Flue that would have kept construction near stock speed:

Batching: drop the >1 guard and let the model emit N browser calls per proposal; the browser executes them in order in milliseconds and returns one signal. FE-1434 already proved the substrate half. It would still need the hash protocol relaxed (or the chain folded into one browser-side `construct` client tool that does mutate → diagnostics → layout → re-read and returns everything in one result) to remove the five-link sequencing.

Hold-open: let a tool's `run` await the browser result over the in-process live channel Brunch already has (single process, one owner per conversation), so the Flue loop continues without a dispatch/admission/history round trip. This was not chosen because Mission 6's imperative was resumability (second tab, reopen, crash survival); a browser disconnect mid-tool would hang the turn. That is a real trade-off, but it is one the stock assistant never had to make.

Net: of the ~5 model turns per fragment, roughly one is substrate-imposed (browser work can't share a turn with `mutate_workpiece`); the rest come from the single-call admission guard and the hash-cited observation protocol, both of which are Brunch design decisions that could be revisited without leaving Flue.
