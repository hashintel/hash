# Brunch architecture

`apps/brunch-agent` composes the Flue server, the Brunch Ledger, SDCPN modelling skill and Petrinaut canonical tools. `apps/petrinaut-website` owns browser-local document state and executes browser tools through Petrinaut's editor. The server imports Petrinaut's published headless catalogue, not the UI package. Native Stock remains a separate panel choice.

## Conversation composition

A conversation whose initial data carries a Petrinaut document binding (`{ binding }`) mounts the Brunch prompt, skill, Ledger tools, filtered net readers, reviewed experiment draft and explanation tool while preserving every canonical Petrinaut tool. A conversation admitted without initial data retains the plugin prompt, skill and Ledger tools but no Petrinaut tools.

The core and plugin Markdown under `packages/*/src/prompts/` and `packages/*/src/skills/` is runtime model input. Prompts are imported with `?raw`. Each skill is an Agent Skills directory whose `SKILL.md` the package exports and imports natively; library builds leave that import in place and the consuming Flue application packages the directory. Gherkin is packaged but unmounted; Dafny and Claims are unmounted experimental packages.

## Package entries

Each Brunch package has a main entry and a `./flue` entry. The main entry holds everything that loads without a Flue build: constants, schemas, types and pure functions, plus core's Ledger tools. `./flue` holds the agent hooks and the skills they mount; a `SKILL.md` import loads only in code Flue builds, so only the Flue application imports `./flue`. The persona launcher, scripts and the website import the main entries. The SDCPN main entry stays browser-safe because the website imports it, so its Flue tool definitions live behind `./flue`; it also carries Petrinaut's contextual user-message framing, which the website writes and the Flue application parses. Core additionally exposes browser-safe `./client-tools`, `./conversation-identity` and `./ledger` slices. Brunch's named constants live in core's `constants.ts`, which imports nothing; the main entry exports them, and browser code and the SDCPN plugin import them through the `./constants` slice, because the main entry's Ledger tools load `@flue/runtime`. Tests exercise the hooks with the `SKILL.md` import mocked; the Flue build is what packages and validates the skills.

## Loading workspace source in dev

Each Brunch package points TypeScript at `src` but runs from `dist`. So that a dev server does not run stale code, every export in these packages carries an `"@dev/source"` condition, placed after `types` and before `import`, that names the TypeScript source. The Brunch and website Vite configs prepend that condition to Vite's default client and server conditions only when they serve; builds, Vitest and plain Node never enable it and keep resolving `dist`. The name is a custom condition rather than `source` or `development`: Vite enables `development` by default in dev, and some published packages ship a `source` condition, so either would also switch third-party packages to unbuilt code. A new Brunch package export adds the condition beside its `types` entry. Petrinaut and petrinaut-core do not use it: they need their own build (Panda CSS and Vite-only imports), so their dev servers run from `dist`.

## Ledger

The Ledger is the ordered sequence of accepted `ledger_commit` calls in the conversation's canonical history; it has no other storage. Each commit appends immutable Notes filed under the categories of a profile core composes around the SDCPN plugin's. The host assigns Note ids (`n1`, `n2`, …) and addresses in canonical order and stamps each commit with the user message it followed; the model supplies content, a category or superseded Note, and epistemic fields (`source`, `basis`, `standing`, `precision`, `qualifier`), or a free-text `disposition` when `BRUNCH_LEDGER_NOTES=open`. Supersession records a relationship and hides nothing.

A running commit reads history, rebuilds the accepted commits before its own call and decides from them alone, so an interrupted durable call re-runs to the same Notes. A commit counts only when its recorded input and successful output agree on call identity and Note addresses. Flue folds a response's steps into one message and may run a proposal's calls concurrently: a commit that runs while an earlier commit in the same response is unsettled is refused. `ledger_compile` renders every Note by category in recording order, with supersession links, epistemic fields and an index of open and contested Notes nothing supersedes; it performs no reconciliation. The website's Ledger pane and persona evidence (`ledger.md`, `ledger.json`) use the same reconstruction and compilation.

## Browser and conversation boundary

Flue's persisted conversation is canonical history. In a document-bound conversation, every browser tool, the canonical catalogue, the filtered readers and the experiment draft, is a server-issued call that waits for a direct one-use HTTP result; no browser result arrives as a later Flue signal. The panel orders same-document canonical calls; the draft card claims and settles its own call once preparation finishes. Admission refuses a proposal that places a tool beside a tool whose result it reads (`query_basis` beside a net read; `ledger_compile` beside `ledger_commit`; the draft beside `getLatestNetDefinition`). The browser returns Petrinaut's own output unchanged and host-only metadata: `documentRevision: { before?: string; after?: string }`, where `before` names the revision observed before the call and `after` exists only when the call changed the document, and after a change a `readBack` of the net's structure. A document revision is a structural hash of the document's content, computed by the host, so equal content has an equal revision. Neither the one-use capability nor the document binding authenticates the person; ownership middleware binds the authorized conversation, and the browser-call rendezvous binds the document. An attempted write without a settled result is never presumed rolled back or retried after reload.

`readNetOutline` and `readNetStructure` run `getLatestNetDefinition` in the browser and return it without canvas positions, visual settings or host metadata; the outline also omits code.

## Net freshness

Before each provider request the context projection records which net reads and settled changes the model's context holds. A document change is issued only against the revision of the latest of those; with none left, for example after compaction, it is refused before reaching the browser. The browser accepts the change only if its document has moved since that revision through Brunch's own settled changes, following their before-to-after chain, so a hand edit refuses it as stale. The projection strips the host envelope from browser results and shows the latest change's `readBack` as `netAfterChanges` unless a later net read supersedes it. It does not change canonical conversation history, public history, call identity or ordering.

The server credits an applied canonical call with its settled `after` revision; it does not re-hash or replay browser-produced evidence. `net-changes.ts` projects those calls in history order. `query_basis` looks up a named element in the latest net read and lists applied calls associated by element ID, each with the Ledger revision current at the call and the Notes recorded earlier in its turn. These temporal associations do not prove a semantic basis. A reviewed experiment draft requires an earlier net read; the browser prepares against the current document revision. Canonical `createExperiment` remains Petrinaut-owned and does not mutate the document.

## Runtime and persistence

Local development and tests use Flue's SQLite store; production requires Postgres. See `apps/brunch-agent/src/database-config.ts` and `apps/brunch-agent/src/db.ts`.

The repository patches `@flue/runtime@2.0.3`, `@earendil-works/pi-agent-core@0.83.0` and `@earendil-works/pi-ai@0.83.0` for context projection, native tool input and complete provider schemas. Re-evaluate this patch boundary together when upgrading Flue or Pi.
