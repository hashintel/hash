The canvas renders the active net as an interactive graph and owns its scene, its pointer state, the per-frame simulation values and the gestures.
The editor and the [preview](layer:ui.preview) both mount it, so it imports nothing from the [editor shell](layer:ui.views.editor). No rule of `archinaut check` enforces that.

![A gesture changes one store, the scene is derived again, React Flow renders the nodes whose object changed, and the arc layer the arcs whose shape changed](./canvas-flow.d2)

## Entry point

`SDCPNView` in `ui/views/SDCPN/sdcpn-view.tsx` composes four parts, in this order:

1. `useCanvasScene` builds a `CanvasScene`: plain data that says what to draw and holds no React Flow type.
2. `CanvasPointerContext` carries a `CanvasPointer`: the hover, the item that waits for a release to be hovered, and the drag preview of this canvas. `SDCPNView` creates it once with `createCanvasPointer`.
3. `CanvasFrameStoreProvider` holds the values of the viewed simulation frame. It is keyed by `petriNetId`, the id of the document, so another document starts with an empty store.
4. `ReactFlowCanvas`, the [React Flow renderer](layer:ui.views.canvas.react-flow), draws the scene and publishes a `CanvasController`. It mounts once the size of the container is known.

`SDCPNView` also mounts `CursorTooltip` beside the renderer.

## Interface

| Name                                       | File                         | Use it to                                                                                                                                                                                          |
| ------------------------------------------ | ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `SDCPNView`                                | `sdcpn-view.tsx`             | Mount the canvas. `onControllerChange` receives the controller.                                                                                                                                    |
| `CanvasController`                         | `canvas-renderer.ts`         | Move the viewport from outside (`setViewport`, `zoomIn`, `zoomOut`, `fitView`, `frameSceneAfterRender`), read where it will rest (`getRestViewport`) and convert a screen point (`screenToScene`). |
| `useCanvasController`                      | `canvas-renderer.ts`         | Read the controller inside the renderer.                                                                                                                                                           |
| `useCanvasInteractions`                    | `use-canvas-interactions.ts` | Turn a renderer's gestures into selection, moves, connections and drops.                                                                                                                           |
| `usePlaceTokenLabel`, `useTransitionFrame` | `canvas-frame-store.tsx`     | Read one item's value of the viewed frame, by id.                                                                                                                                                  |
| `useIsHovered`                             | `canvas-pointer.ts`          | Ask whether the pointer is on one node or line.                                                                                                                                                    |

## Data flow

A user drags a node:

1. React Flow reports position changes. `useApplyNodeChanges` passes them to `moveNodes`, which writes the positions to `dragPreview` in the canvas pointer, snapped to the grid while the `snapToGrid` setting is on.
2. `useCanvasScene` derives the scene again with the previewed positions.
3. `useReactFlowElements` maps the scene to nodes and edges, and `useStableItems` returns the previous object for each item whose content is the same. The edges are one edge for all the arcs, one for each selected arc, and the fusion links.
4. React Flow renders the dragged nodes. The arc layer reads the scene from a context and renders the arcs that end at them.
5. On release, `dropNodes` commits the positions in one document mutation and clears the preview in the same tick.

## What renders

| Gesture        | Nodes and arcs that render                                                                                                                                      |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Select         | The nodes whose selected state or focus changed, the arcs whose role changed, and the runs that hold those arcs                                                 |
| Hover          | The state tooltip of the place under the pointer, at once. After the pointer rests, the nodes and arcs whose focus changed, and the runs of those arcs.         |
| Drag frame     | The dragged nodes and the arcs that end at them. The merged paths of a run are written at the first frame and at the drop, and not in between.                  |
| Pan, zoom      | No node and no arc: React Flow writes one transform on the viewport element. An open place state tooltip renders on each frame, because it reads `useViewport`. |
| Playback frame | The places and transitions whose value moved. No arc: a firing adds a path to the page outside React.                                                           |

The focus of a node or an arc is its `CanvasNodeFocus` or `CanvasArcFocus` in `canvas-focus.ts`: how it relates to the hovered or selected items.
The pointer rests after 150 ms with no move above 2 px, and a hover changes focus only while the `highlightOnHover` setting is on. A place with visualizer code reaches the scene before the rest, so its visualizer shows at once.
The release of a button counts as a move, so a hover that begins at the release waits the same 150 ms.

`benchmarks/monaco-performance/canvas-scale.mjs`, from the package root, measures each gesture on a net of about 500 nodes and, with `details=1`, lists who rendered. Its header says which build to serve.

## The arc layer

React Flow draws the nodes and the fusion links. `ArcLayer` draws the arcs, all of them in one `svg` that React Flow renders as one edge.
The arcs at rest are merged into a few paths for each run of consecutive arcs, and an arc with a focus role, a selection or a dragged end draws its own strokes.
Each arc keeps one element with the name, the role and the tab stop of an edge of React Flow, which takes the pointer for it.
[The arc layer](doc:ui.views.canvas.react-flow/arc-layer) has its parts, its rules and where an arc differs from an edge of React Flow.

## Rules

**A handler given to `ReactFlow` keeps its identity.** React Flow renders every node and arc when a handler prop is a new function. `useCanvasInteractions` returns its actions through `useStableActions`, and each action reads the latest state when called. `use-stable-actions.test.ts` holds this for the actions. The handlers that `ReactFlowCanvasInner` writes inline keep their identity through the React Compiler, and no test checks those.

**An unchanged node or edge is the same object, and an unchanged list the same array.** React Flow renders an item for a new object and walks every item for a new array. `use-stable-items.test.ts` and the test "preserves unaffected nodes when focus changes" in `use-react-flow-elements.test.tsx` hold this.

**A value that changes per playback frame is read by id from the frame store.** A frame moves one number per place and per transition, and a scene rebuild for each frame would compare every node. The test "re-renders only the items whose values moved" in `canvas-frame-store.test.tsx` holds this.

**Hover and drag preview stay in `CanvasPointer`.** No panel subscribes to it, so a pointer move renders no panel. `use-canvas-scene.test.tsx` covers the hover delay and the drag.

**A node or arc that comes under the pointer while a button is down is hovered at the release.** A pan moves the net one frame after the pointer, so nodes and arcs pass under the pointer. Hovered on the way, each would fade the rest of the net and clear again, which takes most of the frames of a pan on a large net. A renderer reports each item with `enter` and says whether a button is down and whether a connection is being drawn. `enter` keeps an item that has to wait in `hoverOnReleaseId` of the canvas pointer, and `releasePointer` hovers it. Two gestures hover without that wait: a node is hovered from the start of its drag, and a connection being drawn hovers the item it comes onto. The tests under "the hover of what the pointer comes onto" in `use-canvas-interactions.test.tsx` hold this, and "waits as long for the hover a released button leaves behind" in `use-canvas-scene.test.tsx` holds the delay after the release.

A visualizer window that is kept open stays through a pan and stands for its place, so it follows the rule: under a pressed pointer it writes its place to `hoverOnReleaseId`. A preview and the eye hover their place whatever the buttons. A preview closes once its place is no longer hovered, and the eye shows on a place that is hovered or selected, which is lit already. The test "keeps the place of a window kept open for the release when a pan carries the window under the pointer" in `place-state-tooltip.test.tsx` holds the window's part.

A release has to count as a move before `releasePointer` hovers the item, or the hover finds the pointer at rest and shows at once. `usePointerAtRest` therefore listens for the release in the capture phase: React runs the handlers of a release inside the visualizer window, which is a portal, before that release bubbles to the canvas element. The window stops the release of its own drag only, so a pan that ends over it reaches `releasePointer`. "hears a release before a handler on its target does" in `use-pointer-at-rest.test.ts` and "stops the release of its own drag and lets any other through to the canvas" in `visualizer-window.test.tsx` hold these. No test checks what the React Flow renderer passes to `enter`, or that a browser counts the release before `releasePointer` runs.

**A control drawn over the canvas has the class `nokey`.** While the selection key is held, React Flow starts a selection box from a press anywhere inside the pane, and takes the press from the control. A control that is no part of the net (the visualizer window, the eye that opens it, the fold toggle of a component card) opts out with React Flow's `nokey` class. `useSelectionKeyRelease` covers the case where the page saw Shift go down and not come up, as after a system shortcut: the next press that says Shift is up sends the missing keyup. The tests in `selection-keys.test.tsx` and `visualizer-window.test.tsx` hold both.

**No opacity goes on an element that every arc has.** The browser draws a group with an opacity into a buffer of its own on every frame, and a group per arc is a buffer per arc. [The arc layer](doc:ui.views.canvas.react-flow/arc-layer) has how a faded arc is drawn without one, and the tests that hold it.

**No opacity goes on a node, or on an element inside one that draws more than one thing.** The browser draws such an element into a buffer of its own on every frame of a pan, a zoom or a drag, and a net has one per node. So a node outside the focused neighbourhood draws each of its things at 0.4 by the alpha of that thing's own colour, and what lies behind the node shows through it as it would through an opacity. On a net of 470 nodes with a node selected, a pan showed 43 frames a second with those buffers and shows 84 without them, on a GPU: [Editor performance on a large net](doc:editor-performance) has the numbers. The rules are in `paneStyle`, in `pane-style.ts` of the [React Flow renderer](layer:ui.views.canvas.react-flow), and find what a node draws by class:

| What a node draws                          | Class          | While the node is faded                                             |
| ------------------------------------------ | -------------- | ------------------------------------------------------------------- |
| The card or box                            | `node-surface` | Its fill, `--node-fill`, at 0.4, the ring of a classic box at 0.4   |
| Text                                       | `node-text`    | Its colour at 0.4: `--node-text`, or the colour it inherits         |
| A background of its own                    | `node-fill`    | `--node-fill` at 0.4                                                |
| A border                                   | `node-border`  | `--node-border` at 0.4                                              |
| A background nearly the colour of the card | `node-inlay`   | Not drawn                                                           |
| A token count, the pin of a port           | `node-cover`   | Opaque, mixed 0.4 toward the colour of the canvas                   |
| The shapes of an icon                      | none           | `fill-opacity` and `stroke-opacity` 0.4, no stroke on a filled icon |

Where two things of a node lie on each other, two alphas show the lower one through the upper, which an opacity on the node did not. Four parts differ from a plain alpha for that reason:

- The icon box of a transition or of a component instance is an inlay: it is nearly the white of its card, so the card under it draws that colour and the box is left out.
- The icon box of a compact place lies on the colour of a token type. The fill of a faded place is a gradient with a hole under the box. A gradient does not fade, so the colour under it does, and the gradient goes once the fade back is over.
- A token count and a pin are covers. Each lies across the border of its node, and a count is white on black. They stay opaque and take the colour they would have over the bare canvas.
- A filled icon is a fill under a stroke of one colour, and the inner half of the stroke would show as a darker rim. Its stroke goes.

The flash and the bolt of a firing are keyframes that no rule reaches. `useTransitionFiringAnimation` asks whether its node is faded when the firing lands, and the bolt carries `node-bolt` so the rule for icons leaves it alone.

**No rule of that fade changes what an element hands down to the elements inside it.** A custom property or a `color` on a faded node restyles every element of every node. On the net of 470 nodes that added 100 ms of style to a hover and its leave. So a colour a rule has to mix is a custom property its element sets once and never changes, `node-text` goes on the element that holds the text, and the fade of an icon is set on each shape.

A part added to a node carries the class of what it draws, or it stays at full strength in a faded node. `faded-node-parts.test.tsx` renders each kind of node and fails for an element that draws text, a background or a border without its class, and for an opacity between 0 and 1. `pane-style.test.ts` reads the rules: none gives a node or a part an opacity, none changes the node itself, and none sets a custom property, or a `color` outside `node-text`, on a part. The tests in `use-transition-firing-animation.test.tsx` hold the flash. No test draws a faded node: the tests read class names, and the pictures are in [Editor performance on a large net](doc:editor-performance).

A faded node is not the picture of a node under an opacity in these places:

- A part that lies on the fill of its node lets 36% of what is behind the node through, where the whole node let 60% through: its text, the glyph of a classic transition and the disc of a badge. It shows where an arc passes behind a faded node.
- A token count and a pin hide what is behind them.
- A filled icon is smaller by half the width of its stroke, 0.9 px on each side at zoom 1.
- A faded node has no elevation. At 0.4 its shadow darkened the canvas by 4 of 255 at most, and a blurred shadow is what a compact card costs most on every frame of a pan.
- The hairline of an icon box, the rule under a component's header, the white ring of a port place's pin and an inlay change at the start of a fade. Everything else takes the 200 ms.
- The border of a compact transition or of a component card takes those 200 ms to darken under the pointer, as the ring of a classic box does: one transition serves the hover and the fade.
- The fade runs on the main thread, as a transition of each colour, where the opacity of a node ran on the compositor with a layer per node. A small net shows as many frames of it as before. A net of 470 nodes shows fewer: the same page of the performance guide has the frames.

## Pitfalls

- No custom property is registered for the canvas, by `@property` or by `CSS.registerProperty`. A registered property with a delayed transition could hold an arc's head through the fade back in CSS alone. With any property registered, used or not, Chromium 145 takes 550 to 850 ms to restyle that net for a change of focus, where it takes 77 ms. A registration holds for the whole document, so one made by the page around the editor costs the same. The test in `panda.config.shared.test.ts` holds that the Panda preset makes none. WebKit 26.5, the engine of Safari, also paints the next marker while such a transition waits. A transition on `marker-end` itself makes Chromium paint no head for as long as it runs.
- `useStableItems` reads a ref during render and opts out of the React Compiler with `"use no memo"`. It compares against the previous render's objects, which no effect can do in time. Keep scene items plain data: the comparison handles primitives, plain objects and arrays only.
- An action from `useCanvasInteractions` is for an event. Calling one during render reads state of an earlier render.
