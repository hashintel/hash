A sweep experiment has one orchestrator, the sweep session, and one React
provider that owns it. The session holds no React: it turns selection changes
into batches and keeps their frames in a cache per selection. The provider
turns what the session publishes into experiment records and decides which
backend computes each batch.

![A selection change and an optimizer trial enter through the same two actions, and every batch reaches the record the drawer and the activity list read.](./sweep-orchestration.d2)

## The selection path

A slider move or a pick on the surface calls `setSweepSelection` through the
actions context. The session normalizes the selection. When the selection or
the run cap changed, or nothing is computing, it aborts the ladder that was
computing and starts the ladder for the new selection.
[Parameter sweeps](doc:react.experiments/parameter-sweeps) gives the rungs,
where the ladder stops, and why at most two rungs compute at once.

Each rung asks the provider to instantiate a batch. The provider builds an
`ExperimentRequest`. Per-run parameter draws travel in it as a typed-array
plan over the net parameters the sweep's axes can reach, and a point
selection travels as a constant plan. Every batch therefore lays out the same
per-run buffer, and the GPU backend keeps one compiled setup across
selections. The backend selection chooses between the CPU worker pool and
the WebGPU backend once per experiment, with its first batch. Each later
batch assesses the chosen backend again with its own request.

Frames come back through the stores of the experiment handle. The session
merges the selection's cached frames with the frames of the rungs computing,
and publishes at most once per 100 ms, the first frames at once. The provider
writes each publish into the record, which the drawer and its charts read
from the experiments context.

## The optimizer path

A study starts during creation when **Start optimizer immediately** is
checked (`useCreateOptimizedExperiment`), or later through **Optimize** on
the Parameters card (`useSweepOptimizer`). Both call the function
that `useStartSweepStudy` returns, with the experiment record and the
objective.

The first trial relies on one contract of `createExperiment`: the sweep
branch awaits nothing before `startSweepSession`. The session is then
registered when the promise resolves, and the study's first `navigateSweep`
finds it. The provider's test holds that no `await` is inserted before it.

If the immediate start rejects, creation removes the experiment before
selecting it. If a later start rejects, the experiment and its earlier study
remain.

A trial goes through `navigateSweep(experimentId, point, { runCap })`. The
session adopts the point as its selection with a run cap and restarts its
ladder there. The call resolves with the point's value per metric once the
point has that many runs in the cache. It resolves null when another
navigation superseded it, when the sweep is disposed while it waits, or when
its ladder ends with no finished run. It rejects with the batch's reason
when a batch of the point fails, and with "The sweep is no longer running"
when the session is gone before the call. The evaluator lets a rejection
fail the study.

The cap keeps the ladder from starting a rung the next trial would abort. A
plain `setSweepSelection` lifts it, so a point the user returns to refines to
the run budget. A sweep computes nothing until something selects.

The optimizations provider owns the evaluator that calls `navigateSweep`,
in [the sweep evaluator](layer:react.optimizations.sweep-evaluator). The
experiments layer never learns who asked.

## The batch path

Every publish of the session lists the rungs computing at that moment,
oldest first, each with its id, its run count and its completed runs. The
provider stores the list as `sweepBatches` on the record, which the
experiment's details read. A session that stopped computing publishes an
empty list.

The activity list and the popover of the top bar show the same progress. For
a sweep it is the sampled runs of the selected combination over the run
budget. For any other experiment it is simulated time over the experiment's
end time.

## Constraints through the sweep

An experiment's constraints are lowered to HIR in the Create Experiment
drawer and stored on the record, with the pass threshold as
`constraintPolicy` and the scenario's parsed values as
`scenarioParameterValues`. They are enforced in two places, both outside the
study's own code.

A **parameter constraint** is judged by the sweep evaluator at the snapped
grid point, before `navigateSweep` is called. The evaluator interprets the
HIR with the net's defaults as `parameters` and the snapped values as
`scenario`. An infeasible draw is pruned with the reason `Infeasible: <name>`
and moves nothing: the sweep's selection stays where it was.

A **state constraint** travels with every request the experiments provider
builds for the sweep, as one precompiled indicator metric under the id
`constraint:<id>`. The body is wrapped as `cond ? 1 : 0`, with
`aggregateTime: "min"` over each run's frames and `sampleRuns: "notErrored"`.
Those ids never reach `metricSpecs` on the record, so no tile, picker or
surface option shows them.

The mean of the indicator over a visited cell is the share of runs that
passed among those that did not error, and `sweepCellPassCount` turns it back
into the count the evaluator reports. `toGpuMetricSpecs` refuses a time
aggregation, so a sweep with state constraints runs on the CPU. The drawer's
GPU gate carries a placeholder `min` spec per drafted state row, so the
switch says so before creation.

The rates that the Constraints card, the steps table and the objective strip
read are computed from each trial's `constraints`. A trial pruned as
cancelled carries none and counts in no rate.

## The study in the experiment drawer

`experimentResultsModel` builds the `ResultsModel` that the results view of
the Simulate panel renders. `useSweepOptimizer` finds the current study by
the experiment id in the `origin` of an `OptimizationRecord`.

Once a study exists, the results show the optimization's progress, an
objective strip, constraint and sensitivity cards, and a steps table. They
stay after the study completes, stops or fails.

The Parameters header offers **Optimize** for an eligible sweep with metrics
and a connected source. Its popover selects the metric, the direction and the
step budget, with the same validation as creation. An active study replaces
that action with **Stop** and locks the sliders and the surface. Requests
owned by the assistant and cancelled experiments lock the controls too.

A new start that succeeds removes the settled study once the provider has
registered its replacement. A start that rejects keeps the previous study.
The experiment keeps its sampled points across searches.
