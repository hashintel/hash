A sweep experiment declares an interval per swept scenario parameter and
computes only the region of those intervals that is selected. Each interval
is quantized into `SWEEP_AXIS_STEPS` positions, and an integer parameter
steps by whole numbers.

A selection is an inclusive position range per parameter, a `SweepSelection`.
A range whose two ends are equal is a point. The navigator shows one slider
per parameter and selects a point with each move. When the selection changes,
the batches that were computing are cancelled and the new selection starts.

![A selection change restarts the ladder at the new selection. Finished batches stay in the cache, so a selection that is revisited resumes where it stopped.](./sweep-refinement.d2)

## Points, ranges and the ladder

A point selection runs the experiment at that value. A range selection runs
one stochastic experiment over the ranges. Each run carries its own drawn
value per ranged parameter (`sweepRangeDraws`). The draws are low-discrepancy
across the selected interval and rotated by a shift derived from the seed, a
Cranley–Patterson rotation, so each experiment seed explores its own
sequence. They are prefix-stable in the seed, the axis and the global run
index. The quantized positions bound the interval, and the draws are
continuous inside it.

One selection is one experiment. It uses the whole worker pool, and its
metric stream is the distribution over the region from the first frames on.

Either kind climbs `EXPERIMENT_RUN_LADDER`: 8, 25, 100, 500 and 1,000 runs,
then five times and twice the last target in turn, capped by the run budget.
Each rung is a batch that covers the runs the earlier rungs left. A finished
batch goes into a cache keyed by the whole selection.

The climb is pipelined. Run ranges are disjoint, and draws and seeds are
prefix-stable in the run index, so the next rung starts as soon as a rung
streams its first frames. At most two rungs compute at once.

Batches enter the cache in rung order. A rung that a selection change
cancels discards the rung started after it, so the cache never holds a gap.
A selection that is revisited gets its runs back and resumes from its rung.

Per-run parameter values travel as the `runPlan` of the experiment request:
one run-major `Float64Array` and the names it overrides. The WebGPU backend
copies it into its per-run buffer, and the CPU backend expands it into the
engine's per-run configurations where the request reaches the worker pool.

Scenario compilation needs one value per parameter. An initial state derived
from a ranged parameter is therefore compiled at the middle of the range
(`selectionMidpoint`), while what the run reads of the parameter varies per
run.

## What a batch costs on the main thread

Everything between a selection change and the first dispatch runs on the main
thread: drawing the per-run values, translating them through the scenario,
and building the request. At a rung of a million runs this work is what the
user feels, and most of it is scenario compilation.

Draws are continuous inside the interval, so almost every assignment is one
the compiler has not seen, and a result per draw cannot be cached. Three
things keep the cost down:

- `prepareScenarioCompiler` does once what does not depend on the values:
  type-checking the overrides and the initial state, building the expression
  contexts, parsing the defaults of the net's parameters. Each compile after
  that merges the assignment, interprets the override expressions and coerces
  the results. The provider prepares one compiler per experiment.
- `compileParameterNumbers` compiles a run's parameters without the initial
  state and without converting to strings. A batch's marking comes from the
  compile at its midpoint, so an error in the initial state fails the batch
  once, and not each of its runs.
- `sweepRangeDraws` writes one typed array of draws, and
  `translateRangeDraws` fills one `Float64Array` column per parameter name,
  each filled with the base value first. No record is allocated per run.

What remains is linear in the run count, so the draw and translation loops
yield. `createCooperativeYielder` checks a budget of 8 ms every few thousand
iterations and hands the thread back, through `scheduler.yield()` where the
browser has it and a macrotask elsewhere. The total cost is the same, and no
single task holds the main thread through it.

## Determinism

A batch that covers runs `[from, target)` takes the seed
`deriveRunSeed(seed, from)`, and the first batch keeps the base seed. The
ladder is the same for every selection, so the same rung draws the same seeds
everywhere: common random numbers across the space. A rung that was cancelled
and runs again repeats exactly, and a cached result never goes out of date,
because the same position always means the same runs.

## Who does what

`createSweepSession` owns the loop: selection, ladder, cache and
cancellation. It knows no backend. It asks an injected `instantiateBatch` for
a `MonteCarloExperiment` per batch and reads that handle's stores, so the CPU
worker pool and the WebGPU backend behave the same to it.

The provider supplies `instantiateBatch`. A sweep's first batch goes through
the same [backend selection](doc:core.experiments/backend-selection) as a
plain experiment, and later batches assess the chosen backend again with
their own request. The swept net parameters travel in the per-run plan for
every batch, a point selection as a constant plan, so the GPU backend keeps
one compiled setup and its calibration across selections. The scenario is
compiled per batch, because the swept values change the compiled initial
state.

Each slider move of the navigator reaches `setSweepSelection` with a point.
Everything else the UI shows of a sweep is the experiment record, which the
session streams out.
