`SimulationProvider` owns the run configuration, starts a run or an
experiment on the selected simulator, and mirrors its handle into React. It
computes nothing: a simulator from
[the simulators layer](layer:react.simulators) computes,
[the viewed execution](layer:react.execution-trace) says which trace the
editor shows, [event playback](layer:react.event-playback) moves the viewed
time over it, and
[the execution frame source](layer:react.execution-frame) hands frames to the
views.

![A start takes the configuration and gives a run in Quick mode or an experiment in Stochastic mode. A run is a trace its worker writes, and the host's execution in Actual mode is mapped to one. The trace of the editor's mode is the one viewed: one player moves over it, and the views read it.](./simulation-session.d2)

## Entry point

`SimulationProvider` in `provider.tsx` publishes `SimulationContext`. It is
mounted below `SimulatorsProvider`, and above `ExecutionTraceProvider`,
`EventPlaybackProvider` and `ExecutionFrameProvider`, which wrap one another
in that order below the editor state.

## Interface

| To                                | Read                                                                                                                                                                                               |
| --------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Start, pause or rewind            | `play`, `pause` and `stop` of `EventPlaybackContext`, which call `initialize`, `run` and `pause` of `SimulationContext`                                                                            |
| Discard the run                   | `reset` of `SimulationContext`                                                                                                                                                                     |
| Change what the next run computes | `setInitialMarking`, `setParameterValue`, `setMode`, `setRuns`, `setMaxTime`, `selectSimulator`, `setSimulatorParameter`, `setSelectedScenarioId`, `setAdHocScenario`, `setScenarioParameterValue` |
| Show where it stands              | `state`, `error`; `eventCount` of `EventPlaybackContext` for a run                                                                                                                                 |
| Read the viewed execution         | `trace`, `origin`, `clock` and `continuity` of `ExecutionTraceContext`                                                                                                                             |
| Show the state of a run at a time | `currentFrameReader` of `ExecutionFrameSourceContext`                                                                                                                                              |
| Show the metrics of an experiment | `stochasticRun.reader`                                                                                                                                                                             |
| Show the viewed time              | `useEventPlaybackFrame`                                                                                                                                                                            |

A frame is the state one event of a run recorded, and `totalFrames` of
`ExecutionFrameSourceContext` counts them. The viewed frame is the state at
the viewed time, which a `SimulationFrameReader` gives: `getPlaceTokenCount`
and `getPlaceTokens` for a place, `getTransitionState` for a transition.

`clock` says what a position counts: simulated seconds, or steps for an
untimed net. A view reads it from `ExecutionTraceContext`, which gives the
viewed execution's clock; `SimulationContext` gives the simulation's. The
location owns the selected scenario, so `setSelectedScenarioId` navigates.

## Data flow

Pressing Play with nothing started:

1. `play` of `EventPlaybackContext` calls `initialize` with
   `PETRINAUT_DEFAULT_SEED`.
2. `initialize` takes the configuration as it stands. A selected scenario, or
   the ad-hoc one, is compiled. Its parameter values replace the manual ones.
   Its marking is merged over the manual marking, so a place it does not set
   keeps the manual one.
3. The net's code is compiled, by the language client in the editor and by
   the `compiler` prop where the host passes one. The selected simulator is
   assessed with the request, and starts an `EventSimulation` in Quick mode
   or a `MonteCarloExperiment` in Stochastic mode.
4. The provider keeps the handle in state and reads its status with
   `useStore`. `playbackSource` is the run's
   [execution trace](layer:core.execution-trace), which the worker's events
   are written to.
5. `ExecutionTraceProvider` gives that trace as the viewed execution, and
   `EventPlaybackProvider` loads it into the one player.
6. The player advances the viewed time once per animation frame. It asks
   the trace to cover the viewed time plus the lead of the play mode, which
   `EVENT_PLAY_MODE_LEAD` gives: 2 seconds in `computeBuffer`, no bound in
   `computeMax`. In `viewOnly` it asks for nothing, so the run computes
   nothing more. `event-playback/provider.test.tsx` holds both.
7. `ExecutionFrameProvider` publishes the trace's state at the viewed time.

Stochastic mode differs from step 4 on. `playbackSource` is the experiment's
samples as something the player can play: positions, and no events. The
experiment computes freely, so asking it to cover a time does nothing. It
has no frames: `currentFrameReader` is null, `totalFrames` stays at zero,
and a view reads the metrics by time from `stochasticRun.reader`.

In Actual mode the host supplies an initial state and a list of firings
through `ActualModeContext`, and `useActualModeTrace` maps them to an
execution trace. From step 5 on nothing differs: the same player moves over
that trace and the same views read it. The player opens it at its end and
follows it while the host's execution is still going, and Play never starts
or pauses a simulation there.

`reset` ends the run and puts the parameter values back to their defaults. It
keeps `initialMarking`, which configures the next run.

`keepStochasticRun` hands the experiment of Stochastic mode to its caller.
The views keep showing it, and `reset` no longer stops it. An experiment
created in the Simulate view never passes through this provider:
[Two execution paths](doc:two-execution-paths) gives the reason.

## Rules

- **A render that changed nothing gives the same `SimulationContext` value.**
  The canvas, the bars and the panels read this context, so a new value
  renders all of them. Held by `provider.context-value.react.test.tsx`.
- **A setter that changes what the live run reflects discards the run.** The
  views would otherwise show a run of another configuration.
  `provider.simulators.react.test.tsx` holds it for `selectSimulator`. No
  test holds it for the other setters.
- **Play pressed during a start joins that start.** A second `initialize`
  would supersede the first and compile the net again. Held by
  `event-playback/provider.test.tsx`.
- **One trace lasts for one execution of the host.** The trace grows with
  the host's list of firings, so the viewed position and the zoom of the
  timeline survive an update. Another source id, another net, or a list
  that does not continue the one mapped starts a new trace. Held by
  `execution-trace/use-actual-mode-trace.test.tsx`.

## Pitfalls

- A component that calls `useEventPlaybackFrame`, or reads
  `ExecutionFrameSourceContext`, renders on every animation frame while
  playing. Read either in the component that shows the time or the state at
  it.
- `SimulationContext` does not change when the event count or the viewed
  time does. Subscribe to `playbackStore` with `useStore`.
  `EventPlaybackContext` carries `eventCount` and `coveredTime` as numbers,
  so its value changes on every batch of events the worker posts.
- `initialize` resolves `false` when a change of configuration overtook the
  start, and the caller then has nothing to play. It rejects when the
  simulator refuses the request or the net does not compile, and puts the
  reason in `error`.
