A panel size changes on every pointer move of a drag, and how far a panel is
in view changes on every frame while it slides open or shut. Held in React
state, each change re-rendered every reader of the editor context. Both are
therefore Motion values, and the elements that depend on one are written
directly.

```text
pointer move
  -> ResizeHandle.onResize(size)
  -> panelSizes.propertiesPanelWidth.set(size)   a Motion value, no React state
same frame, before it is painted
  -> styleRef: panel.style.width = size          each dependent element, no render
  -> watch listeners run                         the camera keeps the selection clear
  -> useReading readers re-render                only those that compute with it
pointer up
  -> ResizeHandle.onResizeEnd()
  -> user settings saved                         once per drag
```

## Motion values, and where they stop

[Motion](https://motion.dev) is the library behind these values. Four of its
functions are in use: `motionValue` holds a value and tells its listeners when
it changes, `styleEffect` writes values onto an element's style once per
frame, `transformValue` computes a value from the values it reads, and
`animateValue` takes a number from one value to another over time. UI code
reaches `styleEffect` and `transformValue` through `ui/lib/readings.ts`.

Use a Motion value for a number of the UI's own that changes on every pointer
move or frame and that elements follow: a size, an offset, a position, how far
a panel is in view. The document, a run and what a plugin publishes come from
Core as stores and are read with `useStore`. Section animations with fixed
keyframes use the browser's `element.animate`.

| `Reading`                                   | `ui/lib/readings.ts`                                                   | A Motion value, or a function computed from the Motion values it reads.           |
| `styleRef`, `bindStyle`                     | `ui/lib/readings.ts`                                                   | Keeps an element's inline style on readings, as a ref or for an element in hand.  |
| `watch`                                     | `ui/lib/readings.ts`                                                   | Calls a listener when a reading changes.                                          |
| `useReading`                                | `ui/lib/readings.ts`                                                   | A reading as a value, in a component.                                             |

| `ResizeHandle`                              | `ui/resize/resize-handle.tsx`                                          | Asks for the size when a drag starts, reports each move and the end.              |

The values keep one identity for the editor's life. Reading `usePanelSizes()`
or `usePanelPresence()` never re-renders the reader.

## Reading a value

Pick the first row that fits.

| The reader                                                | Reads with                              | Renders per move or frame  |
| --------------------------------------------------------- | --------------------------------------- | -------------------------- |
| An element whose style follows sizes, presence or insets  | `ref={styleRef({ property: reading })}` | No                         |
| An event handler                                          | `value.get()`                           | No                         |
| An effect                                                 | `watch(reading, listener)`              | No                         |
| A component that needs a yes or no computed from them     | `useReading(() => answer)`              | Only when the answer flips |
| A component that computes with the number while rendering | `useReading(value)`                     | Yes, that component        |

```tsx
const { propertiesPanelWidth, bottomPanelHeight } = usePanelSizes();
const { shown } = usePanelPresence();

<GlassPanel
  ref={styleRef({
    width: propertiesPanelWidth,
    bottom: () =>
      shown.bottomPanel.get() * (bottomPanelHeight.get() + PANEL_MARGIN),
    transform: () => slideFromEdge("right", shown.propertiesPanel.get()),
  })}
  resizable={{
    edge: "left",
    getSize: () => propertiesPanelWidth.get(),
    onResize: (width) => propertiesPanelWidth.set(width),
    onResizeEnd: () => saveWidth(propertiesPanelWidth.get()),
  }}
/>;
```

The Properties panel follows four values: its own width, how far it is in
view, and the height and the presence of the bottom panel it ends above.
`width` takes the value itself. `bottom` and `transform` take a function,
which is a reading too.

The rules of a reading:

- A function is followed through the Motion values it reads the first time it
  runs. It reads every value it depends on before any condition on one of
  them.
- A function may close over React values such as the view the editor is in.
  When one changes, the component renders, the ref is attached again and the
  style is written with the new value.
- A style is written when the element attaches, and from then on once per
  frame in which a reading changed. A function is worked out once per frame
  too, however many of its values changed.
- `watch` and `useReading` hear of a Motion value at once, and of a function
  once per frame.
- Properties go by the names Motion takes: `width`, `marginLeft`,
  `--a-custom-property`. A number is in pixels where CSS takes a length.
- `styleRef` must not set a property that the element's React `style` prop
  also sets: React would write its own value back on the next render.

## Keeping clear of the panels

The panels overlay the canvas, so whatever floats over the canvas keeps clear
of them by the canvas insets. `useCanvasInsetsReader()` gives a function that
works the insets out from the four sizes and from how far each panel is in
view. It is a reading: called inside a bound style, `watch` or `useReading` it
makes them follow the panels, and called on its own it gives the insets at
that moment.

| Reader                    | How it follows a drag or a slide                                                                                        |
| ------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| Viewport controls         | `styleRef` writes `right` and `bottom`.                                                                                 |
| Minimap                   | React Flow's minimap takes no ref. A `display: contents` box around it finds the minimap and binds its `right`.         |
| Bottom bar                | `bindStyle` writes its `transform`. `useReading` says whether the bar still fits, so it renders only when that changes. |
| Camera controller         | Calls the function when it frames the scene.                                                                            |
| Keeping selection in view | `watch` moves the camera once per frame in which the insets changed.                                                    |
| Visualizer windows        | `useCanvasInsets()`: they compute their bounds while rendering, so an open window renders on each move.                 |

A panel that opens or closes moves its presence value, so the same readers
follow its slide frame by frame and whatever keeps clear of a panel moves with
the panel's edge.

## Opening, closing, docking and floating

`PanelPresence` holds one value per panel for how far it is in view, from 0
(closed) to 1 (open), and two for the AI assistant.

```text
the editor's state opens a panel                   one render, as for any state
  -> PanelPresenceProvider: animateValue(0 -> 1)   150 ms, in a layout effect
each frame
  -> shown.propertiesPanel.set(progress)           a Motion value, no React state
  -> styleRef: panel.style.transform               slideFromEdge, no render
  -> insets readers                                minimap, controls, bottom bar
last frame
  -> shown.propertiesPanel is 1                    the transform is `none`
```

| Value                | Range                  | Who follows it                                                                                       |
| -------------------- | ---------------------- | ---------------------------------------------------------------------------------------------------- |
| `shown.<panel>`      | 0 closed to 1 open     | The panel's `transform`, the insets, and the edges of the panels beside it.                          |
| `aiAssistantDocked`  | 0 floating to 1 docked | The assistant's box, which lies between the floating window's and the docked column's.               |
| `aiAssistantHasRoom` | 0 or 1, in one step    | The width of the room beside the editor. Each change lays the whole editor out, so it does not ease. |

The provider is the one place that animates. It reads which panels are open
from the editor's state and where the assistant sits from
`AssistantPlacementContext`, and takes each value to its target with
`animateValue`. Where the Animations setting is off, or the system asks for
reduced motion, the value jumps. A change of target while a value animates
starts the next animation from where the value is.

- **The slide counts from its first frame.** Motion counts an animation's time
  from the call that starts it. The render that opens a panel can take the
  time of several frames, and the first frame drawn would then show most of
  the slide done. The provider sets the animation's time to zero in that
  first frame, as a CSS transition starts.
- **A panel at rest has no transform.** `slideFromEdge` gives `none` for a
  panel that is fully in view. Any transform would make the panel the
  containing block of the fixed elements inside it, such as a code editor's
  suggestion list.
- **A closed panel leaves when it has slid out.** A panel reads
  `useReading(() => shown.leftSidebar.get() > 0)`, which renders it twice per
  slide, and unmounts or hides once that is false.
- **The docked assistant covers its room before it takes it.** While it
  arrives, `assistantCover` says how much of its width lies over the editor.
  The insets add that to the right edge, and the Properties panel moves by
  it, so they slide out of the assistant's way while the editor keeps its
  width. When the assistant has arrived, `aiAssistantHasRoom` steps to 1, the
  editor gives up the room and the cover is zero. When it leaves or floats,
  the room goes back at once.

A floating window keeps its position and size the same way.
`useFloatingPanel` holds them as Motion values and `bindPanel()` is the ref
that writes them on the window as four custom properties. The window's box is
CSS over those properties (`box`), which keeps it inside its parent whatever
the values are. They are custom properties on the window itself, so only the
window's own elements inherit them.

## Why the write goes to each element

A custom property on the editor root looks like the simpler design: one write,
and every reader picks it up with `var()`. It was built first and measured.
A custom property is inherited, so the browser restyles every element below
the one it changes on, whether or not any of them reads it.

Sixty frames with one write each, on the Supply Chain example with 9,288
elements under the editor root (M1 Max, Chromium 145, production build):

| Write per frame                      | Style recalculation | Median frame |
| ------------------------------------ | ------------------: | -----------: |
| None                                 |                2 ms |       8.3 ms |
| Custom property on the editor root   |            2,410 ms |      41.2 ms |
| Custom property on the panel element |              264 ms |       8.3 ms |
| `width` on the panel element         |               14 ms |       8.3 ms |

Use a custom property for a value that changes rarely. For a value that
changes per frame, write the property itself on the element that needs it. The
cost of a custom property grows with the number of elements below it. The
minimap's box carried its offset as one at first. The map draws one shape per
node, and each of them was restyled on every frame of a slide: 92 elements
per frame on Supply Chain, against 8 with `right` written on the minimap.

## Selectors that make a write dear

A direct write makes the browser work the element's style out in full, where a
CSS transition only applies the animated value. That is cheap unless a rule
on the element is expensive to match. The panels' container had four
`:has()` rules that looked for a resize handle being dragged, and matching
them searched every element in the panel:

| One `transform` write on the left sidebar, 3,500 elements | Style recalculation |
| --------------------------------------------------------- | ------------------: |
| With the `:has()` rules on the panel                      |             0.95 ms |
| With the attribute on the panel itself                    |             0.15 ms |
| A browser animation, for comparison                       |             0.05 ms |

`GlassPanel` now sets `data-resizing-edge` on its own element while its handle
is dragged, from the handle's `onResizeStart` and `onResizeEnd`. Keep `:has()`
off any element whose style is written per frame or per pointer move.

## Saving

A drag saves the size to the user settings when it ends, through
`onResizeEnd`. Saving re-renders every reader of the settings and writes local
storage, which is one frame of about 25 ms on the Supply Chain example. During
the drag nothing is saved.

## What a drag costs

Sixty pointer moves on the Supply Chain example with the Visualizer editor
open, medians of three runs, production build. Script time per pointer move:

| Drag                   | In editor state | Sizes outside React | Insets outside React too |
| ---------------------- | --------------: | ------------------: | -----------------------: |
| Properties panel width |         23.8 ms |              4.6 ms |                   2.1 ms |
| Bottom panel height    |         25.2 ms |              4.7 ms |                   2.5 ms |
| Left sidebar width     |         25.9 ms |              6.2 ms |                   3.5 ms |

For comparison, a drag of the splitter between two sections of a panel, which
never went through editor state, costs 1.8 ms per move.

Frames over 12 ms per drag went from 13, 32 and 62 to 1 or 2: the release,
when the size is saved. Style recalculation and layout did not change. On the
profiling build, React render time for the Properties panel drag went from
1,026 ms to 50 ms. With a 4x CPU throttle its script per move went from
120.8 ms to 6.8 ms.

Those figures were taken with the sizes in stores of Petrinaut's own, written
to the elements at once. Motion values, written once per frame, cost the same.
Three rounds of each, run in turn on the same day:

| Drag                   | Own stores | Motion values |
| ---------------------- | ---------: | ------------: |
| Properties panel width |     2.3 ms |        2.5 ms |
| Bottom panel height    |     2.7 ms |        2.8 ms |
| Left sidebar width     |     4.5 ms |        3.9 ms |

Motion adds 4.4 kB of gzipped code for those three functions.

Reproduce with `benchmarks/monaco-performance/geometry.mjs`. Compare two
builds only by runs that alternate between them: the same build measured on
two days differed by more than the two columns above.

## What a slide costs

Before, the panels slid by CSS transitions that a flag in React state switched
on. Main-thread work per toggle on Supply Chain, production build, two rounds
of three samples that alternate between the builds:

| Toggle                     | Script before | Script now | Style before | Style now |
| -------------------------- | ------------: | ---------: | -----------: | --------: |
| Open the Properties panel  |        121 ms |     126 ms |        37 ms |     38 ms |
| Close the Properties panel |         94 ms |      90 ms |         9 ms |      8 ms |
| Open the bottom panel      |         92 ms |      93 ms |         4 ms |      5 ms |
| Collapse the sidebar       |         71 ms |      51 ms |         7 ms |      5 ms |
| Expand the sidebar         |         55 ms |      49 ms |         6 ms |      4 ms |

Layout and the longest frame did not change. A frame of a slide recalculates
the style of 8 elements in 0.2 ms, where a frame of the transitions took
0.1 ms for 10.

What changed is what moves together. Under CSS transitions each element eased
on its own curve: one frame into a slide the Properties panel was 117 px in
and the minimap had moved 2 px. Opening the assistant moved the Properties
panel in one step. Now every follower reads the same value in the same frame,
and the gap between a panel and what keeps clear of it is the same on every
frame.

`animateValue` adds 8.2 kB of gzipped code. Motion's `animate`, which also
animates elements, would add 22.8 kB.

Reproduce with `benchmarks/monaco-performance/panel-toggles.mjs` and
`assistant-dock.mjs`.

:::danger[Readers that still render on each move]

About two React commits per move remain during a drag with a visualizer
window open. The window reads the insets as a value, and it renders with the
canvas viewport, which the camera moves while it keeps the selection in view.
Opening or closing a panel still sets a field of the editor's state, so every
reader of the editor context renders once per toggle. The slide itself renders
only the panel, twice.
Tracked in
[FE-2169](https://linear.app/hash/issue/FE-2169/prototype-faster-monaco-opening-and-typing-in-petrinaut).

:::
