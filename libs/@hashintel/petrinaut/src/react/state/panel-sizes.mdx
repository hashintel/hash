---
title: Panel sizes outside React state
description: How a panel drag changes the page without rendering the editor, and the rules for reading a size.
sidebar_order: 30
---

A panel size changes on every pointer move of a drag. Held in React state, each
move re-rendered every reader of the editor context. The sizes are therefore
held in stores, and the elements that depend on a size are written directly.

```text
pointer move
  -> ResizeHandle.onResize(size)
  -> panelSizes.propertiesPanelWidth.set(size)        a store, no React state
       -> styleFromStores: panel.style.width = size   each dependent element, no render
       -> useStore readers re-render                  only those that compute with it
pointer up
  -> ResizeHandle.onResizeEnd()
  -> user settings saved                              once per drag
```

## The parts

| Part                                  | File                                                             | Job                                                                  |
| ------------------------------------- | ---------------------------------------------------------------- | -------------------------------------------------------------------- |
| `PanelSizes`, `createPanelSizes`      | `react/state/panel-sizes.ts`                                     | One store per size, in CSS pixels.                                   |
| `PanelSizesProvider`, `usePanelSizes` | `react/state/panel-sizes-provider.tsx`, `panel-sizes-context.ts` | Creates the stores from the saved settings, once per editor.         |
| `styleFromStores`                     | `ui/lib/style-from-stores.ts`                                    | A ref that writes an element's inline style from stores.             |
| `ResizeHandle`                        | `ui/resize/resize-handle.tsx`                                    | Asks for the size when a drag starts, reports each move and the end. |

The stores keep one identity for the editor's life. Reading `usePanelSizes()`
never re-renders the reader.

## Reading a size

Pick the first row that fits.

| The reader                                                | Reads with                              | Renders per pointer move |
| --------------------------------------------------------- | --------------------------------------- | ------------------------ |
| An element whose style is a function of one or more sizes | `ref={styleFromStores(sizes, toStyle)}` | No                       |
| An event handler or an effect                             | `size.get()`, or `size.subscribe()`     | No                       |
| A component that computes with the number while rendering | `useStore(size)`                        | Yes, that component      |

```tsx
const { propertiesPanelWidth, bottomPanelHeight } = usePanelSizes();

<GlassPanel
  ref={styleFromStores(
    { propertiesPanelWidth, bottomPanelHeight },
    (sizes) => ({
      width: `${sizes.propertiesPanelWidth}px`,
      bottom: `${isBottomPanelOpen ? sizes.bottomPanelHeight + PANEL_MARGIN : 0}px`,
    }),
  )}
  resizable={{
    edge: "left",
    getSize: () => propertiesPanelWidth.get(),
    onResize: (width) => propertiesPanelWidth.set(width),
    onResizeEnd: () => saveWidth(propertiesPanelWidth.get()),
  }}
/>;
```

The Properties panel follows two stores: its own width, and the height of the
bottom panel it ends above. `toStyle` may close over React values such as
`isBottomPanelOpen`. When one changes, the component renders, the ref is
attached again and the style is written with the new value.

`styleFromStores` must not set a property that the element's React `style`
prop also sets: React would write its own value back on the next render.

## Why the write goes to each element

A custom property on the editor root looks like the simpler design: one write,
and every reader picks it up with `var()`. It was built first and measured.
A custom property is inherited, so the browser restyles every element below
the one it changes on, whether or not any of them reads it.

Sixty frames with one write each, on the Supply Chain example with 9,288
elements under the editor root (M1 Max, Chromium 145, production build):

| Write per frame                      | Style recalculation | Median frame |
| ------------------------------------ | ------------------: | -----------: |
| None                                 |                2 ms |       8.3 ms |
| Custom property on the editor root   |            2,410 ms |      41.2 ms |
| Custom property on the panel element |              264 ms |       8.3 ms |
| `width` on the panel element         |               14 ms |       8.3 ms |

Use a custom property for a value that changes rarely. For a value that
changes per frame, write the property itself on the element that needs it.

## Saving

A drag saves the size to the user settings when it ends, through
`onResizeEnd`. Saving re-renders every reader of the settings and writes local
storage, which is one frame of about 25 ms on the Supply Chain example. During
the drag nothing is saved.

## What a drag costs

Sixty pointer moves on the Supply Chain example with the Visualizer editor
open, medians of three runs, production build.

| Drag                   | Script per move, in editor state | In a store | Frames over 12 ms, in editor state | In a store |
| ---------------------- | -------------------------------: | ---------: | ---------------------------------: | ---------: |
| Properties panel width |                          23.8 ms |     4.7 ms |                          13 of 313 |   2 of 185 |
| Bottom panel height    |                          25.2 ms |     4.7 ms |                          32 of 306 |   1 of 170 |
| Left sidebar width     |                          25.9 ms |     6.2 ms |                          62 of 319 |   2 of 225 |

On the profiling build, React render time for the Properties panel drag went
from 1,026 ms to 119 ms. With a 4x CPU throttle its script per move went from
120.8 ms to 16.3 ms, and the 95th-percentile frame from 107 ms to 25 ms.

The frames over 12 ms that remain are the release, when the size is saved.

Reproduce with `benchmarks/monaco-performance/geometry.mjs`.

:::danger[Readers that still render on each move]

The canvas insets read the four sizes with `useStore`, so the minimap, the
viewport controls, the bottom bar, the canvas and the visualizer windows
render on each move: about three React commits per move remain. The assistant
shell reads its width with `useStore` and renders with it. Moving the insets
to stores of their own is tracked in
[FE-2169](https://linear.app/hash/issue/FE-2169/prototype-faster-monaco-opening-and-typing-in-petrinaut).

:::
