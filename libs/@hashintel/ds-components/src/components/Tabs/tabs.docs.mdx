## Installation

1. Install the package.

```sh
npm install @hashintel/ds-components
```

2. Import the component.

```tsx
import { useState } from "react";

import { Tabs } from "@hashintel/ds-components";

export const EntityPage = () => {
  const [tab, setTab] = useState<"overview" | "properties" | "history">(
    "overview",
  );

  return (
    <Tabs value={tab} onChange={setTab}>
      <Tabs.TabList
        items={[
          { id: "overview", children: "Overview" },
          { id: "properties", children: "Properties" },
          { id: "history", children: "History" },
        ]}
      />
      <Tabs.TabContent
        items={[
          { id: "overview", children: <EntityOverview /> },
          { id: "properties", children: <EntityProperties /> },
          { id: "history", children: <EntityHistory /> },
        ]}
      />
    </Tabs>
  );
};
```

### When to use

<DoList
  items={[
    "Use Tabs to split one page region into alternative views the user visits one at a time — an entity's Overview, Properties, and History.",
    "Use link tabs (items with href, no panels) when each tab is a route and the page itself is the content.",
    "Use the folder variant when the panel should read as a contained surface the active tab opens into — code or payload viewers, configuration panes.",
  ]}
/>

### When not to use

<DontList
  items={[
    "Don't use tabs for a display toggle that re-renders the same data — a table/graph/grid switch is SegmentedControl.",
    "Don't use tabs to stage a linear flow users must complete in order — use separate pages or a Dialog sequence.",
    "Don't hide content users need to compare side by side behind different tabs — lay it out together instead.",
    "Don't exceed roughly 7 tabs — scrolling keeps them usable, but a Select or sidebar navigation scans better.",
  ]}
/>

## Anatomy

```tsx
<Tabs value={tab} onChange={setTab}>
  <Tabs.TabList items={tabItems} actions={actionButtons} />
  <Tabs.TabContent items={panelItems} />
</Tabs>
```

`Tabs` holds the selection and wires the parts together. `Tabs.TabList` can
also be used standalone with its `selected` prop when there are no panels —
see [Link tabs](#link-tabs).

## Examples

### Basic

Selection is always controlled: pass the selected tab's `id` as `value` and
update it from `onChange`. Panels pair with tabs by `id`.

Set `variant`, `size`, or `orientation` once on `Tabs` and both children pick
them up; either child can still override for itself.

a flap opening into a bordered panel. Prefer `line` for page-level sections,
`pill` for lightweight switches inside panels, and `folder` where the panel is
a contained surface.

## Behavior

- Every panel renders up front and stays mounted; unselected panels are
  hidden, so their state survives switching.
- Overflowing lists scroll on their main axis with a fade effect instead of a scrollbar. `actions` stay pinned.

## Content

- Name each tab for its view with 1–2 word nouns — "Overview", "History",
  "Permissions" — not actions ("View history").
- Keep labels similar lengths so the row reads as equal peers; one long label
  unbalances the strip.

## Accessibility

Tabs implements the
[WAI-ARIA tabs pattern](https://www.w3.org/WAI/ARIA/apg/patterns/tabs/). Tab moves into and
out of the list, arrow keys move between tabs, and selection follows focus.

### What Tabs provides

- Tab/panel roles, ids, and `aria-controls`/`aria-labelledby` wiring automatically come from
  the item `id`s.
- Items with `href` render real `a` elements, and keyboard selection follows
  the link, so link tabs work as plain navigation.
- `actions` sit outside the tablist: they're reached with Tab, not arrow keys.

### What you must do

- Keep a readable text label inside each tab's `children` — it is the tab's
  accessible name, even when you add icons or tooltips around it.
