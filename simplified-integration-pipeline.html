Simplified integration pipeline

A run moves through four stages. Three of them end in a checkpoint: their result is stored in S3, and every retry restarts from the last one. No stored projections and no data in the workflow engine.

The one rule. A stage either finishes and pushes its result to S3 as a checkpoint, or pushes nothing. When a stage fails, it starts over from the last checkpoint, however many steps it had already done.

Your questions

Three retry points?

Yes: checkpoints 1, 2 and 3. Everything inside a stage is redone when the stage fails.

What does send do?

It sends the planned writes to the Graph, batch by batch. Everything else in it is detail: a batch the Graph refuses is retried one write at a time, so one bad row doesn't block the rest. Every request also takes a token from a shared rate limit.

Is current.json just metadata?

Yes. Two fields: which run is committed, and which runs started sending but never committed.

Do we keep the diff and hash table of every run?

Yes, at checkpoint 2. The next run compares against the committed run's hash table, and any earlier run can be computed again from its checkpoints. That is what replaces the projections.

And the workflow engine?

Restate, or DBOS, runs the four stages in order and starts the run again after a crash. It allows one active run per integration, and handles cancel. It stores none of our data. Each stage starts by checking whether its _done.json already exists; if it does, the stage is skipped.

Each create and patch is the JSON body the Graph receives. Pushed to S3 as checkpoint 3, and handed to step 6.

Step 6 · Send and commit stage

Deliver

Input

writes.parquet, batch by batch, in seq order

Output

current.json   sending: [N]        before the first request
POST  /entities/bulk   [create, …]   batch 0
PATCH /entities/bulk   [patch, …]    batch 1
rejected.parquet       only if the Graph refused writes

If the stage restarts, every batch is sent again. That's safe: the Graph ignores writes that change nothing.

Step 7 · Send and commit stage

Commit

Input

run N, every batch sent

Output: current.json

before  { "committed": "N-1", "sending": ["N"] }
after   { "committed": "N",   "sending": [] }

The next run compares against run N's hashes.parquet.

Contracts

Each stage has an input and either a checkpoint it pushes or a side effect. The structs are sketches for the design, built from types the monorepo already has (RunId, WebId, VersionedUrl, EntityId, Definition).

Stage 1 · step 1

Capture

Read every source in full and store it unchanged.

Input

struct CaptureInput {
    run: RunId,
    web: WebId,
    actor: ActorEntityUuid,   // the run's owner; secrets are read as them
    definition: Definition,   // only its sources are used
}

Does

Resolves each source's secret, reads the source in full, and writes one Parquet file per source to local scratch. Uploads the files, then _done.json last.

Output

Checkpoint 1.

Fails: nothing is pushed. The stage starts over and reads the sources again.

Knows nothing about SQL steps, hashes or the Graph.

Checkpoint 1

Captures

In S3

runs/{run}/capture/
  {source}.parquet    the source's rows as fetched
  _done.json          written last: the checkpoint exists once this does

_done.json

struct CaptureCheckpoint {
    captured_at: Timestamp,                    // becomes loadedAt in Graph provenance
    sources: BTreeMap<SourceName, FileRef>,
}

struct FileRef {
    key: String,      // S3 key
    sha256: String,   // checked when the file is read back
    bytes: u64,
    rows: u64,
}

Size: the size of the sources. On this branch, captures are already stored under their sha256 and bound to the run. That binding plays the role of _done.json for one source.

Stage 2 · steps 2 to 4

Hash and diff

Turn the captures into one row per entity, and work out what changed since the committed run.

Input

struct DiffInput {
    run: RunId,
    definition: Definition,
    capture: CaptureCheckpoint,          // checkpoint 1 of this run
    committed: Option<DiffCheckpoint>,   // checkpoint 2 of the committed run
    resend: Vec<PlanCheckpoint>,         // runs that started sending, never committed
    mode: Mode,                          // Normal | Reconcile
}

Does

  1. Loads the captures into a fresh DuckDB workspace.
  2. Runs the definition's SQL steps and checkpoints, producing one table per sink and link pipeline.
  3. Derives each row's entity ID from namespace, type and source ID, and its content hash: an md5 of the mapped columns.
  4. Compares with the committed run's hashes, by entity ID: new is insert, different hash is update, gone is archive.
  5. Marks every entity in a resend run's writes for sending again. In reconcile mode, every row.
  6. Applies the guards: duplicate IDs, mass archive, partial sources, hash or config version changes.

Output

Checkpoint 2.

Fails: nothing is pushed. The stage starts over from checkpoint 1; the sources are not read again.

Knows nothing about the network, secrets or request formats.

Checkpoint 2

Hashes and diff

In S3

runs/{run}/diff/{sink}/
  hashes.parquet    every entity this sink has written, live or archived
  changes.parquet   only what changed since the committed run
runs/{run}/diff/_done.json

hashes.parquet

entity_id      VARCHAR   web~uuid
source_key     VARCHAR   the row's primary key, as JSON
content_hash   VARCHAR   md5 of the mapped columns
live           BOOLEAN   false once archived; kept so reconcile can archive again

changes.parquet

entity_id      VARCHAR
op             VARCHAR   insert | update | archive | resend
…                        the mapped columns, except for archives

_done.json

struct DiffCheckpoint {
    sinks: BTreeMap<SinkId, SinkDiff>,   // sinks and link pipelines
}

struct SinkDiff {
    entity_type: VersionedUrl,
    hash_version: u32,     // a change sends every row again
    config_hash: String,   // likewise for a changed mapping
    hashes: FileRef,
    changes: FileRef,
    counts: DiffCounts,    // inserted, updated, unchanged, archived
}

Size: the hash table grows with the number of entities, at a few dozen bytes each. The changes grow with what changed. Kept for every run.

Stage 3 · step 5

Plan writes

Turn every change into the exact request the Graph will receive, without sending anything.

Input

struct PlanInput {
    run: RunId,
    web: WebId,
    namespace: String,          // entity IDs derive from it
    definition: Definition,     // property mappings
    captured_at: Timestamp,
    diff: DiffCheckpoint,       // checkpoint 2 of this run
}

Does

  1. Reads the changes, a chunk at a time.
  2. For each insert, update or resend, plans a create and a patch. The patch replaces all properties, so a value that became empty is removed. For each archive, plans an archive patch.
  3. Puts the writes in send order: entities, links, link archives, entity archives.
  4. Cuts them into batches of at most 128 writes and about 1.5 MB, under the Graph's 2 MB request limit.
  5. Writes rows that cannot be converted to issues.parquet.

Output

Checkpoint 3.

Fails: nothing is pushed. The stage starts over from checkpoint 2.

Knows nothing about sources or HTTP.

Checkpoint 3

Planned writes

In S3

runs/{run}/plan/
  writes.parquet    one row per Graph write, in send order
  issues.parquet    rows that could not be planned; no row values
  _done.json

writes.parquet

seq         UBIGINT    send order
batch       UINTEGER   writes sent in one request
group       VARCHAR    entities | links | link-archives | entity-archives
entity_id   VARCHAR
create      JSON       body for POST /entities/bulk; empty for archives
patch       JSON       body for PATCH /entities/bulk

A patch, as stored

{
  "entityId": "{web}~{uuid}",
  "entityTypeIds": ["https://…/entity-type/flight/v/1"],
  "properties": [{ "op": "replace", "path": [], "property": { … } }],
  "archived": false,
  "provenance": { "actorType": "machine", "sources": [{ "type": "integration", "loadedAt": "…" }] }
}

_done.json

struct PlanCheckpoint {
    writes: FileRef,
    issues: FileRef,
    batches: u32,
    counts: BTreeMap<WriteGroup, u64>,
}

Size: grows with the number of changes. These are exactly the requests the Graph receives.

Stage 4 · step 6

Send and commit: deliver

Send the planned writes to the Graph.

Input

struct SendInput {
    run: RunId,
    plan: PlanCheckpoint,   // checkpoint 3 of this run
}

Does

  1. Adds the run to sending in current.json.
  2. Reads writes.parquet batch by batch, in order, and sends each batch. Each request first takes a token from the rate limit shared by all workers.
  3. If the Graph refuses a batch, sends its writes one at a time. A create that finds the entity becomes its patch; a patch that finds none becomes its create.
  4. Writes the Graph refuses for their own data go into the send report.

Output

runs/{run}/send/rejected.parquet   only if writes were refused
  entity_id   VARCHAR
  status      USMALLINT
  reason      VARCHAR             no row values

Fails: starts over from checkpoint 3 and sends every batch again.

Sending twice is safe. IDs are deterministic, create falls back to patch, and the Graph ignores a patch that changes nothing. Knows nothing about sources, SQL or hashes.

Stage 4 · step 7

Send and commit: commit

Make this run the one the next run compares against.

Input

struct CommitInput {
    run: RunId,
}

Does

Writes current.json with committed set to this run and sending emptied. The write is conditional on the version this run read, so a second run can't overwrite it unnoticed.

Fails: writes it again. If it already names this run, there is nothing to do.

Metadata

current.json

struct Current {
    committed: Option<RunId>,   // whose hashes the next run compares against
    sending: Vec<RunId>,        // runs that started sending and never committed
}

Why sending: a run that dies while sending leaves some of its writes in the Graph, but committed still names the run before. The next run reads that run's writes.parquet and sends those entities again with current values, or archives them. Nothing stays wrong.

S3 layout

Everything for one integration

tenants/{web}/integrations/{integration}/
  current.json                     committed run, sending runs
  runs/{run}/
    capture/{source}.parquet
    capture/_done.json             checkpoint 1
    diff/{sink}/hashes.parquet
    diff/{sink}/changes.parquet
    diff/_done.json                checkpoint 2
    plan/writes.parquet
    plan/issues.parquet
    plan/_done.json                checkpoint 3
    send/rejected.parquet          only if writes were refused

Every run keeps its three checkpoints. Restore and reconcile are ordinary runs:

  • Restore to run K: start a run from K's checkpoint 1, with K's definition, and diff against the committed run.
  • Reconcile: a run in reconcile mode, which sends every row again and archives every archived entity again.

How many runs to keep is a retention setting.

Still to decide

  1. Type version bumps. Entity IDs include the versioned type URL, so a bump creates new entities and archives the old ones. Is that what we want?
  2. Replacing all properties in one patch. Confirm with the Graph team that it accepts a replace at the root path, and still treats an unchanged one as a no-op.
  3. Roll forward instead of an immediate restore. After a run dies while sending, the Graph is mixed until the next run, or until a restore run.
  4. Retention. How many runs to keep.
